## 一、现在只推荐这一条主线

**暂定题目：面向 LLM 生成 LLVM IR 的优化收益保持修复。**

英文工作标题：*Preserving Optimization Gains when Repairing LLM-Generated LLVM IR*。

一句话解释：模型同时改了几处代码，一处改错后，不急着把全部结果扔掉；先检查哪些修改组合仍然正确且有收益，再让模型只重写需要处理的部分。

这里的 LLVM IR（Intermediate Representation，中间表示）是编译器内部使用的程序形式。LLM 仍然直接输出具体程序的 IR，不输出 Pass 序列，也不生成可复用的优化规则，所以主类别仍是 **Translator**。

唯一主研究问题：

> 在相同模型调用与验证预算下，对语法合法但语义验证失败的 LLM 优化候选，保留可验证、有收益的修改组合，再进行局部重写，能否比完整重生成和普通局部修复得到更多正确且更小的 IR？

## 二、把范围固定下来

| 项目 | 本轮收敛结果 |
|---|---|
| 输入与输出 | LLVM IR → 优化后的 LLVM IR |
| 第一版程序 | 无循环、无内存副作用的整数直线代码；完整单基本块函数 |
| 要处理的失败 | 语法合法，但 Alive2 给出语义反例的候选 |
| 不处理 | 验证超时、任意循环、指针别名、跨架构、GPU Kernel、编译器规则生成 |
| 唯一核心机制候选 | 在正确性约束下保留优化收益，而不是只追求最少修改或修复通过 |
| 主指标 | 固定预算内，验证通过且 IR 指令数严格减少的函数比例 |
| 配套指标 | 全样本平均 IR 缩减、失败候选救回率、模型 Token、验证调用与耗时 |
| Runtime | 不作为必达目标；没有实测就不声称加速 |
| 第一版训练 | 不训练；先用固定模型及推理时方法验证机制 |

## 三、为什么没有直接宣布“创新成立”

“编译反馈 + LLM 修复”“定位错误后填空”“分析程序后回退”都已有研究。此次技能要求的近邻审查改变了原先较宽泛的“局部修正”提案：现在只保留**优化收益保持**这一待检验的区别，并强制与普通局部修复、纯工具回退搜索比较。

当前证据最强的是：验证失败确实会发生，反馈修复有明确前作。最弱的是：真实错误候选中究竟有多少可保留的优化，以及收益感知机制是否优于简单搜索。后两点必须通过实验回答，不能从几篇论文拼接推断。
