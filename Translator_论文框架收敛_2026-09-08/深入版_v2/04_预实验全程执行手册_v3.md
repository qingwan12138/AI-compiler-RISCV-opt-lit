## 0. 先说明你最后要得到什么

不是先做一个完整系统，而是依次回答：

1. 固定 Oz 编译基线后，真实数据是否还有可以被 LLM 改善的空间？
2. LLM 产生的错误候选中，是否存在值得修复的候选？
3. 简单重采样或整函数反馈能解决多少，局部修复是否还有必要？
4. 若有必要，跨反例一致性与区域接口信息是否有独立价值？

LLM 仍直接输出优化后的 LLVM IR（编译器使用的中间程序表示），不是选择 pass，也不是生成通用优化规则。

三种推进方式中，推荐“分阶段验证”：直接实现完整框架成本最高、风险未消除；只跑整函数反馈能建立基线但不能检验局部机制；分阶段验证可以在无收益时及时停止。

所有样本数、预算和门槛都是本次建议的研发止损规则，不是已完成结果、领域标准或统计功效保证。付费阶段开始前冻结配置，不能看到结果后降低门槛。

## 1. 我们怎样全程协作

你不用先学会全部 LLVM 或一次配置完整服务器。每次只推进一个检查点。

| 每一轮 | 你提供什么 | 我负责什么 | 何时结束该轮 |
|---|---|---|---|
| 准备 | 可用机器、访问方式、模型来源和费用上限 | 核对约束，形成与实际机器匹配的命令 | 输入齐全，不泄露凭据 |
| 实现 | 批准当前小模块的实现范围 | 实现、单测、检查错误状态与日志 | 验收通过，不以“文件存在”代替通过 |
| 运行 | 批准明确命令和批次预算 | 执行或提供你能复制的命令，检查进度 | 到批次结束或硬上限 |
| 解读 | 若在外部服务器执行，提供完整输出与日志路径 | 区分工具故障、数据限制、真实负结果 | 写出继续／修改／停止及理由 |

如果当前会话不能访问服务器，由你运行我给出的命令并贴回结果；不要求上传密钥。进程卡住或失败，先留证据、查原因，不盲目重试。

总路线：S0 → S1 → S2 → S3 → 决策 → S4 → S5。S3 之前不开发复杂区域契约；S4 无增量则不启动 S5。

建议开发顺序：验证与日志适配器 → 函数筛选器 → 固定模型调用器 → 简单基线 → 区域检查器。先不训练、不做 RL、不做多 Agent、不做 Pareto 前沿、不做任意重叠补丁库。

## 2. S0：确定执行机器、版本和花费

### 2.1 当前已知情况

本机是 Windows。本轮 PATH 检查发现 `py.exe` 和 `wsl.exe`，未发现 `clang、opt、alive-tv、cmake、ninja`。发现 wsl.exe 不代表已安装可用 Linux 发行版；未发现工具也不代表整台机器完全没有安装。

优先使用已有 Linux 服务器；其次是已能正常启动的 WSL2；新租机器和新安装系统是另外的授权事项。先不承诺 GPU 必需：LLVM 和验证器主要用 CPU，只有本地模型推理涉及显存。

建议原型起步资源为 8 个 CPU 线程、32 GB 内存和较充足磁盘；这是规划建议，不是最低要求，源码编译 LLVM 所需空间和内存另算，低配机器降低并行度。模型显存依据选定权重、精度、上下文和推理引擎实测，不凭参数量保证能装下。

### 2.2 第一轮可执行的只读检查

Windows PowerShell：

```powershell
Get-Command py,wsl,git,clang,opt,alive-tv -ErrorAction SilentlyContinue
wsl --list --verbose
```

进入已经获准使用的 Linux 终端后再运行下面命令，不要原样粘贴到 PowerShell：

```bash
uname -a
lscpu
free -h
df -h .
command -v clang opt alive-tv cmake ninja python3
nvidia-smi
```

`nvidia-smi` 不存在只说明此检查不可用，不阻止 CPU 工具验收。公开日志前删除主机名等不必要个人信息，不打印环境变量全集。

### 2.3 版本如何选

按 [Alive2 官方说明](https://github.com/AliveToolkit/alive2)选择相容的 LLVM/Alive2 构建组合，记录两者完整 commit、Z3 版本、编译参数和二进制哈希。不要任意拼接发行版 LLVM 与最新 Alive2，也不要把随时变化的 main 当版本锁。

首次在实际机器完成构建测试后才给出锁定安装命令。此处不提供未验证 commit 或声称某 Docker 镜像已经可用。工具数据 IR 也必须与解析器版本相容，不用字符串替换来“修好”不兼容语法。

模型沿用一个能固定版本的代码模型；若采用旧协议的 Qwen2.5-Coder-7B-Instruct，它只是低成本载体，不是“最新最强模型”。记录权重 revision 或 API 返回的实际模型 ID、推理引擎、精度、聊天模板和采样配置。服务不支持 seed 时明确记录，不能承诺请求可逐字重现。原始响应保存后可离线重放工具评价。

模型提供商、传输内容、费用上限需要确认。只发送获准的公开 IR 与必要反馈，不发送私有语料库、账号信息、系统目录内容。

### 2.4 S0 验收

产物：`environment.lock.json`（计划文件，尚未生成）、机器资源摘要、模型配置、费用硬上限。

通过条件：能定位工具的绝对路径与版本；机器可持续运行；模型调用方式明确。尚无模型也可以先做 S1/S2。环境未通过，不开始大规模生成。

## 3. S1：确认工具不会把错误当正确

### 3.1 固定评价链

设 C 为锁定版本的 Oz 清理流程，P 为清理后的原函数，Q 为模型候选：

```text
原始函数只读保留 → C → P
模型输出 Q → 格式及范围检查 → C → Q_clean
Alive2 检查 P → Q_clean
通过后才允许计入优化收益
```

Alive2 做的是源到目标的 refinement（精化检查：目标不能引入源程序不允许的行为），不是简单地跑几个测试，也不要求对所有程序都能给出结论。[官方工具说明](https://github.com/AliveToolkit/alive2)

所有函数保持签名、目标布局、属性约束。初期无调用、单基本块，避免跨过程变换。禁止通过删除源程序属性、增加 assume 或新建未定义行为来获得“优化”。清理后再次检查支持范围；出现不支持语义则不能交给简化解释器硬剪枝。

### 3.2 命令和文件的关系

工具与测试文件准备好后，Linux 中的基本命令为：

```bash
opt --version
opt --help
alive-tv --help
opt -S -passes='default<Oz>' source.ll -o source.clean.ll
opt -S -passes='default<Oz>' candidate.ll -o candidate.clean.ll
alive-tv source.clean.ll candidate.clean.ll
```

这是工具调用示例，`source.ll` 等测试文件尚待创建，不是当前目录已有文件。正式运行由待实现的进程包装器捕获输出、退出码和超时。具体参数以锁定二进制帮助为准。[opt 官方说明](https://llvm.org/docs/CommandGuide/opt.html)

C 在原程序与候选上完全一致。先测试重复 Oz 是否稳定；若不稳定，在 S1 内选择并冻结“固定一次”或“有界迭代”的统一规则，记录未稳定实例，之后不得按方法区别处理。

### 3.3 需要创建的验收样例

| 类型 | 数量建议 | 预期 | 用途 |
|---|---:|---|---|
| 原样返回与确定等价变换 | 10 | VERIFIED | 排除工具链不匹配 |
| 确定错误变换 | 10 | COUNTEREXAMPLE | 排除误判正确 |
| IR 语法、类型或 SSA 错误 | 5 | INVALID | 不把解析失败算语义反例 |
| 超时、进程崩溃、未知输出 | 各至少 1 | 对应状态 | 可用受控故障注入测包装器，不伪称真实求解案例 |
| 原区域回填／联合补丁冲突 | 各至少 2 | 恒等通过／冲突拒绝 | 留待 S4 前补齐区域测试 |

测试用人工程序单独标 `synthetic`，永不混入真实样本胜率。对于入口支持的位宽与运算，后续解释器必须与 LLVM/Alive2 交叉检查；未实现解释器时，S3 的普通文本反馈仍可先跑。

### 3.4 结果不能压成一个“成功/失败”字段

分别记录：

- `format_status`：格式、解析、范围是否有效；
- `verdict`：VERIFIED / COUNTEREXAMPLE / TIMEOUT / UNSUPPORTED / TOOL_ERROR / NOT_RUN；
- `gain_status`：STRICTLY_SMALLER / EQUAL / LARGER / UNAVAILABLE；
- `witness_parse_status`：SUPPORTED / UNSUPPORTED / NOT_APPLICABLE。

这样“语义错误但不更小”“通过但无收益”都能保留。没有收益不是一种验证结果。退出码为 0 也不能直接当证明通过。

所有非 VERIFIED 输出均不得进入最终可返回库。超时和未知不等于不等价。原函数 P 是安全回退；返回 P 不算优化成功。

验收产物：`tool_smoke_report.md`、每个夹具的原始 stdout/stderr、状态解析测试、统一指令计数测试。计数使用 LLVM 解析后的 instruction 对象，包含 ret，不数文本行、注释和元数据。

通过条件：已知正确与错误样例全部正确归类，未知不会误通过，离线重放得到相同确定结论。失败则修工具，不评价研究框架。

## 4. S2：先看真实数据够不够，不调用模型

### 4.1 数据来源与采样

主来源选 [LLVM Opt Benchmark nightly](https://github.com/dtcxzyw/llvm-opt-benchmark-nightly) 中可追溯的真实项目 IR；锁定下载清单与文件 SHA256。先检查项目、来源和许可证，不全量下载巨大仓库。项目缺少可用未优化/中间 IR 时，标明上游已优化状态；不能将 Oz 施加于已 O3 优化的数据后，声称是纯 Oz 基线。

在正式取样前冻结三个开发项目和模块选择规则：每项目按路径排序的 SHA256 顺序取最多 20 个模块；大文件大小上限在清单中统一记录。首先清点这些模块内全部定义函数。该有限框架不代表整个代码生态，只对实际抽样范围报告覆盖率。

另预留至少两个不同项目，直到 S5 才查看模型结果。项目不足时不要用同项目随机函数伪装跨项目保留集。

### 4.2 最小范围

- 原生完整函数，单基本块、单整数返回值；
- 主分析对象在 Oz 后 5–80 条指令；
- 初始白名单：无 flags 的 add/sub/mul、and/or/xor、icmp、select、整数截断与扩展、ret；
- 暂不支持内存、指针、调用、phi、循环、向量、浮点、异常、除法与移位；
- 不接受未建模属性或 poison/undef/freeze 语义；过滤而不是删掉源语义。

记录 raw 与 Oz 后两个阶段的长度和排除原因。两边均需能解析；进入主队列的 P 和初始模型候选须满足声明的范围。若想扩展 shift/div 或 flags，先通过新增语义测试并建立新队列，不能悄悄混回旧实验。

LLVM 的 poison 等语义不能用普通 Python 整数随意近似；select 等行为也需按正式语义处理。[LLVM LangRef](https://llvm.org/docs/LangRef.html#poison-values)

### 4.3 原生函数与抽取片段分开

不把 LPO 的包装片段当原生函数。其提取器会把外部操作数变成包装函数参数，改变可见输入接口。[LPO 提取器](https://github.com/uw-pluverse/lpo-artifact/blob/main/lib/Extractor.cpp)

若原生函数少，先扩大真实项目覆盖；再考虑单独的 snippet 队列。不能把手工制造容易优化的样例混进主队列。

按规范化 IR 去重：可消除命名差异，但必须保留常量、类型、属性；近重复同组。日志同时保留原始函数数量和去重后数量。

### 4.4 必须拿到的表

`corpus_manifest.csv`（尚待生成）：

```text
sample_id, project, source_commit, module_path, function_name
source_sha256, origin_kind, upstream_pipeline, license
raw_instruction_count, oz_instruction_count
eligible, exclusion_reason, duplicate_group, split
```

报告逐项目漏斗：扫描函数数 → 可解析数 → 语义范围内数 → Oz 后长度合格数 → 去重后数。排除理由设主原因并可附多标签，防止加总混乱。

决策：目标是至少 120 个去重开发函数、来自至少三个项目；先取每项目 40 个。若某项目不足，不凑数，说明并按预先声明的备选项目清单扩展。两批覆盖摸底后仍不足，就暂停严格原生范围，讨论范围调整；这说明适用覆盖受限，不证明所有 Translator 研究无效。

## 5. S3：自然失败与简单基线——第一笔模型预算用在这里

### 5.1 先做 10 个函数的通信烟雾测试

从非保留集取 10 个函数，每个只生成一次，检查模型实际 ID、提示格式、输出截断、解析状态、日志、单次 Token 与耗时。此批是调试集，后面不混入主比较。

每次输出上限先设 2048 Token，temperature 0.7、top_p 0.95（仅在模型支持时）；不支持的参数记录而非强行伪装。若频繁截断，在该批内统一调整并冻结，而不是只为某方法增加限制。

成本估算：输入 Token × 单价 + 输出 Token × 单价，按提供商实际计价补充其他收费。由烟雾结果估计正式批次上限，用户批准后才继续。密钥放本地受保护配置，永不进入文档或 Git。

### 5.2 初始自然候选调查

冻结 120 个函数，每函数独立生成 4 个候选，最多 480 次调用。每个请求只含 P、固定规则、优化目标，不给局部修复机制特殊线索。

初始提示内容固定为：

> 将给定 LLVM 函数变换为语义合法的更短 IR；目标是经过指定 Oz 流程后的指令数，而非文本长度。保持函数签名、类型、目标布局和既有语义约束，只用允许的运算，不增加 assume 或未定义行为。只返回完整 LLVM IR；无法改进时允许原样返回。

每个可解析、范围内候选都清理并验证，包括未缩小者，以观察真实状态分布。验证外部硬超时初设 10 秒；所有原始响应、清理输出、验证输出保留。

这里生成的是完整 IR。不要为便于本方法对齐而强制所有主样本使用区域格式；之后无法对齐的实例也保留，计入机制覆盖率。结构化生成可以是后续独立队列。

输出两种比例，不能混淆：

- 候选级：480 个请求中各状态有多少；
- 函数级：120 个函数中至少出现一次验证成功／语义失败／有益成功的各有多少。

确定失败池：每函数按调用序号取首个明确 COUNTEREXAMPLE、可解析且在范围内的 Q；不要求它已更小，不按“看起来好修”选。保存 Q 的 raw 与 clean 两版。纯格式错误不混入语义修复问题。

如果不同函数的自然语义失败不足 30 个，最多扩大到总计 360 个开发函数，规模扩展要另核预算。仍不足，则不继续大规模失败修复；不能故意削弱模型或手工造错凑分母。

### 5.3 第一轮只比较三种简单策略

先在固定失败池按 hash 顺序取 10 个起点做工程验收；规则稳定后，在预先选好的最多 30 个起点上完成诊断。每个起点共享相同 P、Q 和初始反馈。

| 策略 | 输入与操作 | 输出 | 要排除的解释 |
|---|---|---|---|
| B0 安全回退 | 不调用模型，返回 P | 原函数 | 原样正确不算优化成功 |
| B1 独立重采样 | 只看 P 和同一优化要求，不看错误 Q | 完整 IR | 单纯多试几次是否足够 |
| B2 整函数反馈 | 看 P、当前 Q、编译/验证反馈、目标 | 完整 IR | 普通反馈是否已经解决问题 |

B2 是 LPO-style 的预算匹配实现，不冒充原作者系统复现。迭代时工作候选与安全最佳候选分开：有效新 IR 更新工作候选，只有验证且有益才能更新安全最佳；解析失败不破坏上一个有效工作候选。达到上限返回安全最佳或 P。

每个策略每起点最多 4 次生成、8 次完整验证、16k 输入 Token、8k 输出 Token、5 分钟墙钟，任一上限先到即停。完整预算定义见第 9 节。10 个起点的调试输出不用于最终显著性判断。

B1/B2 在 30 个起点上的最大修复请求数为 30×2×4=240，另加初始调查；不是一次默认授权调用 720 次。前 10 个若调了协议，保留为开发数据，不拿旧输出拼接成冻结后的结果。

### 5.4 有限候选复用是独立小诊断，不阻塞 B1/B2

仅对可可靠对齐的失败 Q，固定最多 6 个互不重叠区域，每区保留 P/Q 两种版本，最多 64 个组合。检查原样回填与类型接口，完整重建后统一清理和验证。初版不处理重叠补丁。

最多 20 个函数；每次验证 5 秒，总墙钟预算 2 小时，记录线程数与总 CPU 秒。所有组合必须确定验证后才可称“该有限库已穷尽”；有超时、截断或无法对齐就标未知。找不到组合不证明任意新生成都不可能。

观察：多少有益正确版本可以仅靠组合找回；多少需要多个修改同时存在，单个修改却错误。自动恢复不能简单假设“单步错误意味着所有包含它的组合都错误”。

若这一步工程投入超过两个工作日仍不能稳定对齐，先放下，不为一个诊断写大型 IR diff 系统；将对齐困难如实记录，继续判断整函数路线。

### 5.5 S3 检查点

产物：完整候选状态漏斗、固定失败起点清单、B1/B2 配对结果、可选组合诊断、成本账单和三个可重放案例。

建议按以下规则决定：

- 至少 10 个不同失败函数、跨至少两个开发项目，被某种方法变为验证且严格缩小的程序：值得研究该范围内的失败修复。
- 仅 1–9 个：证据偏弱，只允许小批诊断或调整范围，不直接扩完整框架。
- 没有：记录预算与工具未知率，不称数学上的无解；停止当前大规模投入。
- 若普通重采样与反馈已解决大部分可观察问题，又没有明确局部信息损失案例，不启动复杂局部机制。

这些是投入门槛，不是声称“10 个案例足够发论文”。

<a id="stage-s4"></a>
## 6. S4：只验证一个机制——跨反例一致性是否帮得上忙

### 6.1 最小方法，不保留原版全部模块

工作候选是一棵完整函数版本树。一次局部修改产生完整新版本并记录 parent；联合区域 AB 作为原子修改，不再与旧 A/B 任意组合。安全最佳只由整函数验证更新。

每次失败后：确定有限候选区域 → 检查接口与反例约束 → 选择区域 → LLM 输出区域 IR → 重建完整函数 → 统一清理 → 完整验证 → 更新工作候选／安全最佳。

候选范围由固定的 SSA 定义—使用关系生成：先枚举连续指令范围，再尝试相邻范围合并，最多 12 个范围；排序按指令数、起始位置。接口是完整 live-in/live-out（区域外传入／区域外使用的值），不人为隐藏依赖来制造优势。最多两项 live-out，超出则回退整函数。

### 6.2 必须验证的逻辑

同一个局部程序，对于相同局部输入必须给出一致输出。但输出未必唯一，不能先为每个反例随便选一个输出，再因为它们不同而误判无解。

针对每个源定义明确的反例 w，构建固定外部程序 E 所需的关系 K_w(h)：将区域输出设为 h 后，E 的最终结果应与 P 一致且保持合法。将局部输入元组相同的反例分组，共享同一个符号输出 h，再联合求解所有 K_w。

这相当于从“每个反例自己能满足”升级到“相同局部输入需要共享解”。只有在受支持的确定性子集中，确定 UNSAT 才能排除该固定接口和固定外部上下文；SAT 仍不保证存在可写出的短 IR，UNKNOWN 不剪枝。

更严格地说，区域输出若无法从外部环境中独立确定，先保留关系约束，不强行转换成单一 I/O 标签。外部候选改变后必须重新计算约束；缓存包含上下文哈希。

注意：位运算示例 x 与 x&1 只是验收反例，不是自然数据优势。真实活跃输入若包含 x，原示例的冲突就不成立。另记录“同局部输入但要求冲突”的自然发生率；若几乎不发生，该机制可能没有应用空间。

### 6.3 先完成机制单测，后调用模型

- 相同输入要求 0 和 2：联合 UNSAT。
- 两个约束允许区间有交集：SAT，不能因单独任选不同值而误剪枝。
- 多个不同局部输入：不凭输出不同判冲突。
- 外部程序改变：旧契约缓存失效。
- 不支持 poison/undef、超时、接口无法重建：UNKNOWN 并回退。
- 区域扩大后能读取被丢失信息：允许重新判断，不永久封禁。

所有排除决策记录反例 IDs、输入分组、公式、求解结果和作用范围。错误排除一个已知可行夹具即停止硬剪枝。

### 6.4 三个对照隔离贡献

先取 10 个开发失败起点调通，再在新的、预先固定的 30 个自然失败起点比较：

| 策略 | 区域、模型、预算 | 唯一变化 |
|---|---|---|
| B2 整函数反馈 | 同一 P/Q 与总预算 | 不限制局部范围 |
| R0 最小范围反馈 | 固定区域排序、原始反例反馈 | 无关系约束 |
| R1 逐反例约束 | 与 R0 同范围候选 | 使用逐反例可满足性和关系反馈 |
| R2 跨反例一致性 | 与 R1 相同 | 相同接口输入共享输出的联合检查 |

R2 对 R1 是预设主机制比较；R2 对 B2 检查实际用途。否则不能分清优势来自“局部提示”还是“新一致性检查”。暂时不要加入收益前沿。

每方法每起点仍使用 4 次生成、8 次整函数验证、16k/8k Token、5 分钟总墙钟。局部求解每次最多 1 秒、每起点累计最多 20 秒，最多 12 个区域；先到限额就回退文本/整函数，不消耗完预算后才开始生成。局部分析与清理全部计时。

最多保存 8 个代表反例供提示使用，选择规则固定；后台可保留全部受支持反例。四次修复最多四个验证失败反例时自然不会达到 8，不能为了凑约束无预算地追加验证。

4×30×4=480 是本阶段修复调用上限，初始起点收集另计。调试、扩样与对照复用严格分开。

### 6.5 继续条件

检查 R2 是否真正触发了新的排除／扩区决策，而非只增加提示长度。逐个展示 R2 赢、输、无变化的程序。

值得做 S5 的探索性信号：R2 相对 R1/B2 的有益修复比例提高，或在相近比例下明显省成本；优势不是集中在一个模板，并且出现至少 5 个不同函数、至少两个项目的可解释机制作用案例。主机制无触发或只有开销，就删除这一主张。

若 R1 有用但 R2 没用，结论是关系反馈可能有价值，不是跨反例一致性被验证。若简单组合就足够，不把新生成当必需贡献。

<a id="stage-s5"></a>
## 7. S5：小规模独立确认，不直接扩成论文大矩阵

冻结方法、模型、提示、范围和主指标，选至少两个未用于调参的项目，目标 60 个原生函数。不筛选初始失败，做端到端比较。

每函数每方法总共最多 5 次生成：共享的 1 次初始输出＋最多 4 次后续生成。共同初始成本计入每个方法的逻辑预算，实际发送一次；所有方法同样初始，初始成功也记入结果。保留 B1、B2、R1、R2；若某方法已在 S4 淘汰，不为了凑表继续跑。

统一上限：累计 20k 输入／10k 输出 Token、10 次完整验证、6 分钟墙钟；局部分析仍计入总时间。四方法最多实际发送 60＋60×4×4=1020 次生成，早停会减少，启动前重新审批费用。

观察正向趋势是否跨项目保留。60 不是论文统计充分性的保证：报告配对差值和不确定性，不凭一两个净胜样本定方向。如果调整方法，这批自动成为开发数据；另找保留集确认。

暂不默认启动 300 函数×2 模型×3 seeds。只有 S5 信号仍存在，才依据配对差异、费用和希望检测的效应规划更大实验。

<a id="measurements"></a>
## 8. 指标：到底什么算成功

### 8.1 唯一主收益口径

前期固定 J=统一 Oz 后的 LLVM 指令数。严格小于原 P 且整函数验证通过才是有益结果。

`U_IR = 有益结果函数数 / 预先纳入函数数`

`G_IR = 全部函数的平均相对缩减率`

未成功者返回 P，缩减为 0。例如 30 个函数中 6 个各减少 10%，U_IR=20%，G_IR=2%。不得只对 6 个成功者报告“平均提升 10%”作为整体效果。

S3/S4 的 U 是“给定自然失败起点”的条件有益修复率；S5 是所有预选函数的端到端率，不能在同一列混比较。验证正确但不更小另计“正确修复”，不算主成功。

### 8.2 必须附带的成本与覆盖

记录实际请求数、输入输出 Token、模型耗时、清理耗时、验证耗时、局部求解耗时、总墙钟、首个有益结果的时间，以及 timeout/unsupported/tool_error 比例。首个成功时间的未成功者作为右删失或直接报告预算内未达，不能丢掉。

每方法保存 1/2/4 次修复请求前缀结果，不为每个点重新运行。必要时在预先选定子集延长采样预算，检验“多采样就能追平”；该扩展另核费用。

### 8.3 Oz、O3 和二进制尺寸

Oz 主基线不改变，O3 只做后续补充。同一原始输入分别建立 Oz/O3 管线，不把 O3 接在 Oz 后面称 O3-only。如果主数据本就上游优化过，如实命名流水线。

本预实验不要求 runtime。若将论文目标升级为代码尺寸，则在独立测试前把固定后端机器码字节数设为主 J，并同步修改候选选择目标。函数符号字节数与整个目标文件大小不同；后端版本、triple、CPU、代码生成等级、size 属性、LTO 和对齐都需固定。不能只换图表名字。

### 8.4 统计解读

主要展示同函数配对表：R2 独赢、R1 独赢、都成功、都失败；报告 U 的百分点差值、G 和成本差值。候选不是独立样本，重复请求不是新函数。按项目分别报告，函数/近重复族为组处理。

S3/S4 为探索性，不通过反复比较选最大值后宣称显著。S5 主比较预设 R2 对 R1，B2 为重要实用对照。项目只有两三个时，不用复杂 bootstrap 制造“跨所有项目都成立”的印象；小样本区间宽就报告不确定。正式样本规模之后根据目标效应和配对不一致率规划。

## 9. 预算、进程与结果记录

### 9.1 预算是多个上限，不是资源等价证明

生成次数、Token、验证次数、墙钟四类上限共同约束，任一先到立即结束该起点；工具清理默认每调用 10 秒，验证默认 10 秒，模型请求默认 120 秒，且受剩余总预算约束。超时值先在 S1/通信烟雾中校准，然后冻结。

解析错误消耗一次生成，不免费无限重试。已发送但网络响应丢失可能收费，标记 UNKNOWN_REQUEST 并暂停查账，不自动补发。连续 3 次工具错误暂停该批次；日志无增长时先判断进程状态，不能把卡死当正常研究失败。

使用阶段独立累计费用上限。达到限额保留部分结果及停止原因，不只返回已完成成功实例。

确定性工具缓存键含 P/Q 内容、工具二进制、参数和语义配置。方法比较记录逻辑查询数与实际缓存成本，防止后运行方法免费复用而看起来更快。调度随机交错，避免某方法独占服务器空闲时段。

### 9.2 建议输出目录（计划，尚未创建）

```text
translator-pilot/
  configs/           # 版本、预算、冻结提示
  manifests/         # 数据来源、排除、split
  fixtures/          # 工具/语义测试，不进主实验
  data/raw/          # 不覆盖的原始公开 IR
  data/normalized/   # Oz 后基线
  runs/<run_id>/     # 候选、验证、日志，只追加
  reports/           # 每阶段验收和配对结果
```

每次候选保存：P、Q.raw、Q.clean、父候选 ID、提示与响应、模型实际 ID、计数、原始验证输出、退出码、状态、Token、时间、停止原因、哈希。方法涉及区域时再加接口、范围、契约、反例、求解结果和回退原因。

不要在 Git 中提交密钥、模型权重、缓存或大规模生成数据。公开代码与公开数据也要检查许可证；本文没有自动发布授权。

## 10. 遇到问题怎么处理

| 现象 | 首先检查 | 不该做什么 |
|---|---|---|
| 原样 P→P 验证失败 | 工具版本、布局、函数匹配、解析器 | 继续跑模型掩盖工具错误 |
| 大量解析错误 | 提示、截断、IR 版本、格式提取 | 默默用另一个模型无限修好格式 |
| 大量超时／不支持 | 程序范围、属性、版本、CPU 争用 | 记为语义错误或直接删样本 |
| 初始成功很少 | 范围覆盖、Oz 后空间、模型理解 | 马上训练 RL 或降低编译基线 |
| 回原函数总能“修好” | 主指标是否要求严格收益 | 将正确率当优化率 |
| R2 没触发 | 是否真的有共享局部输入冲突 | 手动隐藏输入来造优势 |
| R2 优势只在玩具上 | 真实分布是否存在该失败模式 | 把玩具并入真实表格 |
| 方法多用 Token 才赢 | 等预算曲线与额外分析成本 | 只报告验证调用数下降 |
| IR 更短但二进制不变 | 后端指标是否不同 | 宣称 runtime 或二进制收益 |

## 12. 预估日程与当前第一步

| 阶段 | 粗略开发工作量 | 交付与停止点 |
|---|---|---|
| S0 | 半天摸底，安装编译另计 | 可用机器、版本、预算；否则暂停模型阶段 |
| S1 | 2–4 工作日 | 验证与日志可信；否则修工具 |
| S2 | 1–3 工作日 | 真实样本覆盖；不足则调整范围 |
| S3 | 2–4 工作日，模型时间另计 | 自然失败与简单方法空间；无空间则止损 |
| S4 | 4–8 工作日，取决于语义适配 | 唯一机制与消融；无增量则删机制 |
| S5 | 按 S3/S4 实测吞吐估计 | 独立趋势；不稳定则不锁定论文主张 |

整体是数周原型研究，不承诺固定日期完成或一定正结果。现阶段不需要你一次读完所有实现细节：**实际执行从 S0 的机器检查开始。**你最先提供的是可用 Linux 机器或 WSL 状态；模型与费用在首次付费前确认。

最终研究判断分三种，不把任何结果都叫成功：

1. 有自然问题、有独立机制增量、有可重放证据：进入更大规模论文实验。
2. 有问题但新机制无优势：保留可靠工具和负结果，删掉新机制，重新收敛。
3. 限定范围下问题罕见或基本没有收益：停止当前失败修复主线，不继续堆模块。
