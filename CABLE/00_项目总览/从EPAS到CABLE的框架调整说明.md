# 从 EPAS 到 CABLE 的框架调整说明

## 1. 为什么需要调整

EPAS 的核心思想是让不同架构保持同一项通用优化知识的预期效应，并只学习必要的架构增量。它解决了“通用知识不能直接等同于固定 Pass 序列”的问题，也明确要求真实编译和硬件测量。

但继续推演后发现，EPAS 仍有三个不足：

1. **最小架构增量难以准确定义**：规则数、参数量和候选数并不能直接代表知识增量；
2. **未见平台快速适应扩大了研究范围**：需要更多平台、校准程序和迁移算法，会削弱当前硕士课题的主线；
3. **知识失效后的学习闭环不完整**：EPAS 可以发现效应没有保持，却没有明确说明如何用这次失败修正知识本身。

CABLE 因此将问题重新集中为：

> 如何通过真实多架构效应确定编译知识的适用边界，并利用目标平台反例持续修正该边界？

## 2. 保留的内容

CABLE 保留 EPAS 中以下有效思想：

- 通用知识不能只是自然语言意图或固定 Pass 序列；
- 一条知识必须有可测量的预期后端效应；
- x86、ARM、RISC-V 可以采用不同实现；
- IR、目标代码和真实运行结果需要共同作为证据；
- RISC-V 是重点实验平台，但不是方法边界；
- 所有核心结论必须来自真实编译和真实测量；
- 任何阶段均不使用世界模型。

## 3. 退出当前主线的内容

以下内容不再作为 CABLE 的主要贡献：

- 最小架构参数量或最小 Adapter；
- 对未见平台进行零样本或少样本快速适应；
- 用适配参数量定义知识迁移程度；
- 双智能体或多智能体结构；
- 完整端到端强化学习；
- 性能预测世界模型和多步 imagined rollout；
- 第一阶段同时开展代码翻译和编译器调优。

它们可以成为未来扩展，但不能占用当前主线的实验预算。

## 4. 新增的核心思想

### 4.1 知识适用边界

CABLE 把每项优化知识看作一条带边界的结构化规则。知识是否通用，不由研究者预先指定，而由它在多个程序和架构上的真实效应决定。

### 4.2 真实反例

当某项知识在目标平台出现方向相反的性能变化、严重 spill、代码尺寸越界或预期向量化没有发生时，该样本被记录为反例。

### 4.3 边界演化

反例不会只触发一次重新搜索。系统还要缩小、分裂或重新分类知识边界，使后续相似程序不再重复错误复用。

### 4.4 失配驱动修正

架构调优模块读取具体的效应失配维度，针对 spill、访存、分支、代码尺寸或向量化失败选择修正候选，而不是仅依赖单一运行时间进行盲目搜索。

## 5. 框架对照

| 维度 | EPAS | CABLE |
|---|---|---|
| 核心对象 | 效应契约与架构增量 | 带适用边界的效应知识 |
| 主问题 | 如何以较小增量保持效应 | 知识在哪里成立、如何从反例修正边界 |
| 平台目标 | 包含未见平台适应 | 先做好已部署架构的通用与专用调优 |
| 失效处理 | 增加平台特化 | 门控、边界更新、失配驱动修正 |
| 知识更新 | 更新适配结果 | 更新适用条件、知识类别和证据 |
| 主要证据 | 效应误差与增量成本 | 正例、反例、门控结果和重复错误率 |
| 世界模型 | 禁止 | 永久禁止 |

## 6. CABLE 的统一主张

> CABLE 将编译优化知识表示为具有预期效应和可学习适用边界的规则，通过多架构真实测量区分通用、敏感、冲突和专用知识；当目标平台产生反例时，系统不仅执行架构专用修正，还反向更新知识边界，从而减少跨架构负迁移和重复错误。

这使研究重点从“为新平台快速迁移一个模型”转变为“理解并维护编译知识的跨架构复用边界”。

## 7. 版本关系

- 桌面 `EPAS`：历史框架、原始设计和已验证 Mini Demo；
- 桌面 `CABLE`：当前研究主线和后续新增资料；
- EPAS Demo：后续可作为 CABLE 真实测量基础设施，但当前不代表 CABLE 方法已实现；
- 两个文件夹独立保存，不覆盖、不混写。
