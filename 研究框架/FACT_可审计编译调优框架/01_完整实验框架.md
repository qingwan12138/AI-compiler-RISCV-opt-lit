## 1. Experiment Overview

- **Title**：面向真实硬件反馈的可审计编译优化智能体实验
- **Objective**：验证意图落地审计、Pass 反事实归因和硬件性能反例校准能否提高有限预算编译优化的可信度与真实性能
- **Type**：compiler systems benchmark / analysis / optimization
- **Primary target**：LLVM Pass 序列优化
- **Primary objective**：运行时间
- **Secondary objectives**：语义正确率、意图落地率、负优化率、真实测量预算

## 2. 研究问题与假设

### RQ1：意图审计是否能识别“看起来成功但实际未落地”的优化？

H1：相比只使用编译和测试反馈，逐层审计能显著提高 `valid_and_realized` 候选比例，并识别后端擦除和反作用候选。

建议成功阈值：

- `valid_and_realized` 比例相对提高至少 15%；或
- 达到同等合格候选数量时，平均重试次数降低至少 20%；
- 不能以语义正确率下降换取上述提升。

### RQ2：反事实归因是否改善有限预算 Pass 搜索？

H2：在相同真实测量次数下，归因引导搜索比只用终局奖励的搜索获得更好运行时间，或以更少测量达到同等性能。

建议成功阈值：

- 达到相同加速水平所需实测次数降低至少 25%；或
- 相同预算下几何平均性能再提高至少 3%；
- 高贡献 Pass 的删除应在多数重复实验中显著破坏收益。

### RQ3：硬件反例校准能否降低 RISC-V 上的负优化？

H3：加入 x86—K3 收益翻转反例后，K3 上的候选重排序优于未校准版本。

建议成功阈值：

- K3 负优化率相对降低至少 30%；或
- K3 几何平均运行时间相对完整未校准版本改善至少 3%；
- x86-64 结果不能出现超过 1% 的显著回归。

### RQ4：三个模块是否存在互补性？

H4：完整系统在“语义正确、意图落地、真实性能提升”三者同时满足的成功率上优于任一单模块或双模块版本。

## 3. 自变量、因变量与控制变量

### 3.1 自变量

- 是否启用意图契约和逐层审计；
- 是否启用反事实归因；
- 是否启用硬件反例校准；
- 候选生成方法；
- 目标硬件；
- 真实测量预算。

### 3.2 主要因变量

- 运行时间 speedup：相对 `clang -O3`；
- 合格优化成功率：语义正确且性能提升；
- `valid_and_realized` 比例；
- 负优化率：运行时间显著劣于基线的候选比例；
- 达到目标性能所需的实机测量数。

### 3.3 次要因变量

- 编译通过率；
- 语义验证通过、失败和 inconclusive 比例；
- 后端擦除率；
- 归因稳定性；
- Pass 协同边复现率；
- 代码尺寸；
- 系统自身时间开销。

### 3.4 控制变量

- 编译器版本和 commit；
- target triple、CPU、feature flags；
- benchmark 输入；
- CPU 频率策略、温度区间和后台负载；
- 候选预算、序列长度、Pass 集；
- LLM 模型版本、prompt 和 decoding 参数；
- 每个候选的运行次数和异常值处理规则。

## 4. 实验平台

### 4.1 x86-64 主平台

用途：大规模候选生成、工具开发、初始搜索、主要消融和统计实验。

要求：

- 固定一台专用机器或固定 CPU 型号；
- 禁用或记录动态频率影响；
- 固定核心绑定和 NUMA 策略；
- 记录操作系统、内核、微码、LLVM 和链接器版本。

### 4.2 RISC-V 主验证平台

平台：进迭时空 K3 的 X100 通用核。

用途：跨 ISA 外部验证、收益翻转发现、硬件反例校准和最终性能结论。

不得把 K3 的 X100 通用核与 A100 AI 核结果混合。正式实验前必须通过实际系统命令冻结 CPU、RVV、编译器和 PMU 能力；当前文档不在未访问设备的情况下臆测软件版本。

### 4.3 可选外部平台

从实验室其他 RISC-V 板卡中选择一个与 K3 微架构差异明显的平台，只用于最终外部有效性实验。它不进入 6 个月最小投稿线。

### 4.4 QEMU 边界

QEMU 只用于：

- 功能正确性预筛选；
- ISA 和 target feature 配置覆盖；
- 批量编译运行；
- 静态指令类别和代码尺寸检查。

QEMU 不参与真实性能 speedup、代价校准或硬件间优劣结论。

## 5. Benchmark 与数据划分

### 5.1 首期 benchmark 池

选择 LLVM 工具链可稳定构建、可在 x86 与 RISC-V 运行的 C/C++ 程序：

- LLVM test-suite 中可独立运行的程序；
- PolyBench/C 的循环内核；
- cBench 中能稳定交叉编译的程序；
- TSVC 仅作为向量化意图补充，不承担全部结论。

首期目标规模：

- 30–50 个完整程序；
- 100–200 个热点函数；
- 每个程序至少一个固定输入和一个外部验证输入。

### 5.2 数据划分

- 训练/证据积累集：50%；
- 开发集：20%；
- 最终测试集：30%。

必须按程序划分，不能把同一程序的函数分到训练和测试两侧。若没有训练模型，“训练集”仍用于建立归因和反例记忆；最终测试集全程封存到主方法冻结后。

### 5.3 四类首期意图

只覆盖能由工具检测的意图：

1. 减少内存访问；
2. 消除冗余计算或死代码；
3. 简化分支和控制流；
4. 促进循环向量化。

循环展开、内联、代码尺寸等可作为 Pass 动作或副作用，但首期不单独定义更多意图类别。

## 6. 候选空间与生成方法

### 6.1 Pass 集

从 LLVM 新 Pass Manager 中选择 12–20 个行为清晰、可稳定组合的中端 Pass。序列长度先限制在 8–16，允许重复但设置单 Pass 最大重复次数。

### 6.2 候选生成器

至少包含：

- Random：统一随机合法序列；
- Search：一种经典进化或强化学习搜索基线；
- LLM-Agent：生成 Pass 序列和同步意图契约；
- FACT：在 LLM-Agent 或 Search 上增加审计、归因与校准。

主创新不依赖某个专有 LLM。正式实验必须冻结模型版本，并保留统一 prompt、temperature、seed 和原始输出。

## 7. 基线

| 编号 | 基线 | 用途 |
|---|---|---|
| B0 | LLVM `-O3` | 标准性能基线 |
| B1 | Random Pass Search | 最低搜索基线 |
| B2 | 经典搜索器，仅终局奖励 | 检验搜索器本身 |
| B3 | LLM + compile/test feedback | 当前常见智能体反馈范式 |
| B4 | B3 + Intent Audit | 单独检验创新一 |
| B5 | B3 + Counterfactual Attribution | 单独检验创新二 |
| B6 | B3 + Audit + Attribution | 检验前两项协同 |
| B7 | 完整系统，无硬件反例校准 | 检验创新三 |
| B8 | 完整 FACT | 主方法 |

若开发周期不足，B4 与 B5 必须保留；可以减少不同候选生成器数量，但不能删除关键消融。

## 8. 实验矩阵

### E0：环境与基线复现

- 在 x86 和 K3 上复现 `-O0/-O2/-O3`；
- 验证 benchmark 正确性、测量稳定性和交叉编译；
- 建立环境冻结文件和运行脚本接口。

通过标准：同一二进制重复运行的性能变异系数在主要 benchmark 上可接受；异常程序必须从正式集合中剔除并记录原因。

### E1：意图审计准确性

- 人工标注一批候选的意图是否在 IR 和机器码落地；
- 比较自动审计结果；
- 报告每类意图的 precision、recall、F1 和错误类型。

额外对比：只读 optimization remarks、只做 IR diff、完整 IR+MIR/asm 审计。

### E2：意图审计对 Agent 的帮助

- 比较 B3 与 B4；
- 指标：合格候选率、重试次数、虚假成功率、最终 speedup；
- 分析 `valid_but_erased` 和 `valid_but_counterproductive` 案例。

### E3：反事实归因忠实度

- 对高贡献 Pass 做删除验证；
- 对低贡献 Pass 做删除验证；
- 计算贡献排名与真实性能破坏之间的相关性；
- 在不同重复测量和不同输入下检查稳定性。

### E4：归因引导搜索效率

- 比较 B3、B5、B6；
- 横轴为真实测量次数，纵轴为当前最佳 speedup；
- 报告达到固定性能阈值所需的测量预算。

### E5：跨硬件收益翻转分析

- 将 x86 上的 top-k 候选部署到 K3；
- 统计正迁移、无显著差异和负迁移；
- 利用 IR/MIR/asm 和可用 PMU 信息分析原因；
- 形成硬件反例库。

### E6：硬件反例校准

- 比较 B7 与 B8；
- 主指标：K3 负优化率、top-k regret、几何平均 speedup；
- 次指标：对 x86 的回归、额外测量数和拒绝/守卫比例。

### E7：端到端主实验

- 所有正式测试程序；
- 固定总候选预算和实机测量预算；
- 比较 B0–B3、B6–B8；
- 报告正确性、意图落地、搜索效率、x86 性能和 K3 性能。

## 9. 统计与测量协议

### 9.1 性能测量

- 每次正式比较先热身；
- A/B 版本随机交错运行；
- 绑定 CPU 核心；
- 记录温度、频率和后台负载；
- 使用中位数作为单程序中心估计；
- 报告 bootstrap 95% 置信区间；
- 无法与噪声区分的差异标记为 `no_significant_change`，不强行判为提升。

### 9.2 汇总统计

- speedup 使用几何平均；
- 成对比较优先使用 Wilcoxon signed-rank test；
- 同时报告 Cliff's delta 或其他非参数效应量；
- 多基线、多指标比较采用 Holm 校正；
- 除 p 值外必须报告效应量和置信区间。

### 9.3 随机性

- 搜索和 LLM 采样至少使用 5 个随机种子；
- 每个种子使用相同候选预算；
- 报告均值/中位数、离散度和最坏种子结果；
- 模型 API 不能保证完全确定时，记录请求时间、模型版本和原始响应。

## 10. 正确性协议

候选必须依次通过：

1. 编译检查；
2. benchmark 自带测试；
3. sanitizer 可用时的运行检查；
4. 额外随机/边界输入差分测试；
5. Alive2 支持范围内的 IR 等价验证。

Alive2 的 `inconclusive` 单独统计，不得记为验证成功，也不得直接记为语义错误。

## 11. 失败处理

| 失败 | 处理 |
|---|---|
| 编译失败 | 记录编译器诊断，不进入性能测量 |
| 语义失败 | 标记 invalid，保存最小复现 |
| Alive2 inconclusive | 转入差分测试，仍保留不确定标签 |
| 测量噪声过大 | 增加重复数；仍不稳定则从主性能集合排除 |
| K3 工具链缺特性 | 降低 Pass 集到两端共同支持范围，并记录 |
| PMU 不可用 | 使用时间和静态机器码证据，不虚构微架构原因 |
| LLM API 漂移 | 冻结模型快照或改用可复现开源模型完成正式实验 |

## 12. 输出文件规划

研究设计批准并进入实现后，建议统一输出：

| 输出 | 格式 | 内容 |
|---|---|---|
| environment lock | YAML/JSON | 两个平台的完整环境 |
| candidate manifest | JSONL | 候选、意图、Pass 序列和 seed |
| audit evidence | JSONL | IR/MIR/asm 审计结果 |
| counterfactual manifest | JSONL | 删除、替换、交换关系 |
| raw measurements | CSV/Parquet | 每次原始运行，不只保存中位数 |
| summary metrics | CSV | 每个 RQ 的汇总指标 |
| figures | PDF/SVG | 预算曲线、消融、跨硬件翻转图 |
| failure cases | Markdown/IR | 最小反例与解释 |

## 13. 最小投稿线与增强线

### 13.1 6 个月最小投稿线

- x86 + K3 两个平台；
- 30 个程序、100 个热点函数以上；
- 四类意图；
- B0、B1、B3、B4、B5、B6、B7、B8；
- 完成 E0–E7；
- H1、H2、H3 分别达到其对应的至少一个备选成功阈值；
- 开源或可复现的审计标签与测量协议。

### 13.2 8 个月增强线

- 增加第二款 RISC-V 板卡；
- 增加输入迁移和跨版本 LLVM 实验；
- 加入一个经典 RL/进化搜索强基线；
- 将典型硬件反例转成 LLVM TTI/调度参数的人工验证补丁；
- 补充真实开源项目案例。

## 14. 证伪条件

出现以下任一情况，应收缩或改题：

- 意图审计 F1 低且无法通过确定性分析提高；
- 反事实归因在重复测量间不稳定；
- 归因引导不节省测量，也不提高最终性能；
- x86 与 K3 几乎没有收益翻转，硬件校准无数据支撑；
- 校准后 K3 改善但 x86 大幅回归；
- 完整系统的额外成本远高于减少的候选测量成本。

## 15. 当前验证状态

这是实验设计，不是实验结果。所有阈值是立项与停止标准，尚未被实测支持；不得写成已经取得的性能提升。
