# 从零设计硬件感知 LLM 编译优化研究框架计划书

## 1. 这份计划书解决什么问题

如果直接从“LLM Agent + 编译器 + 硬件反馈”开始写代码，容易出现三个问题：

1. 研究问题不清楚，只是在不断增加模块；
2. 创新点和实现手段混在一起；
3. 实验只报告加速案例，不能证明新机制有效。

本计划把研究拆成可检查的阶段：

~~~text
研究问题
  ↓
创新边界
  ↓
最小系统
  ↓
预实验 Demo
  ↓
小规模试验
  ↓
完整实验
  ↓
论文证据
~~~

## 2. 当前主线定义

### 2.1 研究主问题

**硬件效应反馈是否能让 LLM 编译优化智能体在相同预算下减少错误候选和负迁移？**

这里的硬件效应反馈不是硬件型号名称，而是硬件对向量、缓存、stride、分支和访存模式的实际响应摘要。

### 2.2 推荐主线名称

**硬件效应反馈驱动的可验证 LLM 编译优化智能体**

### 2.3 不作为核心创新的内容

以下内容只能是工具或实验条件：

- 使用 LLM；
- 使用 Agent；
- 使用 RAG、LoRA 或强化学习；
- 使用 RISC-V/RVV；
- 读取硬件型号；
- 在真实硬件上运行；
- 增加一个数据库；
- 更换一个大模型。

只有当这些手段改变了输入、约束、反馈或决策，并通过消融实验显示作用时，才可能成为支撑机制。

## 3. 核心创新点

### 创新点一：硬件条件化证据契约

Agent 不只输出“请尝试 tile=32”，而是输出：

- 程序前提；
- 硬件前提；
- 编译动作；
- 预期 IR 证据；
- 预期汇编或后端证据；
- 性能假设；
- 否定条件。

创新的可检验部分是：硬件前提和预期后端证据会改变候选是否被接受，而不是只作为自然语言说明。

### 创新点二：迁移、补测、拒绝三态路由

当历史优化经验来自平台 A、当前目标是平台 B 时，Agent 不强制复用：

- 证据和硬件响应相似：迁移；
- 有潜在收益但不确定：补测；
- 硬件效应不相似或出现反例：拒绝。

创新的可检验部分是：三态路由能否在相同目标测量预算下降低负迁移。

### 创新点三：反证式记忆门控

候选只有在正确性、预期后端证据和稳定性能同时成立时才进入已验证记忆。

“性能变好但解释错误”的候选保留为失败样本，不得作为成功经验迁移。

创新的可检验部分是：记忆门控能否降低后续搜索中的错误复用和解释不一致。

## 4. 系统框架

### 4.1 输入

- 程序或 LLVM/MLIR IR；
- 可选的静态程序特征；
- 硬件响应摘要；
- 历史候选和失败记忆；
- 本轮编译与运行预算。

### 4.2 处理

1. Agent 读取程序和硬件摘要；
2. Agent 生成受限动作；
3. Agent 输出硬件条件化证据契约；
4. 编译器工具执行候选；
5. 正确性、IR、汇编和性能工具收集证据；
6. 路由器选择接受、修订、迁移、补测或拒绝；
7. 记忆门控决定是否保存。

### 4.3 输出

每轮输出一条可重放记录：

~~~json
{
  "candidate": "tile_and_unroll",
  "hardware_profile": "target_A",
  "contract": {},
  "compiler_evidence": {},
  "correctness": {},
  "performance": {},
  "decision": "transfer_or_measure_or_reject",
  "memory_write": false,
  "failure_reason": ""
}
~~~

## 5. 实验框架

### 5.1 自变量

| 自变量 | 取值 |
|---|---|
| Agent 条件 | Direct-LLM、Contract-LLM、Hardware-aware Contract-LLM |
| 硬件输入 | 无硬件信息、硬件 ID、实测响应摘要 |
| 路由策略 | 强制迁移、只补测、迁移/补测/拒绝 |
| 记忆策略 | 无记忆、无门控记忆、三层门控记忆 |
| LLM | 至少一个强模型；条件允许时加入第二个模型 |
| 测量预算 | 20、50、100、250 次候选编译/运行 |

### 5.2 因变量

- 编译成功率；
- 正确性通过率；
- 证据一致性；
- 负迁移率；
- 迁移/补测/拒绝路由准确率；
- 达到目标性能所需的候选数量；
- 达到目标性能所需的目标测量次数；
- 几何平均 speedup；
- 相对高预算搜索的 regret；
- 记忆污染率。

### 5.3 控制变量

- 固定编译器和版本；
- 固定模型、prompt 和 temperature；
- 固定输入数据和容差；
- 固定超时和异常值规则；
- 固定 Agent 调用预算；
- 固定性能重复次数；
- 固定系统负载和频率策略。

## 6. 从零开始的最小预实验

### 阶段 A：不接入 LLM

目标：先证明后端证据和门控可以工作。

- 程序：SAXPY 一个 kernel；
- 工具：GCC；
- Agent：Stub Agent；
- 候选：restrict + unroll；
- 检查：编译、checksum、向量化报告、运行中位数；
- 输出：accept、reject 或 request_measurement。

必须先制造一个故意错误候选，确认正确性门能拒绝它。

### 阶段 B：接入 LLM

目标：验证 LLM 能否遵循证据契约。

比较：

- Direct-LLM；
- Contract-LLM；
- Hardware-aware Contract-LLM。

每种条件至少运行 10 次，不能只保留成功案例。

### 阶段 C：加入硬件条件

第一版可使用同一台机器上的两个编译目标配置作为弱代理：

- generic target；
- native target。

这只能验证“硬件条件输入改变路由”的流程，不能作为真实跨硬件结论。

### 阶段 D：加入真实第二平台

优先选择可以复现实验协议的平台：

- ARM Linux；
- RISC-V/RVV Linux；
- GPU Linux；
- 另一台 x86 机器。

平台不是主线限定；只要同一契约、同一路由和同一指标能够复现即可。

## 7. 完整实验矩阵

### 7.1 程序任务

至少三类：

1. SAXPY、向量加法等逐元素 kernel；
2. dot product、reduction 等归约 kernel；
3. stride、tile、缓存敏感的内存 kernel。

完整阶段目标为 20—30 个 kernel，训练、验证和未见测试分离。

### 7.2 基线

1. GCC/LLVM 默认优化；
2. 无 Agent 的随机或贝叶斯调优；
3. Direct-LLM；
4. Contract-LLM；
5. Hardware-aware Contract-LLM；
6. 强制跨平台迁移；
7. target-only 高预算搜索；
8. 最近邻编译器反馈式 Agent。

### 7.3 必做消融

| 消融 | 需要回答的问题 |
|---|---|
| 去掉硬件响应摘要 | 硬件反馈是否真的有作用 |
| 用硬件 ID替换实测响应 | 实测效应是否优于标签 |
| 去掉硬件前提字段 | 条件化契约是否必要 |
| 去掉拒绝动作 | 强制迁移是否增加负迁移 |
| 去掉补测动作 | 主动测量是否节省预算 |
| 去掉反证字段 | 失败诊断是否改变后续行为 |
| 去掉记忆门控 | 偶然成功是否污染后续搜索 |
| 增加调用预算但去掉机制 | 收益是否只是来自更多搜索 |

## 8. 统计与可复现要求

每个配置：

1. 预热；
2. 至少重复 10 次；
3. 丢弃第一次；
4. 报告中位数和离散程度；
5. 使用 bootstrap 置信区间；
6. 同时报告成功、失败、拒绝和不确定样本；
7. 对主要比较使用配对统计；
8. 固定随机种子、模型版本、编译器版本和输入。

不能只报告“最佳加速比”，必须报告所有任务的中位结果和失败比例。

## 9. 阶段门槛

### Gate 0：问题成立

继续条件：

- 能明确写出 Agent 的输入、动作和输出；
- 能明确写出硬件反馈如何改变决策；
- 能区分创新机制与实现工具。

不满足时，重新收窄问题，不开始大规模实验。

### Gate 1：工具闭环成立

继续条件：

- 基线和候选都能编译运行；
- 正确性门能抓住故意错误；
- 后端证据可以被记录；
- 性能测量可重复。

### Gate 2：契约机制成立

继续条件：

- Contract-LLM 比 Direct-LLM 有更高证据一致性或更低错误率；
- 不是因为 Contract-LLM 获得了更多调用次数；
- 失败原因能够改变下一轮候选。

### Gate 3：硬件反馈成立

继续条件：

- 硬件响应摘要确实改变迁移、补测或拒绝路由；
- 完整方法的负迁移率低于强制迁移；
- 补测成本没有抵消收益。

### Gate 4：论文级证据成立

继续条件：

- 至少两个平台；
- 至少三类 kernel；
- 至少一个强 Agent 基线；
- 所有关键模块有消融；
- 结果在未见 kernel 或未见平台上仍有解释边界。

## 10. 失败时如何降级

| 失败现象 | 降级方向 |
|---|---|
| 硬件反馈没有收益 | 保留为证据契约 Agent，删除跨平台主张 |
| Agent 与无契约版本无差异 | 收窄到反证诊断或记忆门控 |
| 只有一个平台可运行 | 做单平台硬件条件 Agent，不声称跨硬件泛化 |
| 拒绝率接近 100% | 只迁移高置信度动作，报告 coverage-risk |
| 结果只在一个 kernel 上 | 收缩为 kernel 家族实验，不扩展主张 |
| 性能提升但证据不成立 | 记为偶然成功，不写入已验证记忆 |
| 复杂模型没有超过简单模型 | 使用简单模型作为主方法，避免无必要复杂化 |

1. 主线研究框架；
2. 证据契约 schema；
3. Agent 候选生成器；
4. 编译/正确性/性能验证器；
5. 迁移/补测/拒绝路由器；
6. 记忆门控记录；
7. 可重放实验脚本；
8. 结果表和失败案例；
9. 论文方法、实验和局限章节。

## 13. 最终判断标准

这项研究只有在下面的因果链被实验支持时才值得继续：

~~~text
硬件效应反馈
  ↓
改变 Agent 的候选或路由
  ↓
减少错误/负迁移或测量成本
  ↓
证据契约和记忆门控能解释为什么
~~~

如果实验只能证明“LLM 生成了一段能运行的代码”，说明还没有形成完整创新，应停留在预实验阶段。
