# 类别三：形式验证、超级优化与规则生成——反例细化的规则效益适用域

> 审阅结论：不能再把“形式证明 + 收益检查”本身写成创新；Alive/Souper/Minotaur/LPG 已覆盖其中大部分。
> 文献范围：本类 20 篇逐篇阅读笔记；重点参考 Alive、Alive2、Souper、STOKE、Minotaur、LLM-VeriOpt、LPG。
> 证据强度：高；两篇源材料受限工作不承担关键结论。
> 日期：2026-07-15

## 1. 先说结论

优化规则有两个完全不同的问题：

1. **语义上能不能做**：规则是否保持程序行为；
2. **目标上值不值得做**：在什么程序上下文、什么目标机器上会带来收益。

Alive/Alive2 已擅长第一个问题，Minotaur 和 2026 年的 LPG 已经把成本或 profitability 检查接入规则生成流程。因此，新方向不能只叫“证明—收益双证据”。

推荐创新点名称：**硬件性能反例驱动的优化规则适用域自动细化**。

## 2. 已有工作与边界

| 工作 | 已经解决 | 仍然留下的问题 |
|---|---|---|
| Alive / Alive2 | LLVM 局部变换的形式化语义验证 | 不判断目标机器收益；验证覆盖有边界 |
| Souper | 合成并验证局部等价重写 | 成本多为静态代理，规则粒度局部 |
| STOKE | 用搜索发现更快机器码 | 测试验证不完备，且 ISA 特定 |
| Minotaur | SIMD 候选合成、Alive2 验证和成本检查 | 主要面向局部、x86 SIMD、固定上下文 |
| LLM-VeriOpt | 把验证反馈纳入 LLM 强化学习 | 主要解决正确性，性能信号仍可能是代理 |
| LPG | LLM 泛化 peephole 规则并做语法、语义、收益检查 | 规则“在哪些目标和上下文有利”的边界仍需更细建模 |

[LPG 预印本](https://arxiv.org/abs/2603.18477)已经明确把 syntactic validation、semantic verification 和 profitability checking 放在同一条流水线上。故“首次结合证明和收益”是不成立的。

## 3. 真正的空白：规则缺少可更新的效益适用域

传统规则常写成：

`precondition(x) => replace A with B`

其中 precondition 主要保证语义合法，却很少显式表达：

- 对哪类微架构有利；
- 在什么寄存器压力、数据布局、向量长度下有利；
- 何时只减少 IR 指令却增加机器指令；
- 已经出现过哪些真实性能反例；
- 对未见上下文是否应该拒绝应用。

本方向要把每条规则从“永远值得应用”改成“在一个可学习、可证伪、可更新的效益适用域内应用”。

## 4. 推荐创新点

### 4.1 一句话解释

规则每遇到一个“语义正确但性能变差”的真实案例，就不简单删除规则，而是分析这个反例与成功案例的差别，自动收紧规则的适用条件。

### 4.2 规则护照

每条规则保存四组信息：

```text
Semantic contract : 等价关系、前置条件、验证器版本与覆盖范围
Structural context: 操作类型、位宽、循环/基本块位置、数据流特征
Target context    : ISA、CPU、VLEN、寄存器/缓存/调度相关特征
Profit evidence   : 正负样本、效应值、置信区间、反例与时间戳
```

注意：语义证明可以较稳定地复用；性能证据只能在记录的条件下成立，不能被写成数学证明。

### 4.3 反例细化闭环

1. LLM、枚举器或现有规则库提出候选规则；
2. Alive2 等工具验证语义，无法覆盖的候选单独标记；
3. 在不同程序上下文中实例化规则；
4. 真实编译、成对测量并获得正效应或负效应；
5. 对性能反例做最小化，寻找导致收益翻转的最少上下文特征；
6. 学习守卫条件 `profit_guard(context,target)`；
7. 对守卫边界附近的样本主动测量，而不是平均撒预算；
8. 新反例到来后更新守卫和置信度。

示例：

```text
规则：把两个窄向量操作合并为一个宽向量操作
语义：Alive2 验证通过
成功条件：寄存器压力低、目标支持低成本宽指令
性能反例：寄存器压力高时发生 spill，运行时间变慢
细化后守卫：estimated_spill_risk < threshold
```

### 4.4 与“知识库”的关系

知识库只是存储形式，不是论文创新本身。论文贡献应落在：

- 性能反例最小化方法；
- 效益守卫的自动学习与校准；
- 边界样本主动选择；
- 规则在未见上下文上的拒绝机制。

## 5. 最小可行实验

### 5.1 范围控制

- 先做 30–100 条 LLVM peephole/SIMD 规则；
- 选 2 类上下文：寄存器压力、向量/标量 lowering；
- 至少 2 个差异明确的真实 CPU；
- 语义验证与真实性能测量分开报告。

### 5.2 基线

1. 无条件应用规则；
2. LLVM 默认 TTI/cost model；
3. 单一目标上训练的 profitability classifier；
4. LPG/Minotaur 风格“候选通过一次成本检查即接受”；
5. 本文的反例细化守卫。

### 5.3 指标

- 语义验证通过率与 inconclusive 比例；
- 负优化率；
- 保留下来的正优化机会比例；
- 守卫精确率、召回率和校准误差；
- 每减少一次负优化所需的真实测量数；
- 新硬件/新程序上的拒绝率与误放行率。

## 6. 可证伪假设

主假设：性能反例驱动的守卫细化能在不过度牺牲正优化召回率的前提下，显著降低规则负优化率。

应判定失败的情况：

- 收益翻转无法由可获得的上下文特征解释；
- 守卫只记住 benchmark，换程序即失效；
- 为降低少量负优化而拒绝了大部分有益规则；
- 实测开销远大于避免负优化的价值。

## 7. 不同规则层级必须分开

本方向首先只适用于局部 rewrite。不要把以下对象混成一个库：

- peephole 等价重写；
- 循环变换；
- Pass 序列策略；
- 源码级算法替换。

它们的语义验证器、上下文特征、收益评估成本完全不同。后续扩展时应分别建模。

## 8. 论文边界

可主张：面向性能反例的规则守卫自动细化、效益适用域和拒绝机制。

不可主张：首次自动生成规则、首次用 Alive2 验证、首次把正确性和 profitability 联合检查、首次建立规则数据库。

## 9. 综合判断

| 维度 | 评分（5 分） | 说明 |
|---|---:|---|
| 新颖性 | 4.1 | 重点是“反例如何改变适用条件” |
| 可实现性 | 3.7 | 需要规则实例化和可靠测量 |
| 实验清晰度 | 4.4 | 负优化率和拒绝质量可直接测量 |
| RISC-V 相关性 | 4.2 | 新后端更容易暴露成本模型与规则适用性差异 |
| 风险 | 中高 | 可能受到上下文特征不足和测量成本限制 |

最终建议：作为类别三主创新，但必须把“语义证明”和“经验收益”用不同术语、不同证据等级呈现。
