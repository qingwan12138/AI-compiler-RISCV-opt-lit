> 文献数量：2024–2026 年独立条目 55；旧文献边界条目 10

> 证据充分程度：高（近邻工作密集，适合做严格碰撞分析；具体新颖性仍需补在线检索）

## 1. 这一类在研究什么

结论：这类研究把大语言模型从“一次性写代码的生成器”变成能调用编译器、测试器、性能分析器和真实硬件的优化智能体。典型循环是“提出变换—编译—测试—测量—读取反馈—继续修改”。2024–2026 年的文献已经覆盖多轮反馈、强化学习、多智能体、多抽象层协作、优化意图、结构化知识库、真实硬件奖励和安全动作空间，因此宽泛地提出“LLM + 编译器反馈”或“多 Agent 优化框架”已经不够新。

真正仍薄弱的环节是：智能体经常给出听起来合理的优化解释，但现有系统主要检查“能否编译、测试是否通过、是否变快”，很少验证它声称的机制是否真的发生。例如，智能体说“向量化减少了标量指令”，程序虽然变快，却可能实际来自内联、常量折叠或输入过拟合。若把这种偶然收益写进长期记忆，后续迁移就会传播错误知识。

## 3. 已有工作已经解决了什么

结论：2024–2026 年已经把“模型、工具、搜索、反馈、验证和多 Agent”几乎所有常规模块组合过一遍。新研究必须改变智能体如何形成和检验知识，而不是继续堆模块。

1. 【论文事实】Compiler-generated Feedback、COCOGEN、CompilerGPT、GraphGlue 和 Compiler Agent Impact 已证明编译诊断既能作为错误反馈，也能用于定位上下文和根因。
2. 【论文事实】Compiler-R1、Kevin、CUDA-L1、Code-Optimise 和 PerfCoder 已分别使用 PPO/GRPO、跨轮归因、对比 RL、DPO 和规划器 RL；更换一种训练算法不足以构成编译创新。
3. 【论文事实】SBLLM、ReasoningCompiler、MCTS RTL、STARK 和 ACCLAIM 已覆盖演化搜索、MCTS、多 Agent 和多抽象层协调。
4. 【论文事实】IntOpt、AutoComp、HintPilot、Code the Transforms 和 PyCraft 已覆盖优化意图、结构知识、受限动作、可执行规则与验证后规则化。
5. 【论文事实】CUDA-L1、AutoComp、NPUEval、MEP 和 PerfCoder 已把真实性能或确定性模拟器反馈纳入循环；“加入运行时间奖励”本身不再新。
6. 【论文事实】IntOpt、Verilocc、QiMeng-xpiler、SymRTLo 和 VecTrans 已使用形式/符号/编译/测试验证约束生成，但验证重点主要是合法性或等价性，而不是优化解释是否忠实。

## 4. 仍未解决的研究空白

结论：最值得做的空白是把自然语言优化策略变成可执行、可反证的证据契约，并阻止“偶然变快但解释错误”的样本进入长期记忆。

### 空白 A：优化解释与真实编译/硬件效应缺少一致性验收

- 【论文事实】PerfCoder 训练显式自然语言策略，但总结明确指出策略可能是伪解释；CompilerGPT 使用优化报告指导改写，却没有验证改写后的收益是否由报告所述机制产生。
- 【论文事实】IntOpt 验证 IR 变换语义，NPUEval 检查硬件利用率，VecTrans 检查向量化结果；这些工作分别验证正确性或单一结果，没有形成“先声明预期机制—再执行反事实检查—最后决定是否学习”的通用协议。
- 【合理推导】若系统只以测试通过和最终加速作为成功标签，输入特化、其他 Pass 联动、测量噪声或意外代码形态都可能被错误归因给智能体的解释。
- 证据充分度：高。

### 空白 B：反馈预算缺少按信息价值动态停止

- 【论文事实】Compiler-generated Feedback 发现多反馈边际收益递减；AutoChip 的旧边界总结发现最近一轮精确反馈可能优于累积历史；STARK 暴露多 Agent 在同预算比较下的公平性问题。
- 【合理推导】智能体需要判断下一次反馈是否会改变决策，而不只是设置固定轮数。
- 证据充分度：中。与主动学习、上下文压缩相邻，需要补检索后才能主张新颖。

### 空白 C：失败证据没有成为可迁移的“禁止条件”

- 【论文事实】GraphGlue 会拒绝错误策略，ECO 会做多级门控，CUDA-L1 暴露跨 GPU 负迁移，FSCM 暴露表面模式陷阱。
- 【合理推导】现有系统多在当前任务内丢弃失败，没有把失败整理为带前提、反例和硬件范围的可查询知识对象。
- 证据充分度：中高，但与类别一的跨硬件信用、类别六的知识迁移存在重叠。

## 6. 最推荐的创新点

### 6.1 创新点名称

【候选创新】**可执行证据契约驱动的反证式编译优化智能体**。

### 6.2 一句话解释

智能体在改代码前必须写下“为什么会变快、编译器和硬件上应该出现什么证据、什么现象会否定我”；系统再用 IR、汇编、编译报告、硬件事件和对照实验逐条验收，只把机制与结果同时成立的优化写入长期记忆。

### 6.3 创新点命名拆解

- **可执行证据契约**：不是自由文本解释，而是机器可解析的前提、动作、预期证据、正确性条件和否定条件。
- **反证式**：系统主动寻找能推翻解释的对照，而不是只收集支持证据。
- **编译优化智能体**：模型负责提出假设和候选，确定性工具负责执行、测量与裁决。
- **长期记忆门控**：性能提升但机制不匹配的“偶然成功”可以暂存为候选，却不能被当作可迁移知识。

### 6.4 文献依据

- 正面依据：PerfCoder 证明显式优化策略可以提升生成；CompilerGPT 证明编译报告能指导改写；IntOpt 证明意图可以结构化并由 Alive2 验证；NPUEval 证明“正确但未使用硬件”必须单独识别。
- 风险依据：Compiler-generated Feedback 显示更多反馈不一定更好；CUDA-L1 显示均值会掩盖负迁移；HPCTransCompile 和 Verilog RL 表明工具或测试的偏差可能被训练过程固化。
- 已覆盖近邻：优化意图、多层 Agent、工具调用、真实硬件奖励、规则合成、验证器重采样均已有代表工作。
- 不能再声称的内容：不能声称“提出编译器反馈 Agent”“首次让 LLM 解释性能”“首次用 Alive2/硬件计数器/反例”“首次多层协作”。
- 当前真正的候选边界：**把事前优化主张编译成可执行证据契约，并以反事实不一致阻止错误机制进入记忆**。

### 6.5 已有工作与研究空白

现有系统通常接受以下成功定义：

```text
测试通过 AND 性能提高
```

该定义能拒绝错误代码，却不能区分：

1. 解释正确，预期变换和硬件效应确实发生；
2. 程序偶然变快，但智能体的解释错误；
3. 只对当前输入或当前编译器版本变快；
4. 测量噪声造成的假阳性。

因此研究空白可写为：

> 【合理推导】如何把 LLM 的优化意图转成可执行、可反证的跨层证据契约，并在功能正确与性能提升之外，校准其机制解释的可信度和可复用范围。

### 6.6 核心机制

每个优化候选先输出契约：

```text
C = <P, A, E, S, F>
```

- `P`（Preconditions）：适用前提，例如循环无跨迭代依赖、数组对齐、trip count 足够大；
- `A`（Action）：允许的变换，例如加 Hint、循环重构、IR rewrite；
- `E`（Expected evidence）：预期证据签名，例如出现 vectorization remark、IR 中标量操作变为向量操作、RVV 汇编出现 `vsetvli/vle/vse`、retired instructions 下降；
- `S`（Semantic oracle）：编译、测试、sanitizer、差分执行或 Alive2 条件；
- `F`（Falsifiers）：否定条件，例如没有目标向量指令、spill 激增、换输入后收益消失、禁用该动作仍得到相同收益。

对观察证据 `O`，计算契约一致性：

```text
Agreement(C,O) = Σ_k w_k · match(E_k, O_k) - Σ_m v_m · hit(F_m, O_m)
```

若进行轻量训练，可使用：

```text
R = I_semantic · [log(T_base / T_new) - λ1·L_evidence - λ2·L_uncertainty] - P_fail
```

- `I_semantic`：语义门控，通过为 1，否则为 0；
- `L_evidence`：事前预期与实测证据不一致损失；
- `L_uncertainty`：证据不稳定或跨重复测量不一致的惩罚；
- `P_fail`：编译、测试、验证或资源约束失败惩罚。

关键新增动作是**反事实探针**：对已接受候选构造一个最小对照，例如移除 Hint、回滚单个变换、关闭特定 Pass、改变输入规模或换一个后端。若性能改善仍存在但预期证据消失，则将其标记为“机制未确认”；若预期证据存在但性能不稳定，则标记为“机制发生但收益无保证”。

最终得到四态结果：

1. **确认成功**：语义、性能和机制证据同时通过，可进入可迁移记忆；
2. **偶然成功**：语义和性能通过，但机制证据失败，只保留结果，不传播解释；
3. **机制无收益**：预期变换发生但没有稳定加速，进入负证据库；
4. **失败**：语义或构建失败，拒绝候选。

### 6.7 系统组成与数据流

```text
源码/IR + 基线 profile + 编译器 remark
                  ↓
LLM 生成结构化证据契约 <P,A,E,S,F>
                  ↓
受限动作执行器实施变换
                  ↓
编译、测试、Alive2/差分执行语义门控
                  ↓
IR diff、优化记录、汇编模式、PMU 与重复计时
                  ↓
反事实探针：回滚动作 / 关闭 Pass / 改输入 / 换后端
                  ↓
契约一致性与置信度校准
                  ↓
确认成功 / 偶然成功 / 机制无收益 / 失败
                  ↓
正证据卡片与负证据卡片分别入库
```

LLM 不裁决自己的解释。契约解析、证据提取、计时、正确性测试和状态分类均由确定性程序完成；模型只在契约缺字段或被反证后重新规划。

### 6.8 小白化例子

智能体说：“把这个循环改写后，LLVM 会向量化，所以程序会变快。”旧系统只要测试通过且快了 8% 就接受。新系统要求它提前声明：编译报告应出现向量化成功，IR 应出现 `<4 x float>`，RISC-V 汇编应出现 RVV 指令，标量 retired instructions 应下降。若程序确实快了 8%，但这些证据都没出现，而反汇编显示真正原因是常量折叠，新系统会保留这份快代码，却拒绝把“向量化有效”写入知识库。

### 6.9 可检验的研究问题

1. 证据契约能否识别“性能提高但解释错误”的偶然成功？
2. 加入反事实探针后，智能体长期记忆在新程序或新硬件上的负迁移率是否下降？
3. 结构化契约是否比自由文本解释具有更高的证据一致率和更好的置信度校准？
4. 在相同编译、运行和 LLM 调用预算下，严格记忆门控是否提高最终有效优化率？
5. 哪一层证据最有增量价值：compiler remark、IR diff、汇编模式还是 PMU？

### 6.10 可验证假设

- H1：相对“测试通过 + 加速”基线，完整方法能识别更多机制错误样本，并在人工/规则审计集上提高解释精确率。
- H2：相对事后让 LLM 自解释，事前契约 + 反事实探针具有更低的错误归因率。
- H3：只允许“确认成功”进入长期记忆，会降低新程序和 RISC-V 目标上的负迁移率，即使短期可用样本数减少。
- H4：移除反事实探针后，性能均值可能变化不大，但偶然成功进入记忆的比例显著上升。
- H5：只用自然语言策略而不检查跨层证据时，模型给出的高置信解释存在明显过度自信。

### 6.11 最小可行 Demo

- **目标**：证明系统能够自动区分“解释正确的加速”和“解释错误的偶然加速”。
- **数据**：从 TSVC、PolyBench 和 LLVM test-suite 选 30 个可稳定运行的循环/函数；划分 20 个开发样本和 10 个未见测试样本。
- **动作空间**：只开放三类可审计动作——编译器 Hint/pragma、向量化友好循环重构、局部 LLVM IR rewrite；避免第一版自由重写整个程序。
- **平台**：x86-64 主机为开发平台，RISC-V Linux 开发板为外部验证平台；具体板卡和 PMU 事件需人工确认。
- **工具**：Clang/LLVM 优化记录、IR diff、`llvm-objdump`、Alive2 可覆盖子集、测试和 sanitizer、Linux `perf`、重复计时。
- **标注集**：人工构造 20–30 个“错误解释但代码可运行”的挑战样本，例如宣称向量化却实际未生成向量指令、宣称减少访存却 cache miss 上升。
- **步骤**：采基线→生成契约和变换→语义门控→抽取证据→运行反事实探针→四态分类→只用确认成功卡片指导未见样本。
- **预计开发工作**：2 周完成契约 schema 与证据提取，1 周完成对照探针，1 周跑基线和审计；第一版无需微调模型。
- **成功标准**：在挑战集上显著优于自由文本自解释；记忆迁移时负迁移率下降，且总测量预算与基线相同。

### 6.12 实验设计

#### 实验平台

固定 LLVM 主版本、优化级别、链接参数、CPU governor、绑核、预热和输入。RISC-V 上不可用的 PMU 事件标记为缺失，不以 x86 事件名称强行映射。QEMU 只做可执行性预筛，不报告性能结论。

#### 数据集与挑战集

- 常规集：TSVC、PolyBench、LLVM test-suite 中具备稳定测试和计时的函数；
- 机制挑战集：通过控制 Pass、输入规模、Hint 和无关变换，制造“性能与解释脱钩”的样本；
- 外部分布集：不同 benchmark 家族或 RISC-V 目标，只在最终阶段评测；
- 所有数据按程序家族划分，防止近重复函数进入训练/测试两侧。

#### 对比基线

- 简单基线：普通 LLM 迭代优化，只以编译、测试和运行时间反馈接受候选；
- 解释基线：PerfCoder 式自由文本策略或事后解释，但不执行证据契约；
- 报告基线：CompilerGPT 式把优化报告反馈给 LLM，但不做事前预测和反事实验收；
- 强基线：结构化契约 + 证据检查，但无反事实探针和长期记忆门控；
- 完整方法：契约、跨层证据、反事实探针、四态分类和正负记忆。

#### 消融实验

分别删除事前契约、IR 证据、汇编证据、PMU 证据、反事实探针、偶然成功隔离和负证据记忆。所有变体使用相同 LLM、提示长度上限、编译次数和真机测量次数。

#### 评价指标

- Correctness rate：语义门控通过率；
- Effective optimization rate：正确且稳定加速的比例；
- Mechanism precision/recall：自动确认的机制与人工/规则审计的一致程度；
- Accidental-win detection AUROC/F1：识别“快但解释错”的能力；
- Evidence agreement：事前预期证据实际出现的比例；
- Calibration error/Brier score：解释置信度是否可信；
- Negative transfer rate：记忆应用到新程序/硬件后退化的比例；
- Speedup 分布、中位数和最坏 10%：防止少数极端值掩盖风险；
- 编译次数、运行次数、LLM token 和墙钟时间：衡量额外验收成本。

#### 统计要求

真实性能至少重复 15 次，报告中位数和 bootstrap 95% 置信区间。机制分类由两名审阅者独立标注一部分挑战集并报告一致性；自动规则阈值在开发集固定。对方法比较使用配对检验和效应量，并对多个 benchmark 的比较控制多重检验。

### 6.13 与已有工作的创新边界

- 与 PerfCoder 的区别：PerfCoder 学习可读策略并用速度训练规划器；本方法要求策略事前给出可执行证据和否定条件，并隔离机制不匹配的偶然收益。
- 与 CompilerGPT 的区别：CompilerGPT 读取已有优化报告后改写；本方法先预测报告/IR/汇编/硬件应出现的变化，再用反事实探针检验预测。
- 与 IntOpt 的区别：IntOpt 重点是把高层意图实现为经 Alive2 验证的 IR 变换；本方法关注语义正确之外，性能解释是否被跨层证据支持。
- 与 NPUEval/VecTrans 的区别：它们检查是否使用特定硬件能力或是否成功向量化；本方法把多种机制统一为契约，并定义偶然成功、机制无收益和负证据入库。
- 与 ACCLAIM/STARK 的区别：本方法不以 Agent 数量或角色分工为贡献；单 Agent 也可实现，核心是可反证知识形成协议。
- 直接复用的模块：LLM、LLVM 优化记录、Alive2、差分测试、反汇编、`perf`、结构化 JSON schema。
- 核心创新候选：**事前可执行证据契约 + 反事实机制验收 + 偶然收益隔离的记忆门控**。

### 6.14 风险与降级方案

| 风险 | 影响 | 降级方案 |
|---|---|---|
| 在线检索发现已有“explanation faithfulness contract”系统 | 新颖性下降 | 收窄到 LLVM/RVV 跨层证据、偶然收益隔离或失败知识入库；先补近邻检索 |
| 机制没有唯一可观测签名 | 误判解释 | 允许“一组兼容机制”而非单标签；输出未确认，不强行裁决 |
| PMU 跨 ISA 不可比 | 三方证据缺失 | 以 IR/汇编/计时为核心，PMU 只作可选证据；使用平台内方向而非事件名硬映射 |
| Alive2 覆盖有限 | 语义门控不完整 | Alive2 可验证子集 + sanitizer + 差分测试；无法充分验证的样本不进入强证据记忆 |
| 反事实探针成本高 | 测量预算上升 | 只对高价值或准备入库的候选探测；与同预算基线比较 |
| LLM 契约经常缺字段 | 可执行率低 | 使用 JSON schema、枚举动作和模板修复；失败计入指标，不人工补齐 |
| 证据规则过于手工 | 泛化差 | 第一版只选三类机制；后续学习 evidence extractor，但保留确定性原始记录 |
| 严格门控导致样本太少 | 优化覆盖下降 | 保留“偶然成功”代码供当前任务使用，只禁止其解释进入迁移记忆 |
| 没有观察到错误解释危害 | 主假设削弱 | 将工作降级为优化解释审计基准和负结果，或转向反馈预算主动停止 |

### 6.15 可证伪条件

以下结果会否定或显著削弱候选创新：

1. 事后自由文本解释与事前契约在机制准确率和校准上没有差异；
2. 反事实探针几乎从不改变机制判断，额外成本没有信息价值；
3. 偶然成功进入记忆不会增加新程序或新硬件的负迁移；
4. 自动证据签名与人工审计一致性低到无法可靠使用；
5. 所有收益来自更小的受限动作空间，而不是契约与反证机制；
6. 在更换 LLVM 版本或 benchmark 家族后，契约规则完全失效；
7. 完整方法的额外编译/测量成本超过其减少错误迁移带来的收益。

### 6.16 综合评分

| 维度 | 1—5分 | 评分理由 |
|---|---:|---|
| 新颖性 | 4 | 与策略解释、意图验证、报告反馈均有明确边界，但需补在线近邻检索 |
| 文献证据 | 5 | PerfCoder、CompilerGPT、IntOpt、NPUEval 等形成直接互补证据链 |
| 可实现性 | 4 | 首版无需训练大模型，主要工作是 schema、工具链和挑战集 |
| 实验可验证性 | 5 | 机制准确率、偶然成功检测、校准和负迁移都可量化 |
| 与 RISC-V 相关性 | 4 | RVV 汇编和跨 ISA 证据可形成强案例，但机制并不只服务 RISC-V |
| 与总体主线兼容性 | 5 | 可作为跨硬件知识库的可靠知识入口和审计层 |
| 研究风险 | 3 | 最大风险是机制多义性和相邻软件工程可解释性研究碰撞 |

结论：当前适合作为**主创新候选或总框架的可信知识形成模块**。它比“多 Agent + 反馈”更容易形成可证伪的学术主张，也能与类别一的跨硬件 Pass 信用分工：类别一回答“某个 Pass 在不同硬件上贡献多少”，本类别回答“智能体对这次优化的机制解释是否值得相信并写入记忆”。
