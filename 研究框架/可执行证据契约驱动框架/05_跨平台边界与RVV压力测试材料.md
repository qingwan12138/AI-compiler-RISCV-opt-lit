# 类别四：向量化与跨 ISA 代码迁移——候选创新点分析

> 文献数量：2024–2026 年独立条目 5；旧文献边界条目 1
> 完整阅读数量：5 份新文献总结；另读 neon2rvv 工程总结作为规则基线
> 交叉碰撞文献：FSCM、AutoVecCoder、VecTrans、CoV、Forklift 等在其他类别单独统计
> 证据范围：本地逐篇阅读总结；本轮没有重新核验 PDF
> 分析日期：2026-07-16
> 证据充分程度：中高（直接文献少，但 VLEN/VLA 边界在多篇直接与交叉文献中一致暴露）

## 1. 这一类在研究什么

结论：这类研究要把固定宽度 SIMD 或标量代码迁移成能利用目标向量指令的代码。x86 SSE/AVX、ARM NEON 通常假定固定向量宽度，而 RISC-V Vector Extension（RVV）采用可伸缩、向量长度无关（Vector-Length-Agnostic，VLA）的执行模型。迁移不能只把 intrinsic 名称一一替换，还要处理运行时 `vl`、尾部元素、掩码、SEW/LMUL、规约次序、内存布局和寄存器压力。

2025–2026 年已有工作已经覆盖：LLM 生成并验证 x86 向量代码、NEON/x86→RVV 的多 Agent 翻译、RVV intrinsic 基准、MLIR 自动向量化 Transformer，以及翻译后的效率压力测试。类别二中的 FSCM 还直接做了 NEON→RVV 高性能库迁移。因此最安全的创新不再是“用 LLM 把 NEON 翻成 RVV”，而是系统回答：翻译结果是否对不同 VLEN、`vl` 边界、尾/掩码策略和输入规模都正确，并在什么条件下出现性能悬崖。

## 3. 已有工作已经解决了什么

结论：已有方法已经能生成、编译、测试并优化 RVV 代码；真正欠缺的是把 VLA 语义作为系统化测试维度，而不是把某块板或某个默认 VLEN 上通过测试当作迁移完成。

1. 【论文事实】IntrinTrans 已把编译、测试、活跃性和寄存器反馈纳入 RVV intrinsic 翻译闭环，多 Agent/FSM 结构不能重复包装。
2. 【论文事实】VecIntrinBench 已定义编译通过、功能正确和相对手写 RVV 性能三维评测；新 benchmark 必须改变测试机制或覆盖维度。
3. 【论文事实】LLM-Vectorizer 和 CoV 已探索 checksum、Alive2、展开/case splitting 与运行时双版本验证；简单增加验证层级会撞题。
4. 【论文事实】FSCM 已说明直接 intrinsic 表面映射不可靠，并使用标量语义锚点；架构无关参考实现已是直接近邻。
5. 【论文事实】OML-vect 已证明单独增加归约识别仍不足，布局与向量化必须联合；但其实验绑定 512-bit RVV 配置。
6. 【论文事实】TRACE 已证明小输入会掩盖巨大效率退化，并提供反馈驱动压力输入合成方法。

## 4. 仍未解决的研究空白

结论：最清晰的空白是围绕 VLEN/`vl` 边界自动生成反例和压力输入，同时检查语义鲁棒性与性能鲁棒性。

### 空白 A：RVV 迁移缺少 VLEN 参数化的系统验收

- 【论文事实】IntrinTrans 和 VecIntrinBench 覆盖多个任务，但总结未给出跨 VLEN、SEW、LMUL、尾/掩码策略的系统矩阵；OML-vect 只验证固定 512-bit 核；neon2rvv 早期固定 VLEN=128。
- 【论文事实】AutoVecCoder 只实证 x86 SSE/AVX；FSCM 只覆盖两块目标设备且未系统评估跨 VLEN 鲁棒性。
- 【合理推导】在一个 VLEN 或少量普通输入上正确，不能证明 VLA 循环在 `n = k·VL±1`、短向量、尾部和掩码组合下正确。
- 证据充分度：高。

### 空白 B：迁移效率缺少针对 RVV 性能悬崖的主动压力输入

- 【论文事实】TRACE 证明压力输入能放大翻译效率缺陷；OML-vect 表明布局和向量化决策会被内存连续性与成本模型共同决定。
- 【合理推导】RVV 应生成能触发 `vsetvli` 频繁变化、尾部占比高、spill、非对齐访存、cache 边界和规约瓶颈的输入，而不是只放大算法规模。
- 证据充分度：中高。

### 空白 C：固定宽 SIMD 优化意图到 VLA 实现的失败原因缺少可复用 taxonomy

- 【论文事实】VecIntrinBench 给出类型、向量长度、语义不等价和编译器差异等失败类别；FSCM 提出表面模式陷阱；IntrinTrans 记录编译/测试失败。
- 【合理推导】可以进一步把失败绑定到最小 VLEN/输入反例和修复动作，形成可执行 taxonomy。
- 证据充分度：中。更适合作为第一候选的分析产物。

## 6. 最推荐的创新点

### 6.1 创新点名称

【候选创新】**VLEN 参数化反例驱动的 RVV 迁移验证与性能悬崖定位**。

### 6.2 一句话解释

不再只问“这段 NEON/RVV 翻译在当前板卡上能否通过测试”，而是自动改变 VLEN、有效 `vl`、输入长度、对齐、尾部和掩码，主动寻找最小错误案例和最差性能区间，再把反例反馈给翻译器修复。

### 6.3 创新点命名拆解

- **VLEN 参数化**：把硬件最大向量长度和运行时有效 `vl` 作为一等测试变量。
- **反例驱动**：发现失败后缩减到最小的 `VLEN/SEW/LMUL/n/alignment/mask` 组合，便于复现和修复。
- **迁移验证**：以标量或源架构参考实现为 oracle，检查不同配置下的输出关系。
- **性能悬崖定位**：寻找代码在某些边界突然变慢的条件，而不只报告平均加速。

### 6.4 文献依据

- 直接依据：IntrinTrans 已建立 RVV 翻译闭环，但测试覆盖有限；VecIntrinBench 已有正确性/性能基准，但任务和配置少；OML-vect 固定 512-bit；TRACE 证明主动压力输入能暴露效率缺陷。
- 验证依据：LLM-Vectorizer 表明向量代码形式验证覆盖不足，动态测试仍需要结构化增强；CoV 表明运行时验证可以接纳静态 unknown，但其重点不是跨 VLEN 反例。
- 碰撞边界：FSCM 已做 NEON→RVV 语义锚点迁移，所以本方法不把翻译 Agent 或标量锚点当创新。
- 不能再声称的内容：不能声称“LLM 自动迁移 RVV”“首次使用 compile/test feedback”“首次构建 RVV intrinsic benchmark”“首次检查迁移效率”。
- 核心候选边界：**把 VLA 配置空间与输入空间联合成可搜索的语义/性能反例空间，并输出可最小化、可复现的失败包络**。

### 6.5 已有工作与研究空白

普通评测近似为：

```text
一个工具链 + 一块机器 + 一组常规输入 → 通过/失败 + 平均时间
```

VLA 代码需要的验收更接近：

```text
(VLEN, SEW, LMUL, vl, tail, mask, alignment, n, compiler)
→ 语义是否一致
→ 相对同平台标量/专家实现是否稳定盈利
```

【合理推导】若不主动覆盖 `n` 位于向量边界附近的情况，错误的尾处理可能长期隐藏；若不寻找性能最差输入，平均值会掩盖短循环 `vsetvli` 开销、spill 或访存不连续导致的性能悬崖。

### 6.6 核心机制

对迁移函数 `f` 定义配置：

```text
z = <VLEN, SEW, LMUL, vl_policy, tail_policy,
     mask_density, alignment, n, stride, compiler>
```

语义 oracle 为标量参考或源 ISA 参考：

```text
Correct(f,z,x) = [RVV(f,z,x) == Oracle(f,x)]
```

性能归一化只在同一硬件内比较：

```text
Speedup(f,z,x,h) = T_baseline(f,x,h) / T_RVV(f,z,x,h)
```

测试生成器从以下高风险族开始：

- `n ∈ {0, 1, VL-1, VL, VL+1, 2VL-1, 2VL, 2VL+1}`；
- 对齐/非对齐地址、不同 stride、别名与非别名输入；
- mask 全真、全假、交替、稀疏和尾部集中；
- 规约中的 NaN、符号零、溢出边界和非结合顺序；
- 不同 SEW/LMUL 导致的寄存器组压力；
- 能触发频繁 `vsetvli`、spill 或 cache 边界的规模。

搜索分两层：

1. **语义层**：在 Spike/QEMU 或可配置模拟环境中快速扫多 VLEN，只用于找错误，不作性能结论；
2. **性能层**：在真实 RVV 硬件上用时间、反汇编和可用 PMU 反馈迭代生成压力输入，寻找最低 speedup 或最大退化。

发现失败后使用 delta debugging 缩减程序输入和配置，生成最小反例卡片：源/目标代码哈希、编译器版本、`z`、输入生成器 seed、期望/实际输出或时间分布。该卡片反馈给 IntrinTrans/FSCM 式翻译器重新生成，修复后必须回放全部历史反例。

### 6.7 系统组成与数据流

```text
NEON/x86/标量参考 + 候选 RVV 实现
                ↓
提取循环、intrinsic、尾/掩码和内存特征
                ↓
VLEN/SEW/LMUL 与边界输入变形生成
                ↓
Spike/QEMU 多配置语义扫描
                ↓
失败最小化与反例回放库
                ↓
真实 RVV 硬件上的时间/汇编/PMU 压力搜索
                ↓
性能悬崖条件与鲁棒性包络
                ↓
反馈翻译器修复 → 全历史反例回归
                ↓
输出：正确范围、性能范围、未知范围
```

系统不要求必须使用 LLM。LLM 可以生成候选和输入 synthesizer，但所有正确性结论由可执行 oracle 给出，所有性能结论来自真实硬件。

### 6.8 小白化例子

一个 RVV 循环在 `n=1024` 时正确且比标量快 4×。普通测试会判定迁移成功。新方法自动测试 `n=VL-1、VL、VL+1`，发现 `n=VL+1` 时最后一个元素被遗漏；修复后又发现当 `n<8` 时，反复设置向量长度的开销让代码比标量慢 30%。最终系统给出的不是一个“成功”标签，而是“所有边界正确；`n≥64` 才建议使用 RVV，否则保留标量路径”。

### 6.9 可检验的研究问题

1. VLEN 参数化变形测试能否发现常规 VecIntrinBench 测试未覆盖的语义错误？
2. 主动压力输入是否比随机输入更快找到 RVV 性能悬崖？
3. 最小反例反馈能否提高 IntrinTrans/FSCM 式翻译的修复成功率和减少轮数？
4. 在同等测试预算下，加入 VLEN/尾/掩码覆盖是否降低新硬件上的失败率？
5. 性能鲁棒性包络能否比单一平均加速更好预测真实应用中的路径选择？

### 6.10 可验证假设

- H1：相对固定输入测试，完整方法发现更多独立语义错误，尤其集中在 `k·VL±1`、mask 和规约边界。
- H2：相对均匀随机输入，PMU/时间反馈驱动的 synthesizer 用更少执行次数找到更低的最坏 speedup。
- H3：最小反例比完整失败日志更能提高 LLM 修复一次通过率。
- H4：依据鲁棒性包络选择标量/RVV 路径，比“始终使用 RVV”降低最坏情况退化。
- H5：删除多 VLEN 扫描后，当前板卡的平均性能可能不变，但跨配置语义失败和未见硬件回归显著增加。

### 6.11 最小可行 Demo

- **目标**：在 20 个 RVV intrinsic/自动向量化 kernel 上发现并最小化 VLEN/输入相关错误或性能悬崖。
- **数据**：优先复用 VecIntrinBench 的 20 个代表函数，加入 OML-vect 中 3–5 个 attention/MatMul kernel；来源分开报告。
- **候选**：neon2rvv 规则结果、IntrinTrans 式 LLM 输出、Clang/MLIR 自动向量化输出各一组。
- **语义环境**：支持调整 VLEN 的 Spike/QEMU/模拟环境；只用于功能测试。
- **性能环境**：一块可稳定运行 Linux 的 RVV 真机；具体芯片、VLEN、编译器和 PMU 需人工确认。
- **步骤**：建立标量 oracle→生成边界配置/输入→扫描并最小化语义反例→真机生成压力输入→定位性能悬崖→回放修复。
- **预计工作量**：1 周适配 20 个函数，1 周配置生成与 oracle，1 周反例最小化，2 周真机压力测试和统计。
- **成功标准**：发现固定测试遗漏的独立失败或显著性能悬崖；主动方法在同等预算下优于随机，且反例可一键复现。

### 6.12 实验设计

#### 实验平台

记录 RVV 版本、VLEN、编译器 commit、`-march/-mabi`、优化级别和运行库。模拟器结果只用于语义覆盖；性能数字只来自真机，平台之间只比较相对各自标量/专家基线，不比较绝对时间。

#### 数据集

- VecIntrinBench：规则和 LLM intrinsic 迁移；
- TSVC 子集：自动向量化和尾/规约模式；
- OML-vect kernel 子集：布局与真实 MLIR lowering；
- 负例集：人工植入错误尾处理、错误 mask、固定 VLEN 假设和 spill 诱发版本；
- 开发与最终测试按函数家族分开。

#### 对比基线

- 原始 benchmark 的固定测试；
- 均匀随机输入和随机 VLEN/规模；
- TRACE 式只按时间/内存迭代但不加入 RVV 结构特征；
- 固定边界清单但无反馈搜索；
- 完整方法：结构化配置、变形关系、主动压力搜索、最小反例和回放。

#### 消融实验

依次删除 VLEN 变化、`k·VL±1` 边界族、mask/tail、对齐/stride、PMU 特征、反例最小化和历史回放。另比较只有语义压力与只有性能压力的结果。

#### 评价指标

- 独立语义 bug 数、bug 类型和首次发现执行次数；
- 配置/边界覆盖率与反例最小化比例；
- 修复一次通过率、平均修复轮数和历史回归率；
- 最低/P10/中位 speedup 与性能悬崖深度；
- 同预算下达到最差已知输入的 Regret；
- 标量/RVV 路径选择后的负优化率；
- 测试总时间、编译次数和 LLM token 成本。

#### 统计要求

真机计时至少重复 20 次，使用中位数和 bootstrap 95% 置信区间；对压力生成方法用相同执行预算和随机种子集合。语义 bug 以根因去重，不把同一错误的多个输入重复计数。

### 6.13 与已有工作的创新边界

- 与 IntrinTrans 的区别：IntrinTrans 解决如何生成、编译、测试和优化 RVV intrinsic；本方法系统搜索 VLA 配置/输入反例，并评价生成结果的鲁棒边界。
- 与 VecIntrinBench 的区别：它提供固定的 50 个任务和测试；本方法是动态、反馈驱动、可最小化反例的评测协议。
- 与 LLM-Vectorizer/CoV 的区别：它们研究候选接纳与验证链；本方法的核心变量是 VLEN/`vl`/尾/掩码和性能悬崖，而非增加验证层级。
- 与 TRACE 的区别：TRACE 面向高级语言效率压力测试；本方法加入 RVV 结构化配置、变形关系、源/标量 oracle 和真机相对基线。
- 与 FSCM 的区别：FSCM 生成 NEON→RVV 高性能迁移；本方法可作为其外部压力审计器，不重复语义锚点和多 Agent 迁移。
- 直接复用的模块：VecIntrinBench 数据、neon2rvv/LLM 候选、Spike/QEMU、真机计时、delta debugging。
- 核心创新候选：**VLA 配置—输入联合反例空间 + 语义/性能双压力搜索 + 最小反例回放**。

### 6.14 风险与降级方案

| 风险 | 影响 | 降级方案 |
|---|---|---|
| 近邻工作已做系统跨 VLEN fuzzing | 新颖性下降 | 收窄到性能悬崖、反例最小化或翻译修复回放；先补在线检索 |
| 只有一块固定 VLEN 真机 | 无法真机跨 VLEN | 模拟器扫语义，多输入扫真机性能；不声称跨 VLEN 性能实证 |
| 模拟器与真机语义行为不一致 | 反例可信度受限 | 真机回放可执行反例；模拟器独有问题单独标记 |
| 测试 oracle 有浮点差异 | 假阳性 | 定义 ULP/相对误差与 NaN/符号零策略；区分严格和近似语义 |
| 未发现新语义错误 | 主结果变弱 | 转向性能悬崖 benchmark，报告覆盖提升与否定结果 |
| PMU 事件不可用 | 压力引导信息少 | 使用时间、汇编、spill 和 `vsetvli` 静态计数；PMU 为可选 |
| 候选函数太小 | 压力结果不代表应用 | 加入 OML-vect kernel 和真实库函数；微基准与应用层分开报告 |
| LLM 修复不稳定 | 无法证明反例价值 | 以检测/基准为主贡献，修复只作附加实验 |
| 搜索只学会放大输入 | 缺 RVV 特异性 | 与 TRACE 式无结构搜索对比，要求报告触发的 RVV 机制 |

### 6.15 可证伪条件

以下结果会否定或显著削弱候选创新：

1. 固定 VecIntrinBench/常规测试已经覆盖全部发现，VLEN 参数化不增加独立 bug；
2. 主动压力生成与随机输入在首次发现成本和最坏 Regret 上没有差异；
3. 找到的性能悬崖都只是通用算法规模效应，与 RVV/VLA 无关；
4. 最小反例不能提高人工或 LLM 修复效率；
5. 模拟器反例无法在任何真实实现或独立模型上复现；
6. 鲁棒性包络不能改善标量/RVV 路径选择；
7. 方法在未见函数家族上只产生大量假阳性或不可解释噪声。

### 6.16 综合评分

| 维度 | 1—5分 | 评分理由 |
|---|---:|---|
| 新颖性 | 4 | 避开 IntrinTrans/FSCM 的生成碰撞，聚焦 VLA 反例与性能悬崖；需补 fuzzing 近邻检索 |
| 文献证据 | 4 | 五篇直接文献少，但 IntrinTrans/OML-vect/TRACE/FSCM 形成互补证据 |
| 可实现性 | 4 | 可从 20 个函数和单块真机开始，主要是测试基础设施 |
| 实验可验证性 | 5 | bug、首次发现预算、最坏性能、修复轮数均可直接测量 |
| 与 RISC-V 相关性 | 5 | VLEN、LMUL、尾/掩码是 RVV 特有且不可用换平台替代的问题 |
| 与总体主线兼容性 | 4 | 可作为跨硬件迁移系统的外部验证与反例生成层 |
| 研究风险 | 3 | 真机 VLEN 单一和浮点 oracle 是主要限制 |

结论：当前适合作为**RISC-V 特异性最强的主创新候选**。它不与 IntrinTrans/FSCM 争夺“谁来生成 RVV 代码”，而是提供生成系统普遍缺少的跨 VLEN 可靠性和性能压力验收层。
