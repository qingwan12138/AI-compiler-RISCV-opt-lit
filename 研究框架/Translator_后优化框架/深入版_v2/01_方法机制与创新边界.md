# 方法机制：收益约束的联合 IR 修复

日期：2026-09-08。以下是待实现、待验证的算法设计。除第 8 节小型算术检查外，没有实验结果。

## 1. 把问题定义得足够具体

输入：经过固定清理的 LLVM IR 函数 P，以及模型直接生成的候选 Q。Q 可以解析，但整函数翻译验证不通过。

输出：同一函数的 IR 程序 Q*；它必须通过 P → Q* 的翻译验证，且清理后指令数少于 P。否则返回 P 或此前已验证的最佳结果，不把原样返回计为有效优化。

LLM 负责输出具体程序的替换 IR，而不是 pass、配置或可复用规则。因此它仍是 Translator。求解器负责筛选组合，不会改变 LLM 的角色分类。

任务不是一般 bug repair：P 是语义参考，Q 才是待修复优化候选；允许放弃 Q 的错误意图，不允许改变 P 的契约。

### 固定范围

- 第一版：完整单基本块、单整数返回值函数，5–80 条非调试 IR 指令。
- 核心语义：无标志的整数加减乘、位运算、整数比较、select、整数宽度转换；随后单独启用合法常量移位与受限除法。
- 暂不支持：内存、指针、调用、phi、循环、浮点、向量、异常、原子操作。
- 不允许候选新增 assume、undef、poison、强化参数属性，或新增 nsw/nuw/exact 等语义前提。
- 不修改原函数签名、数据布局、目标 triple 和属性；本来无法纳入该语义范围的样本保留排除原因。

这些限制是原型可行性边界，不是对真实 LLVM 优化范围的代表性保证。公开范围覆盖率，不能把不支持记成模型失败或悄悄删掉。

## 2. 目标函数与安全不变量

令 C 为固定编译清理，I 为清理后活跃 IR 指令计数：

主实验 C 固定为同版本 LLVM 的 `default<Oz>`；`default<O3>` 为预先约定的补充对照，不要求每个候选同时胜过两种配置。`instcombine,simplifycfg,dce` 只用于工具烟雾和诊断。不在看到结果后挑最有利配置。这里的 opt 中端流水线不等于完整 clang 驱动及后端配置，机器码评价还需单独锁定后端参数。

`J(Q) = I(C(Q))`

目标是在预算内找到 `J(Q*) < J(P)`，且 `Validate(P, Q*) = VERIFIED` 的候选。预算同时限制模型调用、Token、验证和总时间。

示例：P 清理后 20 条，候选清理后 17 条且验证通过，则收益 15%；候选只有 12 条但验证失败，收益记为 0；返回原函数也为 0。

上述 J 是 **IR 简化指标**，不是二进制尺寸或运行速度。P0/P1 先用它验证机制。若后续将论文定位为代码尺寸优化，另定义 `J_size(Q) = Bytes(Backend(C(Q)))`，按固定目标、CPU、后端参数测量函数机器码字节数；范围探针、候选排序和安全最佳结果选择都应对齐这一目标，或明确把 IR 指标作为第一阶段代理并增加机器码复选，不能仅更换结果表的列名。

示例：IR 从 20 条减到 17 条，但机器码从 80 字节变成 84 字节，只算 IR 简化，不算尺寸改善。代码尺寸阶段必须保留原程序作为回退，最终不能仅因 IR 更少而选择机器码更大的版本。

LLVM 优化验证通常是 refinement（细化，即不引入源程序不允许的行为），不能统一写作双向语义等价。对于本方案确定性且有定义的具体输入子域，可以使用结果相等来构造反例过滤；最终仍按工具的整函数细化检查裁决。

**安全不变量：**最终结果只能来自整函数验证成功的候选集合。超时、工具错误、不支持、反例无法解析均不是成功。保存最佳安全结果，不等于永久冻结其中每一处代码。

## 3. 系统数据流

```text
P 与初始错误候选 Q
        ↓
M1：可替换区域与候选库（工程基础）
        ↓
M2：累积反例 → 过滤错误组合（成熟 CEGIS 基础）
        ↓
统一清理与实际收益评价 → 整函数 Alive2
        ├─ 成功且更优 → 更新安全最佳结果
        ├─ 失败 → 保存反例，继续 M2
        └─ 当前组合无进展
                  ↓
M3：决定联动重写范围 + 构造残余关系契约
                  ↓
LLM 直接生成该程序的新 IR 区域
                  ↓
加入候选库，回到 M2；预算耗尽返回安全最佳结果
```

不需要多个 LLM Agent、训练、RAG 或 MCTS。增加它们会让贡献归因更困难。

## 4. M1：可替换区域与候选库

### 输入、处理、输出

输入是 P、Q 的 AST/SSA 数据流，而非逐行文本 diff。SSA（Static Single Assignment，静态单赋值）意味着每个值有唯一的定义，区域替换必须保持定义和使用合法。

第一实现使用 P 的固定数据流区域边界；模型提交每个区域的替换代码和整体重建结果。区域边界只负责接口，不规定区域必须保持原中间值。

- 区域接口：稳定的 Region ID、live-in 值、live-out 值的数量及类型、依赖顺序。
- 区域内部允许新增临时 SSA 值；拼接时自动重命名。
- 多区域可合并成联合区域后重写；否则固定原中间接口可能排除真正的协同变换。
- 一旦跨边界引用非法或无法对齐，不猜测映射；记录覆盖失败并回退全函数生成。

输出：候选图。每个区域的备选值包括原代码、初始 LLM 替换、后续重写；一种组合 z 选择每个区域的一个备选，确定一个完整函数 Q_z。

**两个评测轨道：**主机制实验中所有方法使用同一结构化初始候选；额外测自由整函数生成的可对齐率。否则不能声称方法普遍适用于任意整函数 LLM 输出。

M1 不是创新。过度复杂的图对齐如果成为主要工作量，先停在固定区域轨道，不提前写“通用 IR 补丁恢复”。

## 5. M2：反例约束组合，而不是给修改贴对错标签

设 W 是已收集的具体反例输入集合。对能精确建模的确定性有定义子域，构造：

`Φ_W(z) = ∧_{w∈W} [Defined(Q_z,w) ∧ Value(Q_z,w)=Value(P,w)]`

P 在这些 w 上必须有定义。z 是区域选择；Value 是整函数输出；Defined 约束候选不能在该输入引入未定义行为。使用位向量运算，不使用数学无限整数替代 LLVM 整数溢出。

例：已有两个反例，如果某组合在第一个输出 7 而 P 输出 8，直接排除该组合；不能据此排除“包含它某个修改”的所有其他组合。

### 最小实现分两级

1. 当最多 8 个二选一区域时，最多 256 组：用已验证的具体解释器逐组过滤，并实际调用 C 计数。先做这个版本，不默认 SMT 更快。
2. 组合较多时，再用 Z3 的位向量条件表达式编码不同选择，在 Φ_W 下寻找尚未尝试的配置。此处仅减少全局验证调用，不能保证全局最优。

每次整函数验证失败，累积新反例；替换候选内容改变后重新编码 Φ_W。反例输入保留，但旧区域公式不能盲目复用。

### LLVM 语义安全边界

Alive2 的公开说明展示了文本反例，而非承诺一个本方案可以直接调用的稳定 JSON API。应固定提交版本、保存原始输出并实现受限解析器。[官方仓库](https://github.com/AliveToolkit/alive2)

- poison/undef、未支持的属性或复杂反例不能强转为普通数值。
- 不能为了方便启用 `-disable-undef-input` 后仍声称原始完整语义验证；若做限制实验，必须另外标注输入假设。
- 未支持的反例只作文本反馈；最多排除已经被验证器明确反驳的同一完整候选，不泛化剪枝。
- 自写解释器/SMT 适配层不承担最终正确性保证；在对照校验通过前，只能给搜索排序，不允许硬删除未知候选。

### 不把编译清理成本硬塞进一个错误公式

`J(Q_z)` 不能近似成“各区域减少指令数之和”。清理可能跨区域消除、合并或展开代码。

最小版本对具体组合运行 C 获取真实 J，并缓存结果。SMT 中的原始指令数只可用于候选排序。若代理成本边界下 UNSAT，只能说代理边界/当前库不可满足，不能说不存在清理后有收益的程序。

有限库搜索用完也不等于语义任务无解；新生成代码仍可能带来解。

## 6. M3：以收益前沿决定联动范围，并给关系契约

这是唯一值得进一步试验的方法区别候选。它基于既有语义修复技术，不把“契约”本身宣称原创。

### 6.1 为什么不只告诉 LLM “这里错了”

对于参考输入 w，局部结果不必逐个等于 P 的中间值；只要经固定外部代码组合后输出符合 P 即可。强制每个中间值回到 P，可能恢复正确性同时消除优化。

设 R 是要重开的区域集合，E 是固定外部上下文。将 R 的边界输出临时符号化为 h，得到关系：

`K_(R,E,w)(h) = Defined(E[h],w) ∧ Value(E[h],w)=Value(P,w)`

h 不是模型最终答案，而是描述允许的边界值关系。多个 h 可能相互约束，不能随便挑一组可满足值当唯一正确标签。

对 W 中每个输入分别构造 K；若区域上游也在 R 中，联合建模依赖，不使用过时的具体 live-in 值。

这是一种 angelic（暂把待修复表达式当自由值）的分析，是已有语义修复思想的应用。有限输入上存在满足的 h 也不保证存在一个统一、可实现的 IR 程序。

### 6.2 范围选择的可执行规则

第一版无需学习排序器：

1. 从候选与 P 的差异区域中枚举单区域，再枚举数据流相邻区域对。每轮最多 12 个范围；超出按稳定 ID 排序，预算限制显式记录。
2. 对每个范围检查所有当前反例上的关系可满足性；不满足的范围在固定 E 下不请求 LLM。超时记 UNKNOWN，不视为无解。
3. 同时运行一个**成本探针**：将该范围恢复原区域，其余保持 E，执行 C，得到 `J_probe`。它是回退上下文的静态成本观测，不是合法优化收益或理论最优成本。恢复后结构非法则该探针不可用；若未通过整函数验证，必须标为 unverified，不能称保住了正确收益。
4. 对可行范围维护二维候选前沿：范围指令量越小越便宜，探针成本越低越有保留收益潜力。若 A 两项不劣于 B 且至少一项更好，则 B 本轮低优先级，不永久删除。
5. 从前沿选择范围，按范围指令量、J_probe、ID 依次破同分。连续两次没有新安全改善后，轮转到下一范围；再无进展才扩大到三处或整函数。
6. 已验证最佳程序只是返回保障；允许以它为工作上下文重开区域。已经正确的区域并不禁止加入 R。

这一定序是透明的工程假设，可能不如最小范围策略。**必须用消融证实收益探针和前沿调度有价值；不能把 Pareto 一词当创新。**

### 6.3 给 LLM 的信息，不只是一句自然语言错误

输入包固定包含：

```text
reference_ir：P；working_ir：当前工作候选
region_ids：本次联合区域；live_in/live_out：类型接口
counterexamples：最多 8 个代表反例，完整 W 留在工具端
residual_relations：简化位向量关系，最多 2 个 live-out
allowed_alternatives：几组满足关系的示例，注明非唯一答案
cost_target：J 小于安全 incumbent；这是努力目标，不是允许改变语义
output_contract：只输出该程序的替换 IR，不生成 Pass，不加新前提
```

关系无法压缩到固定 Token 上限时，退回具体输入、源/目标输出和边界信息；记录 contract_fallback，不能把整段求解器表达式无限塞进上下文。

模型仍然生成统一代码而非逐输入修补表。禁止为已见输入硬编码特判的提示；即使模型这样生成，最终全域验证和收益检查也不得放松。

外部 E 改变后，局部契约必须重算。不能把以前上下文中的“局部正确”当永久证书。

### 6.4 具体契约例子

假设外部最终计算 `ret h1 + h2`，参考在输入 w 返回 8。合法局部关系是 `h1 + h2 = 8 (mod 256)`，而不是硬要求 `h1=3,h2=5`。

候选 `h1=2,h2=6` 也能满足这一输入。对下一反例输入还会有新关系，LLM 必须找到同时满足它们的程序；最后通过整函数验证才接受。

这是为什么联合关系比两个独立目标值保留更多候选自由度。但有限反例是否足以帮助模型而不是让提示更难懂，是实验问题。

## 7. 主循环伪代码与退出

```text
best = P
library = original_regions + initial_LLM_variants
W = {}
while shared_budget_not_exhausted:
    z = next_untried_combination_consistent_with_supported(W)
    if z exists:
        Q = assemble(z)
        if not structurally_legal(Q): log_invalid; continue
        Qc = cleanup(Q)
        if cost(Qc) >= cost(best): log_no_gain; continue
        verdict = whole_function_validate(P, Qc)
        if VERIFIED: best = Qc; continue
        if COUNTEREXAMPLE: add_witness_or_text_feedback(W); continue
        log_unknown_or_tool_failure; continue
    R = next_feasible_joint_region_by_frontier()
    if R absent: optionally_expand_to_full_function_or_stop()
    package = build_context_bound_contract(P, working_Q, R, W)
    new_ir = LLM(package)
    add_legal_variants_to_library(new_ir)
return best
```

跳过无收益候选只是不花整函数验证预算，不能删除其局部变体，更不能阻止之后由它们产生新组合。独立 P0 诊断阶段会验证无收益组合，以分析错误交互；它与正式运行策略不同。

## 8. 已运行的语义小检查：为什么单调剪枝错误

这不是 LLVM 或 LLM 实验。2026-09-08 用 Python 穷举 8 位整数 x、y 共 65,536 组输入，检查以下算术模型的八种修改组合：

```text
u = x + 1                  修改 a：u = x
v = u - 1                  修改 b：v = u
q = signed_divide(y, 2)     修改 c：q = arithmetic_shift_right(y, 1)
return v + q
```

加减和返回按 8 位回绕，signed_divide 向零截断。位串 abc 中 1 表示应用该修改。

| 组合 | 全输入不一致数量 | x=0,y=-3 通过 | x=0,y=0 通过 |
|---|---:|---|---|
| 000 | 0 | 是 | 是 |
| 001 | 16384 | 否 | 是 |
| 010 | 65536 | 否 | 否 |
| 011 | 49152 | 是 | 否 |
| 100 | 65536 | 否 | 否 |
| 101 | 65536 | 否 | 否 |
| 110 | 0 | 是 | 是 |
| 111 | 16384 | 否 | 是 |

结论仅有三条：a、b 各自错误但联合正确；初始 111 可以通过撤回 c 恢复；011 会偶然通过第一个反例却不是正确程序。

所以不能从“a 错”推出“所有包含 a 的组合都错”；也不能把一个反例上的补偿视为证明。此例中的冗余可能被编译器直接消除，**不证明 LLVM 清理后存在收益，更不证明自然样本分布**。

可复算代码（纯 Python 算术，非 LLVM 语义实现）：

```python
from itertools import product
wrap = lambda x: x & 255
def signed(x):
    return x if x < 128 else x - 256
def div2(y):
    return (abs(y) // 2) * (1 if y >= 0 else -1)
def run(x, y, a, b, c):
    u = wrap(x + (0 if a else 1))
    v = wrap(u - (0 if b else 1))
    q = (signed(y) >> 1) if c else div2(signed(y))
    return wrap(v + q)
for z in product((0, 1), repeat=3):
    bad = sum(run(x, y, *z) != run(x, y, 0, 0, 0)
              for x in range(256) for y in range(256))
    print(z, bad)
```

## 9. 与已有方法的区别应该怎样写

| 组成 | 定位 | 真正需要证明的增量 |
|---|---|---|
| CEGIS、位向量求解 | 借用技术 | 是否比小规模枚举节省总成本，而非仅减少验证次数 |
| 多位置关系契约 | 借用语义修复思想 | 在生成优化 IR 时是否比原中间值标签更能得到有收益代码 |
| 编译清理和 Alive2 | 工具基础 | 工程可靠性，不是方法创新 |
| 收益探针 + 可行联合区域前沿 | 候选方法区别 | 是否优于最小修改、固定范围、随机范围以及相同契约的普通多位置修复 |
| 失败数据集与固定起点评价 | 实证支撑 | 是否排除了 cherry-picking 和额外预算的解释 |

Angelix、Qlose、MENTOR 等近邻及链接见[独立检索](00_修订结论与独立检索.md)。删除前沿策略后若结果不变，不能继续主张它是贡献；如果只加关系提示有效，论文应诚实收缩为反馈表示研究。

## 10. 可证明什么、不能证明什么

在验证器正确、调用配置无误的条件下，可论证：输出只从验证成功集合选择，不会因自写启发式直接接受未经验证的优化。

不能据此证明：方法完备、得到全局最优、LLVM 全语义无漏洞、代理成本对应 runtime、有限反例可证明正确、某个局部区域天然有错。

若要写剪枝可靠性定理，必须先限定精确支持的指令子集，证明其具体/符号语义一致。否则将其定位为搜索启发式，不声称形式化完备性。
