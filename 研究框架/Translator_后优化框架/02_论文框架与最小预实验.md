# 面向 LLM 生成 LLVM IR 的优化收益保持修复

> v1 历史方案，算法与评价设置不再作为当前执行依据。请使用 [新版预实验协议](深入版_v2/02_预实验执行协议.md)：Oz 主基线、O3 补充对照，并区分 IR 简化与机器码尺寸收益。

日期：2026-09-08。**这是待验证的论文框架，不包含已取得的实验结果。**

证据出处和近邻核验见 [证据审计](01_证据审计与候选比较.md)。本文件中的算法、预算、阈值与时间安排均是研究设计建议。

## 1. 论文究竟研究什么

研究对象是：LLM 已经尝试优化、但被语义验证器否定的具体 LLVM IR 程序。

研究问题不是“如何让模型学会所有编译优化”，而是：

> 同样只允许有限次生成和验证，能否保留错误候选中仍然成立的优化，减少从头生成的浪费，并提高最终可用优化比例？

“优化收益保持”指保留已经通过整体验证的指令缩减，不是保留模型自称有用的修改。语义验证器 Alive2 用来检查源程序到目标程序的 refinement（精化：目标不能引入源程序不允许的行为）；本文不把它简化为对任意 LLVM 程序都完备的数学等价判定。

### 固定三个子问题

- **RQ1 可救回性：**真实错误候选里，是否存在正确且有收益的修改子组合？比例和绝对数量是否值得做？
- **RQ2 方法增量：**同预算下，收益保持修复是否优于整段反馈重写、普通局部修复和纯工具搜索？
- **RQ3 代价与边界：**效果来自收益约束、局部化还是额外搜索？在哪种修改数量、依赖程度和模型上失效？

RQ1 不成立，就不进入完整方法开发。RQ2 不成立，就不能以新方法论文的口径宣称成功。

## 2. 第一版范围：故意小，但不能只选容易样例

| 维度 | 纳入 | 排除 |
|---|---|---|
| 程序形态 | 完整单基本块函数，5–80 条 IR 指令 | 循环、跨块变换、递归 |
| 操作 | 标量整数算术、比较、位运算、转换、select | 浮点、向量、指针、load/store、call、原子操作 |
| 语义边界 | 固定类型、函数签名、返回结构；按 LLVM 语义验证 | 更改函数前置条件、增加 assume、用 undef/poison 投机缩短程序 |
| 输入条件 | 先用固定清理流水线处理，再给模型 | 只用原始 -O0 冗余代码证明增量价值 |
| 处理对象 | 语法合法、验证器明确 refuted 的候选 | 把 timeout、unsupported 当语义错误 |
| 目标 | 更小且通过验证的 IR | 必须提升 Runtime、跨架构泛化、生成通用规则 |

第一版不让 LLM 增加 `nsw/nuw/exact` 等语义约束标志；源程序若含这些特性，先按预登记规则排除，而不是擅自删除标志后说仍是原问题。

采用固定 LLVM/Alive2 兼容版本，记录版本和提交哈希。清理流水线 C 初拟为 `instcombine,simplifycfg,dce`，必须先用开发集验证工具版本支持，然后冻结，不根据测试结果更换。最终输入是 P = C(P_raw)。所有方法的输出统一经过 C 再计数并验证。

这会让任务更难，但能够排除“模型只学会去掉 x+0”这种贡献不足的成功。

## 3. 一个能看懂、但不能用来证明创新的例子

原始程序做三件事：

```text
a = x + 0
q = signed_divide(y, 2)
return a + q
```

模型同时做两处修改：

```text
删除 a，直接使用 x                 ← 这处正确
把 signed_divide(y,2) 改为 y >> 1  ← 对部分负奇数不正确
```

例如 y=-3，向零截断的有符号除法得到 -1，算术右移得到 -2。整个候选应被拒绝。

整段拒绝：两处修改全部丢失。候选做法：撤销错误的除法替换，保留第一处简化，再验证完整函数。如果通过，至少保留了一个正确修改。

**这个例子只解释动机。LLVM 本身已经会消去 x+0，经过主实验的清理流水线后不会构成增量收益，也不算一个研究结果。**真实实验必须用模型自然产生的失败候选，不能仅靠人工把错误拼入正确优化。

## 4. 实现不超过四个模块

### 4.1 修改表示：每次输出具体 IR，不输出优化规则

为了支持可撤销修改，初版让所有模型方法共享同一种输出接口：最多四个不重叠的局部替换区，每区包括原指令 ID、边界输入/输出和新的 IR 片段。

```text
原函数 + 稳定指令 ID + 可替换区域及边界类型
    → LLM
    → 本函数专用的 IR 替换片段
    → 确定性拼装为完整函数
```

边界输入是区域从外部使用的值，边界输出是区域外仍然需要的值。替换不得偷偷改变边界类型或引用未定义变量；删除原输出时必须提供合法的同类型别名映射。新变量在区域内命名，不得直接跨区域引用。

工具只检查和拼接这些具体程序片段，不把自然语言转成 Pass，也不执行模型生成的通用 Python 编译脚本。**因此仍是 Translator，不是 Selector 或 Generator。**

初版不要解析任意整段 IR 的文本 diff 来猜编辑关系。使用显式编辑接口降低实现风险；但必须报告该接口对优化空间的限制，并为所有基线保持一致。另加整段输出对照，检查接口是否过于保守。

### 4.2 合法组合：不是按行随意删除

保存原函数和候选编辑集合 E。对每个子集 S，尝试在原函数上重建 P_S：

1. 检查区域重叠、变量定义使用、类型、边界别名与替换依赖。
2. 对无法独立撤销的编辑组成原子组；子集只按组选择。
3. 拼装后运行 LLVM 合法性检查。失败只记为非法组合，不调用模型“猜测修补”。
4. 最后对完整 P 与 C(P_S) 运行 Alive2；不使用“每段分别通过，所以组合必然通过”的推理。

这里的依赖闭合只解决结构合法性，不证明各编辑语义独立。两个单独错误的修改可能组合正确，两个单独正确的修改也不能在任意上下文中直接拼接。因此搜索不能假定收益或正确性对编辑集合单调。

### 4.3 收益保持：维护可验证的最好版本

维护一个 incumbent，即“当前已验证的最好完整版本”。初始为原输入 P，收益为零。

候选不正确时，先按少撤销到多撤销产生合法子集。主方法优先测试清理后 IR 数量较小的子集；这是待验证的搜索启发式，不是已证明最优算法。对相同计数使用固定 ID 次序，避免隐藏随机优势。

只有同时满足以下条件的子集才更新 incumbent：

- 完整源→目标验证通过；
- 清理后的指令数比 incumbent 更少。

不能因为一个子集指令数很小就宣布它“保留了有效收益”；通过验证之前它只是候选。不能把全量枚举得到的最优答案当作在线方法免费使用。

### 4.4 局部重写：先保护已取得的收益

当找到非空、正确且有收益的保留集合 S 后，只开放其他区域给 LLM 重写。输入包括原区域、当前已验证版本、允许修改的区域、边界类型、当前错误诊断（若有）和成本上界。

模型输出仍是 IR 片段。拼装后重新验证完整函数，并要求指令数严格小于 incumbent 才接受。失败则保持 incumbent，不覆盖已验证结果。

若没有找到可保留的收益，不伪造冻结区域；退化为普通反馈重写，计入同一预算。每次生成的新编辑集合都重新建立依赖与验证状态，不继承旧版本的“局部正确”标签。

当前方案不加入学习型排序器、不训练奖励模型、不建多智能体。可检验的变化只有：**保留集合按已验证优化收益确定，并在后续重写中作为硬约束保护。**

## 5. 简化算法与安全边界

以下是算法说明，不是已经实现的代码：

```text
输入 P、固定模型 M、模型预算 Bm、验证预算 Bv
best ← P
生成候选 Q（计入 Bm）
若 Q 合法且验证通过：按相同成本规则更新 best
若 Q 被语义反驳：
    E ← 解析显式编辑并形成可撤销原子组
    在 Bv 内尝试合法编辑子集：
        对完整 P → C(P_S) 验证；严格有收益才更新 best
    若已取得非零收益：
        冻结保留区域，只让 M 改写剩余区域
    否则：
        使用普通反馈重写
    对每个新完整候选重新清理、验证、计费、择优
预算耗尽：返回 best；另报所有失败和超时
```

不把 Alive2 反例视为“精确定位出错行”的工具。反例只能证明某次变换不成立；本方案通过候选组合验证定位可保留范围。反例回放若实施，仅作为便宜的拒绝测试，不承担最终正确性证明。

所有失败输出回退为输入，是安全策略；但不能把回退计为“模型优化成功”。验证支持范围、原程序未定义行为、编译器和验证器自身缺陷均是适用限制。

## 6. 与最近邻的真正差别在哪里

| 前作/基线 | 不能再宣称的新颖内容 | 本方案必须证明的增量 |
|---|---|---|
| LPO/Lampo 式反馈迭代 | LLM 优化 IR、Alive2 过滤、反馈修复、小片段优化 | 不只是多次尝试，而是在有限预算下保住错误候选中的有效修改 |
| 反例引导的局部程序修复 | 定位、冻结、补洞、反例循环 | 优化任务中“修对”不等于“保住收益”；收益约束是否有独立效果 |
| Delta debugging 式编辑子集搜索 | 逐步撤销修改、测试候选、缩小问题 | 收益导向的保留和 LLM 后续重写是否优于纯工具搜索 |
| 直接 best-of-k 重采样 | 多生成几个然后验证选优 | 不能通过更大模型、更多 Token 或更多 solver 调用获得伪优势 |

Delta debugging 在这里指逐步删减变化并检查结果的调试思想。基线必须尊重程序结构，不能故意用经常产生坏语法的“删文本行”实现削弱它。

如果强基线稍加一个“优先保留缩减量大者”的排序就达到同样效果，那么当前机制增量不足，应撤回方法创新主张。此时可以保留测量结果，但不能用新名字继续包装。

## 7. 指标：正确且有收益，而不是只要通过率高

主实验锁定 **IR 指令数**，不在结果出来后改成最漂亮的其他指标。统计完整函数中所有非调试 IR 指令，包括返回指令；对输入输出采用相同规则。C 表示固定清理流程，I 表示其后的指令数。

### 主指标：有效优化率 U

```text
U = 验证通过且 I(output) < I(input) 的测试函数数 / 全部纳入测试函数数
```

越高越好。例：100 个函数，30 个获得已验证的更小 IR，U=30%；其余错误、超时、原样返回都不算成功。

每个函数在固定预算内只贡献一个最终最好结果。不能把同一函数的多条候选当成独立样本扩大 N。

### 必须同时报告的指标

| 指标 | 定义与方向 | 防止的误导 |
|---|---|---|
| 全样本平均缩减 G | 平均 (I(input)-I(final))/I(input)，回退项为 0；越高越好 | 只展示成功样本的收益 |
| 条件救回率 R | 起始为语义错误的候选中，最后变成正确且有收益的比例；越高越好 | 把所有失败都声称能救回；R 不替代端到端 U |
| 生成/验证状态分布 | 合法、refuted、inconclusive、verified-unchanged、verified-improved | 原样返回使正确率虚高；超时混进错误率 |
| Token、模型调用 | 输入和输出 Token 分列，包括重试与格式修复；越低越好 | 局部修复多调用但只统计短输出 |
| 验证代价 | unique solver 调用、CPU/墙钟时间、超时数、缓存命中率；越低越好 | 把穷举开销藏在工具里 |
| 最坏情况与覆盖率 | 大修改集合、被接口排除的函数、没有剩余优化空间的函数数 | 只选独立且易救回的修改 |

补充实验可以测二进制 `.text` 大小，但固定目标与编译参数；若只改善 IR 而二进制无变化，就明确报告。Runtime 是可选外部有效性检查，不是本论文必达指标。验证耗时属于方法成本，不是程序 Runtime 收益。

这套指标是针对当前任务选取的，并非已完成对全领域“指标使用频次”的统计。

## 8. 公平对比：最少六条基线

| 编号 | 方法 | 要回答什么 |
|---|---|---|
| B0 | 固定 LLVM 清理；另报 -O3、-Oz 参考结果 | 是否只做了传统编译器已有优化 |
| B1 | 同模型独立重采样 + 验证选优 | 是否只是多试几次就能取得的收益 |
| B2 | 整段反馈重写：提供原输入、失败候选、完整相同诊断 | 是否真的优于普通 LPO 式反馈循环 |
| B3 | 普通局部修复：同样编辑接口，按最小回退/固定次序定位，不以收益选择保留集合 | “局部”本身能解释多少收益 |
| B4 | 纯工具、结构合法的编辑子集搜索；不再调用 LLM 修复 | LLM 局部重写有没有增量 |
| B5 | 收益优先的子集搜索，但无冻结收益的后续约束 | 排序启发式是否就足够，无需完整机制 |
| Ours | 收益导向保留 + 冻结有效区域 + 剩余区域 LLM 重写 | 检验完整主张 |

B2/B3 是明确描述的适配基线，不冒称对 LPO、AAAI 修复系统的逐行复现。论文应提供原作者配置能运行时的附加实验；无法复现则公开差异。

两类实验分开：

1. **配对修复实验：**所有方法共享完全相同的失败候选与诊断，测 R，隔离候选生成差异。
2. **端到端实验：**从相同输入开始，生成、搜索和修复一起计费，测 U/G，检验实际收益。

开发集暂定每函数最多 8 次模型生成、32 次独立 Alive2 查询，单次验证上限 10 秒；同时设置固定总 Token 上限。Token 上限在开发集按可容纳完整输出的长度确定并冻结，测试集不能另调。正式表格同时报告实际成本，并画收益—成本曲线，不能只用调用次数声称公平。

B4 少花的模型预算不能凭空忽略：还须比较“B4 + 将剩余预算用于重采样”的强混合基线。固定资源向量不能完全等价于固定墙钟，应分别报告，不合成任意加权总分掩盖差异。

缓存策略与原始验证日志对所有方法一致；离线穷举只用于 RQ1 上限诊断，绝不计作免费在线 oracle（理想答案）。

## 9. 消融：每项只移除一个东西

- **无收益选择：**相同验证数，改为固定/随机次序选择保留集合，检验成本目标。
- **无冻结：**给相同上下文但允许重写全部区域，检验保护已有修改是否有帮助。
- **无 LLM 修复：**只返回最佳验证子集，检验后续生成是否必要。
- **无结构约束：**仅在诊断实验比较文本差分回退；不把此弱基线当主要竞争者。
- **接口对照：**相同模型、输入与总预算，比较整段输出和显式局部输出，识别收益是否全来自格式约束。

机制与格式作用必须分开报告。若增益只来自格式约束，论文主张必须改写，不能仍称“收益保持修复”得到验证。

## 10. P0：第一周先测空间，不写大框架

### 数据及工具

优先检查 [LLM-VeriOpt 公开 artifact](https://github.com/carrotProgrammer/llmveriopt-AE) 的数据、模型输出与许可，能重放则先重放；仓库公开不等于全部所需输出可直接取得。替代来源为 [LLVM test-suite](https://github.com/llvm/llvm-test-suite) 中按固定规则纳入的完整函数。下载和使用前核验许可、版本、数据划分。

用文件/项目来源分组并做规范化 IR 哈希去重；同一模板、来源函数及其变体不能跨开发与测试集合。已有模型可能见过公共测试集，这一污染风险须记录，不能保证“训练未见”。

先选 100 个合规开发函数，顺序由固定种子确定。每函数最多生成 4 个候选。选择生成配置后冻结，不为制造错误故意调高温度。没有优化空间的函数仍保留在端到端分母中。

### 最小工作包

1. 建一个 Python 驱动：调用固定 LLVM、Alive2、模型适配接口并记录 JSONL 日志。LLVM 结构处理用正式解析接口，不能靠正则冒充 IR 解析。
2. 先用 10 个自构造样例检查正确、错误、超时、非法接口四种状态；不计入研究证据。
3. 对 100 个真实函数采样并分类；所有候选和失败输出保存。
4. 对按固定顺序出现的前 40 个合规语义错误候选，最多四个原子编辑组，枚举最多 16 个子集；每次验证上限 5 秒。此处是有界可救回性测量，不声称全局最优。
5. 统计有多少不同来源函数能保留至少一处修改且仍比清理后输入更小；另记完整候选虽错但没有任何有用子集的情况。
6. 把同一批失败候选交给 B1/B2/B3/B4 做小规模比较，记录真实预算，而不是直接开始强化学习。

### P0 继续/停止标准

下列数字是立项止损阈值，不是显著性检验，也不是预期结果：

- 100 个函数中若不足 20 个不同函数产生合规语义失败，可以按同一规则扩到最多 300 个开发函数；仍不足则停止这条失败挽救主线，不能无限增样找案例。
- 在有界检查中，至少 10 个不同函数存在非平凡、有收益的可验证子集，才投入下一阶段。这只是最低开发门槛，不足以支撑论文。
- 若收益只在 -O0 原始输入出现，清理后消失，则不进入该方法主线。
- 若修改组经常无法拆分，或多数预算消耗在非法组合，先判定接口不可用，不先训练模型补救。
- 若纯工具回退已经取得全部收益，LLM 剩余重写不增加结果，则不支持“LLM 修复机制有增量”的主张。

未安装工具、缺模型资源属于执行条件未满足，不等于研究假设被否定。

## 11. P1：过了 P0 才做可写论文的实验

冻结算法和阈值后，另取至少 300 个未用于调参的函数，尽可能覆盖三个独立来源。该数量是启动规模，不是功效保证；依据开发集方差和配对差异率预先做样本量估计，需要扩大时在看测试结果前决定。

使用两个固定版本、不同家族的代码模型，分别报告，不把模型升级产生的收益混入方法增量。第一版不训练；本地小模型或已有授权 API 二选一取决于可用资源。本轮没有发起付费采样。

每方法至少三个独立采样种子。统计以来源函数为聚类单位，使用配对 bootstrap 95% 置信区间；同源变体不当独立样本。主检验只预先选择 U，G、R、成本和消融作为次要结果，避免只挑显著指标。

暂定值得继续的方法效果标准：相对开发集选出的最强基线，测试 U 提高至少 5 个百分点，配对区间下界大于 0，且不突破资源上限；第二模型效果不能完全反转。这是工程投入门槛，不是会议录用标准。

### 论文至少需要的结果表/图

1. 样本流转表：原始→合规→重复剔除→语义失败→存在有用子集。
2. 主结果表：所有方法 U/G、状态分布、Token、验证时间；包含 -O3/-Oz 参考。
3. 收益—成本曲线：在不同预算下是否仍占优。
4. 消融表：收益选择、冻结、LLM 修复各自的作用。
5. 边界分析：按编辑组数量、依赖耦合、输入长度、操作类型分层，展示失败案例。

## 12. 什么结果会否定这篇方法论文

以下任何结果都不能解释成成功：

| 结果 | 应作决定 |
|---|---|
| 真实候选几乎没有可保留的优化 | 放弃机制主线，不继续堆模型 |
| 同预算重采样不差于本方案 | “减少浪费”的主张不成立 |
| B3/B4/B5 足以解释全部收益 | 不把已有修复/搜索换名当创新 |
| 只有人工注错数据有效 | 仅验证了演示可运行，不能证明现实价值 |
| U 提升但验证时间急剧增加、预算不公平 | 重新做公平对比，不能发表为低开销方法结论 |
| 只在未清理输入有效 | 更适合模型能力评测，不能声称发现编译器增量优化 |
| 超时大量增加 | 报告适用范围缩小，不能当作语义正确 |

结果为阴性时可保留公开失败分析与评测材料，但是否足以形成测量论文要重新判断，不能预先承诺“无论结果怎样都能写”。

## 13. 如果结果成立，论文按这条逻辑写

### 拟定的三点贡献

1. **测量贡献：**刻画真实 LLM IR 优化失败中可救回修改的比例、结构和收益上限；用自然失败与来源隔离数据验证，而不是只展示手工案例。
2. **机制贡献候选：**提出优化收益约束下的保留与局部重写，证明区别于最小修复及纯子集搜索；只有消融与强基线支持时才保留此项。
3. **实证贡献：**提供统一预算、明确验证状态和失败回退口径的复现实验，展示收益及失败边界，而非只给平均正确率。

### 章节骨架

| 章节 | 必须回答的具体问题 |
|---|---|
| 1 Introduction | 为什么整个错误候选里可能有值得保留的修改，代价是什么？ |
| 2 Background and Scope | Translator 任务、LLVM 语义、验证及目标范围是什么？ |
| 3 Motivating Study | P0 是否证明问题有足够出现频率，而不只是一个玩具例子？ |
| 4 Method | 编辑接口、子集合法性、收益保持与局部重写具体如何运作？ |
| 5 Evaluation | RQ1–RQ3、强基线、预算、统计和消融如何支持主张？ |
| 6 Discussion and Threats | 受限 IR、污染、工具盲区、仅静态目标会怎样限制结论？ |
| 7 Related Work | 与反馈优化、局部程序修复、语义引导搜索分别有什么差异？ |
| 8 Conclusion | 只总结实际得到的数据，不补写未验证的泛化能力 |

题目备选（均不预告实验一定成功）：

- 面向 LLM 生成 LLVM IR 的优化收益保持修复 / *Preserving Optimization Gains when Repairing LLM-Generated LLVM IR*
- 错误 IR 优化候选中的有效修改保留 / *Retaining Useful Edits in Invalid IR Optimization Candidates*
- LLM 编译优化中局部修复的收益与边界 / *Benefits and Limits of Local Repair in LLM-Based Compiler Optimization*
