# 可验证结构化编辑驱动的 LLM 编译优化器：主线研究框架

## 1. 结论

这个框架最适合快速预实验。它不让大语言模型（Large Language Model，LLM）重写完整程序，而是只允许 LLM 填写一个局部编辑契约，再由确定性执行器完成修改和验证。

## 2. 研究问题

现有 LLM 编译优化方法可以生成源码、LLVM IR、Pass 序列或编译器 Hint，但自由生成容易带来：

- 修改范围失控；
- 语法、类型或 Static Single Assignment（SSA）约束错误；
- 为修复一个错误重写无关代码；
- 结果变好但无法判断是哪一处编辑带来收益。

研究问题：

> 在固定模型、Token 和候选数量下，可验证局部编辑契约能否比自由改写和普通 JSON 输出产生更多正确且有静态收益的优化？

## 3. 核心创新概述

【候选创新】提出**效应绑定的局部编辑契约**：LLM 的每个优化动作必须同时说明修改位置、适用前提、参数化动作、预期证据、验收条件和失败定位。

它不是普通 JSON，因为系统会执行这些字段：

```json
{
  "target": {"function": "dot", "region": "loop:L1"},
  "preconditions": ["trip_count_known", "no_loop_carried_dependency"],
  "action": {"type": "set_unroll_count", "value": 4},
  "expected_evidence": ["loop_unrolled", "ir_instruction_delta_lt_0"],
  "semantic_checks": ["compile", "unit_tests", "ubsan"],
  "failure_scope": {"field": "action.value", "fallback": 2}
}
```

## 4. 输入、处理和输出

### 4.1 输入

- 原始 C/C++ 函数；
- 固定编译命令和优化目标；
- 允许的编辑动作清单；
- 简短的静态分析结果；
- 当前轮编译或测试反馈。

### 4.2 处理

1. 执行器解析程序并产生合法编辑位置；
2. LLM 选择一个位置并生成编辑契约；
3. 模式检查器验证字段和值域；
4. 前提检查器拒绝明显不满足的动作；
5. 执行器只修改契约指定位置；
6. 依次编译、测试、检查静态收益；
7. 失败时只把 `failure_scope` 指定字段返回给 LLM 修复。

### 4.3 输出

- 优化后的程序；
- 完整编辑契约；
- 编译、测试和静态指标证据；
- 接受、拒绝或局部修复决定；
- Token、工具调用和墙钟时间记录。

## 5. 数据流

```text
源码 + 合法编辑位置
        ↓
LLM 生成局部编辑契约
        ↓
Schema 与前提检查
        ↓
确定性执行器修改指定位置
        ↓
编译 → 测试 → IR/代码大小评价
        ↓
接受 / 拒绝 / 仅修复失败字段
```

## 6. 与现有方法发生本质变化的步骤

自由改写的最小决策单元是“整段代码”；普通结构化输出的决策单元是“一个 JSON 建议”；本方法的最小决策单元是“可由工具执行并能定位失败字段的效应绑定动作”。

只有当该绑定在消融实验中提高有效优化率，才可以保留为研究贡献。

## 7. 小白化例子

原程序有一个循环。自由改写让 LLM 重写整个函数，可能顺便改变边界条件。普通 JSON 只写“把循环展开 4 次”，但没有确认循环是否存在跨迭代依赖。

编辑契约先要求依赖检查通过，再让执行器将展开因子设为 4。如果编译器报告代码变大且静态指标没有改善，系统只把展开因子改为 2，不重新生成整个函数。

## 8. 可检验研究问题

- RQ1：编辑契约能否提高编译和测试通过率？
- RQ2：编辑契约能否提高固定预算下的有效优化率？
- RQ3：前提字段、预期证据和失败定位分别贡献多少？
- RQ4：收益是否只是由输出更短或动作空间更小造成？
- RQ5：契约在未见程序家族上是否仍有效？

## 9. 可验证假设

- H1：完整契约的有效优化率高于自由改写和普通 JSON。
- H2：完整契约获得首次有效优化所需 Token 更少。
- H3：去掉前提检查后，测试失败率或无效动作率上升。
- H4：去掉失败定位后，修复轮数和无关代码改动增加。

## 10. 论文贡献候选

1. 提出效应绑定的局部编辑契约，将动作、前提、证据和失败定位统一为可执行对象；
2. 提出局部失败修复流程，避免每轮重写完整程序；
3. 在等模型、等候选和等 Token 预算下验证契约对有效优化率和成本的贡献。

## 11. 风险与降级

- 若普通 JSON 已达到同等效果：降级为工程执行器；
- 若动作空间太小：增加参数化循环、内联和属性动作，但不开放自由重写；
- 若静态收益与运行时间不一致：把静态指标用于筛选，只对 Top-1 计时；
- 若前提分析难实现：首版只使用编译器可直接报告的前提；
- 若不同模型差异过大：固定主模型，并用第二模型仅复核方向。

## 12. 可证伪条件

完整契约不能在同预算下提高有效优化率、去掉核心字段无影响、或者所有收益都能由输出长度解释时，核心主张被否定。

## 13. 一个核心创新与两个支撑创新

三个创新共同回答同一研究问题，但承担不同职责：核心创新改变 LLM 的最小决策单元，支撑创新一决定动作是否适用和是否生效，支撑创新二决定失败后如何低成本修复。

### 13.1 核心创新：效应绑定的局部编辑契约

【论文事实】结构化变换、编译器 Hint 和优化意图已经被近期工作研究，因此“让 LLM 输出 JSON”不能作为创新。

【合理推导】普通结构化建议没有强制把修改范围、动作前提、预期编译效应和验收条件绑定为同一个可执行对象。

【候选创新】LLM 的每个优化动作必须同时说明修改位置、适用前提、参数化动作、预期证据、验收条件和失败定位。

- 输入：合法编辑位置、允许动作、程序摘要和优化目标；
- 处理：生成契约、模式检查、确定性执行和证据验收；
- 输出：候选程序、完整契约、证据链和接受或拒绝决定；
- 本质变化：最小决策单元从文本建议变为可执行、可验收的效应绑定动作；
- 专属消融：自由改写、等长度普通 JSON、完整契约；
- 专属指标：有效优化率、契约执行成功率、无关修改行数；
- 证伪条件：普通 JSON 在相同动作空间和输出长度下达到同等结果。

### 13.2 支撑创新一：前提—预期证据的双向可执行验证

【论文事实】编译、测试、验证器和 compiler remark 已被用于反馈或验收。

【合理推导】“程序能编译”不能证明动作在当前程序上适用，也不能证明编译器产生了 LLM 预期的优化效应。

【候选创新】执行前由前提检查器验证依赖、值域和目标位置；执行后由效应检查器验证 optimization remark、IR 差异或代码大小是否满足声明。

- 输入：编辑契约、静态分析结果和执行后编译证据；
- 处理：前提检查、动作执行、预期效应检查；
- 输出：ACCEPT、REJECT_PRECONDITION 或 REJECT_EFFECT；
- 本质变化：验证从“能否编译”扩展为“动作是否适用且是否产生声明效应”；
- 专属消融：删除前提检查、删除预期证据检查、解除两者与动作的绑定；
- 专属指标：不适用动作率、无效动作率、预期效应命中率；
- 证伪条件：删除任一检查不影响测试通过率、有效优化率或无效动作率。

### 13.3 支撑创新二：失败责任定位与字段级局部修复

【论文事实】多轮编译反馈能够帮助 LLM 修复生成错误。

【合理推导】失败后重新生成完整程序会引入无关修改，也无法判断动作位置、前提还是参数造成失败。

【候选创新】把编译、测试和收益失败映射到契约字段，只允许修改被归责字段及依赖字段。

- 输入：失败证据、契约字段和字段依赖关系；
- 处理：失败分类、责任映射、受限重生成和重新验收；
- 输出：责任字段、修复字段集合、新契约和修复结果；
- 本质变化：修复单元从完整候选变为具有责任边界的字段集合；
- 专属消融：完整重生成、无责任定位的局部修复、带责任定位的字段级修复；
- 专属指标：修复 Token、首次有效优化轮数、无关改动、错误复发率；
- 证伪条件：责任定位不能降低修复成本，或字段边界阻止必要的跨字段修复。

### 13.4 统一因果链与假设

局部编辑契约生成 → 前提检查 → 确定性执行 → 预期证据检查 → 失败归责 → 字段级修复。

- H1：完整契约相对等长度普通 JSON 提高固定预算有效优化率；
- H2：双向验证相对仅编译测试降低不适用动作率和无效动作率；
- H3：字段级修复相对完整重生成减少修复 Token 和无关改动；
- H4：三个创新联合使用时的提升不能由更短输出、更多知识或更多候选解释。
