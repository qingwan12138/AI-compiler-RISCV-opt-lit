# 可验证结构化编辑框架：预实验 Demo

## 1. Demo 目标

在 1—3 天内判断：完整编辑契约是否比自由改写和普通 JSON 更容易产生可编译、测试正确且 IR 指标改善的候选。

## 2. 最小规模

- 10 个 C 函数；
- 3 种方法：自由改写、普通 JSON、完整契约；
- 每方法每函数 3 个候选；
- 共 90 个候选；
- 不训练模型，不运行强化学习；
- 只对每方法的最终 Top-1 做运行时间复核。

## 3. 工具

- Clang/LLVM；
- `clang`、`opt`、`llvm-size`；
- 程序自带测试或输入输出差分脚本；
- 可选 `-fsanitize=undefined,address`；
- 一个固定 LLM。

## 4. Demo 动作集合

只允许：循环展开因子、内联属性、向量化提示和两个安全代数简化动作。所有动作必须能被一个简短执行器确定性应用。

## 5. 步骤

1. 用 `clang -O0 -S -emit-llvm input.c -o baseline.ll` 生成基线 IR；
2. 用固定测试输入记录基线输出；
3. 为程序标注合法编辑位置；
4. 使用三种协议分别生成 3 个候选；
5. 执行编辑并保存原始响应和最终代码；
6. 编译候选，记录诊断类别；
7. 运行全部测试和可选 Sanitizer；
8. 统计优化前后 IR 指令数和目标代码大小；
9. 计算三个主要比例；
10. 对每种方法的 Top-1 预热 3 次、运行 10 次复核。

## 6. 成功标准

进入完整实验至少满足：

- 完整契约有效优化率高于普通 JSON；
- 完整契约没有增加平均 Token；
- 失败定位能让至少一部分候选只修改一个字段后恢复；
- 观察到的提升不是只来自一个函数。

这些标准是继续/停止门槛，不是预设论文结论。

## 7. 失败后的处理

- 若三种方法编译率都接近 100%：增加更容易出错的参数化动作；
- 若均无静态收益：从 `-O0` 改为在固定 `-O2` 基线上做局部动作；
- 若普通 JSON 已最好：停止将该方向作为创新，把契约保留为执行器；
- 若测试大量失败：缩小动作空间并加强前提检查；
- 若计时噪声大：只报告静态结果，并明确性能尚未验证。

## 8. Demo 输出

- `tasks.csv`：任务和测试说明；
- `candidates.jsonl`：模型响应和契约；
- `results.csv`：编译、测试、静态收益和成本；
- `summary.md`：三个方法的配对结果、失败类型和是否继续。

## 9. 最小结论模板

> 在 10 个函数、每任务 3 个候选和相同模型预算下，完整契约在编译率、测试率和有效优化率上的结果分别为……。相对普通 JSON 的差异为……；失败定位使……个候选通过局部修复恢复。该结果仅用于判断是否扩大实验，不支持新颖性或真实运行时间结论。

## 10. 三创新点分阶段预实验

统一设置：从 PolyBench、cBench 或 LLVM test-suite 选取 20 个可独立编译函数；固定一个 LLM、LLVM/Clang 版本、优化级别和提示；每任务最多 5 个候选；所有候选编译、测试并测静态指标，仅对每种方法 Top-1 做运行时间复核。

### 10.1 阶段一：验证核心创新

1. 为每个函数标注相同的合法动作空间；
2. 运行自由改写、等长度普通 JSON、完整效应绑定契约；
3. 记录有效优化率、契约执行成功率和无关修改行数；
4. 若完整契约不优于普通 JSON，则停止把核心契约作为研究创新。

### 10.2 阶段二：验证支撑创新一

1. 在同一批契约上分别关闭前提检查、关闭预期证据检查、全部开启；
2. 前提检查使用循环依赖、目标位置和值域等可直接获得的信息；
3. 预期证据使用 optimization remark、IR 指令差和代码大小；
4. 比较不适用动作率、无效动作率和预期效应命中率；
5. 若删除检查没有退化，该检查降级为工程模块。

### 10.3 阶段三：验证支撑创新二

1. 收集阶段一和阶段二中的编译、测试与无收益失败；
2. 分别采用完整重生成、无责任定位局部修复和责任字段修复；
3. 每个失败最多修复 2 轮，固定总 Token 上限；
4. 比较修复 Token、无关修改、错误复发和首次有效优化轮数；
5. 若责任修复无法降低成本或阻碍必要修改，则该支撑创新被否定。

### 10.4 三阶段最终输出

- 核心创新对比表；
- 双向验证消融表；
- 修复策略对比表；
- 20 个任务的逐候选证据和失败归责记录；
- 三项创新分别继续、降级或放弃的结论。
