# 文献证据矩阵与创新碰撞检查

> 分析日期：2026-07-19
>
> 证据说明：本文件以本地逐篇阅读总结为主要证据；在线补检仅用于发现近邻。没有完成可复现系统综述，因此所有新方向均称为【候选创新】。

## 1. 证据分层规则

- 【论文事实】：本地总结明确记录的论文方法、结果或局限。
- 【合理推导】：由多篇论文共同边界推出，但尚未被新实验验证。
- 【候选创新】：为研究空白设计的新机制，不代表已经确认新颖。

## 3. 2026 年最新碰撞信号

### 3.1 Agentic Code Optimization via Compiler-LLM Cooperation

【论文事实】该 2026 年预印本包含多抽象层优化 Agent、编译器工具、测试生成 Agent、引导 Agent，并研究在多个抽象层之间分配计算预算。

影响：框架二不能声称“首次做预算分配”。候选边界必须缩小为：**对单次反馈的反事实决策变化进行估计，并在同一阶段内主动选择或停止**。

### 3.2 Generative Compilation

【论文事实】2026-07-15 公开的工作研究在自回归生成过程中提供在线编译反馈，而不是生成结束后再反馈。

影响：生成期编译反馈已出现直接近邻。框架一不能把“边生成边验证”作为创新，必须强调局部编辑契约同时绑定前提、预期效应和失败定位。

### 3.3 AI Coding Agents Need Better Compiler Remarks

【论文事实】该 2026 年工作指出现有 optimization remark 对 Agent 含糊，并通过更精确、结构化的分析信息提高小模型能力。

影响：框架二不能只做“摘要日志”或“结构化 remark”。需要比较精确反馈与价值选择的独立贡献，并把结构化精确 remark 设为强基线。

### 3.4 SemOpt

【论文事实】该工作使用规则分析和检索指导 LLM 发现、生成并验证代码优化。

影响：框架三不能把“检索历史模式”称为创新；需要证明失败边界、反例失效和误拦截恢复是普通规则/RAG 不具备的机制。

## 4. 框架一碰撞检查

| 可能主张 | 是否已有近邻 | 处理方式 |
|---|---|---|
| LLM 输出 JSON | 是，结构化输出普遍存在 | 不主张创新 |
| LLM 生成规则或变换器 | 是，Code the Transforms | 作为近邻基线 |
| LLM 插入安全 Hint | 是，HintPilot | 不以换成 LLVM/Clang 为创新 |
| 高层意图到 IR 变换 | 是，IntOpt | 缩小到局部编辑对象 |
| 生成中调用编译器 | 是，Generative Compilation | 不主张首次在线反馈 |
| 动作、前提、证据和失败定位绑定 | 当前未发现完全同构工作 | 保留为候选创新；继续检索 contract-based program repair |

结论：证据充分度中，创新碰撞风险高，适合作为保底或执行器。

## 5. 框架二碰撞检查

| 可能主张 | 是否已有近邻 | 处理方式 |
|---|---|---|
| 多轮编译反馈 | 是 | 作为基线 |
| 精确结构化 remark | 是 | 设置强基线 |
| 多层计算预算分配 | 是 | 不主张创新 |
| 根据错误阶段选择工具 | 相邻工作已有 | 设置固定阶段规则强基线 |
| 预测反馈是否改变下一决策 | 当前未发现直接编译优化近邻 | 保留为候选机制 |
| 单位 Token/工具成本的有效优化价值 | 通用 Agent 路由相邻，编译优化证据有限 | 保留但降低新颖性置信度，补检索 value-of-information tool routing |

结论：证据充分度中高，碰撞可通过严格限定“反事实决策变化”处理，是当前唯一推荐主线。

## 6. 框架三碰撞检查

| 可能主张 | 是否已有近邻 | 处理方式 |
|---|---|---|
| 成功案例 RAG | 是，ECO、SBLLM、SemOpt | 作为强基线 |
| 保存失败日志 | 是，常见 Agent 能记录轨迹 | 不主张创新 |
| 拒绝当前错误策略 | 是，GraphGlue | 区分当前任务拒绝与跨任务负证据 |
| 无条件失败黑名单 | 工程上常见 | 作为消融基线 |
| 适用前提 + 反例条件 + 失效规则 | 当前未发现直接同构编译优化工作 | 保留为候选创新 |
| 测量误拦截并自动撤销 | 当前证据较少 | 作为关键实验，而不是默认有效 |

结论：证据充分度中，直接撞车较少，但需要跨程序家族数据才能证明，不如框架二快速。

## 7. 三框架重复关系检查

- 框架一决定“LLM 可以输出什么动作”；
- 框架二决定“下一步值得获取什么反馈”；
- 框架三决定“过去什么失败应该限制当前动作”。

三者可以串联，但不能把整套组合一次性作为一个创新。每个框架的完整实验只改变一个核心机制。

## 8. 证据最强与最弱方向

- 证据最强：反馈边际收益递减、固定多轮成本高，因此需要预算公平的反馈选择实验。
- 证据最弱：带边界负证据是否能跨程序迁移，目前多为合理推导，必须以误拦截率和失效实验补足。
- 碰撞最大：结构化编辑、意图、Hint 和生成期编译反馈。

## 10. 人工确认项

1. 第一轮使用本地开源模型还是已有 API 模型；
2. 可用 LLVM/Clang 版本；
3. 是否已有稳定测试输入和计时脚本；
4. 是否能获得 LLM 的准确 Token 使用量；
5. 论文最终更强调有效优化质量还是单位成本收益。

## 12. 最终边界结论

当前可以谨慎主张的不是“新的 LLM 编译优化系统”，而是三种待实验验证的机制：

1. 将局部编辑、适用前提、预期证据和失败定位绑定为一个可执行契约；
2. 用反事实决策变化和成本联合决定下一条反馈及停止时机；
3. 用带适用、反例和失效边界的负证据减少跨任务重复失败。

任何一项若不能在同模型、同任务、同预算下优于对应强基线，都应降级为工程组件。
