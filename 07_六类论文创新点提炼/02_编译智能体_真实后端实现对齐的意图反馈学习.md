# 类别二：LLM 编译智能体——优化意图的逐层落地审计

> 审阅结论：保留“意图”这个入口，但把创新中心从泛泛的多平台反馈改为“意图是否真的被后端实现”的可审计链条。
> 文献范围：本类 46 篇逐篇阅读笔记；重点参考 Compiler-R1、Meta LLM Compiler、ACCLAIM、IntOpt、CompilerGPT、Code the Transforms、ECO、IntrinTrans 等。
> 证据强度：高；其中个别源材料受限条目不承担关键论证。
> 日期：2026-07-15

## 1. 先说结论

现有 LLM 编译智能体已经会生成优化、调用编译器、读取报错、反复修改。真正欠缺的是一张“审计账单”：

> LLM 说自己要减少访存，IR 是否真的减少了访存？机器码是否仍保留这个变化？运行时间变快是否真的由该变化造成？

推荐创新点名称：**优化意图的 IR—机器码—运行效应逐层落地审计与归因反馈**。

## 2. 为什么原来的写法需要收窄

“LLM Agent + 编译器反馈”“多智能体协作”“优化意图分解”“跨 ISA 模型”都已有直接先例：

- Compiler-R1 已把工具交互和 RL 用于编译优化；
- ACCLAIM 已做源码、IR、汇编多层协作；
- IntOpt 已把优化意图显式化；
- Meta LLM Compiler 同时覆盖 x86-64 和 ARM，因此不能写“所有工作都只有一个 ISA”；
- CompilerGPT、IntrinTrans、AutoChip 等已证明编译/测试反馈能促进修正。

因此，“增加一个后端 Agent”或“加入真实运行反馈”还不够新。关键是建立可核查的**意图落地链**，把正确性、实现性和收益性拆开。

## 3. 三种经常被混为一谈的成功

| 层次 | 要回答的问题 | 推荐证据 |
|---|---|---|
| 语义合法性 | 新程序是否仍做同一件事 | Alive2、差分测试、sanitizer |
| 意图实现性 | 声称的优化是否在 IR 和机器码中真实发生 | IR diff、optimization remarks、MIR/汇编差分、静态计数 |
| 性能收益性 | 已发生的变化是否让目标机器更快/更省能 | 真实硬件重复测量、PMU、统计检验 |

例如“编译成功且快了 5%”仍不能证明“减少访存”这个意图成功：加速可能来自另一个意外变化，也可能来自测量噪声。

## 4. 推荐创新点

### 4.1 一句话解释

让智能体每次优化都先写一张可检查的承诺单，再由编译器工具逐层核对；如果承诺与实际不一致，就把“在哪一层失真、为什么失真”反馈给智能体，而不是只返回成功或失败。

### 4.2 意图契约

每个候选必须输出结构化意图：

```yaml
intent: reduce_memory_traffic
scope: loop_L3
expected_ir_effect:
  loads: decrease
  stores: unchanged
expected_machine_effect:
  spill_loads: not_increase
  vector_width: increase_or_same
forbidden_side_effects:
  - new_undefined_behavior
  - code_size_growth_over_10_percent
```

结构化生成只保证格式合法，不保证语义正确；XGrammar 等工作已经说明了这一边界，所以后续确定性检查不可省略。

### 4.3 四步审计链

1. **语义闸门**：等价验证或差分测试，不通过即拒绝；
2. **IR 落地检查**：用 IR 差分和分析 Pass 判断预期结构变化是否发生；
3. **后端落地检查**：用 optimization remarks、MIR/汇编和寄存器压力信息判断变化是否在 lowering 中保留；
4. **真实效应归因**：通过成对运行与最小反事实版本，判断收益是否与该变化相关。

输出不再是一个分数，而是四类标签：

- `valid_and_realized`：语义正确，意图落地；
- `valid_but_erased`：IR 中出现，但后端消掉了；
- `valid_but_counterproductive`：意图落地，却在目标硬件上变慢；
- `invalid_or_unverifiable`：语义错误或无法确认。

### 4.4 学习闭环

训练或提示更新时分别使用：

- 合法性奖励；
- 意图落地奖励；
- 性能奖励；
- 自述忠实度奖励。

这避免模型通过“说一个正确理由、实际做另一件事”获得奖励，也避免把编译成功误当成优化成功。

## 5. 与最近工作的差别

| 代表工作 | 已覆盖 | 本方向不重复的部分 |
|---|---|---|
| IntOpt | 意图表达、细化与实现 | 检查意图在 IR 与机器码层是否真实落地 |
| ACCLAIM | 多层 Agent | 层与层之间采用可执行契约，不只传自然语言建议 |
| Compiler-R1 | 工具交互与 RL | 将奖励拆成合法性、实现性、收益性和忠实度 |
| CompilerGPT / IntrinTrans | 编译与测试反馈修正 | 返回失真层级与证据，而非原始报错文本 |
| Code the Transforms | 生成可执行变换器 | 审计变换器声称的效果是否真实发生 |

## 6. 最小可行实验

### 6.1 任务

选择 4 类容易量化的意图，每类 20–30 个函数：

- 减少访存；
- 消除冗余计算；
- 促进向量化；
- 降低分支或控制流复杂度。

先使用 x86 或现有本机完成方法验证，再在 RISC-V 上验证后端失真是否更明显。跨平台不是方法成立的必要前提。

### 6.2 基线

1. 一次性 LLM 优化；
2. 仅编译错误反馈；
3. 编译 + 测试 + 运行时间反馈；
4. 完整逐层审计反馈。

### 6.3 指标

- 语义正确率；
- 意图真实落地率；
- “自述与实际一致”的忠实度；
- 后端擦除率；
- 真实性能提升率；
- 达到合格候选所需的平均重试次数。

## 7. 可证伪假设

主假设：逐层审计反馈能显著提高“语义正确且意图真实落地”的候选比例，并减少无效重试。

方向不成立的信号：

- 意图类别无法由确定性工具稳定检测；
- 完整审计与“编译+运行时间”基线没有显著差异；
- 绝大多数性能变化无法用有限反事实归因；
- 审计成本高于减少的重试成本。

## 8. 论文边界

可主张：提出意图契约、逐层落地标签、基于证据的反馈学习和对应 benchmark。

不可主张：首次使用编译器反馈、首次多 Agent 编译、首次意图驱动优化、首次跨 ISA 编译模型。

## 9. 综合判断

| 维度 | 评分（5 分） | 说明 |
|---|---:|---|
| 新颖性 | 4.3 | 新意在“可审计落地”，不是 Agent 数量 |
| 可实现性 | 4.0 | LLVM IR、remarks、MIR/汇编工具链可支持 |
| 实验清晰度 | 4.5 | 三类成功可分别测量 |
| RISC-V 相关性 | 4.0 | RVV lowering 可提供典型失真案例 |
| 风险 | 中 | 最大难点是自动检测意图和性能归因 |

最终建议：作为类别二主创新。它既能独立成篇，也可为其他类别提供审计方法，但本文件不依赖任何总框架才能成立。
