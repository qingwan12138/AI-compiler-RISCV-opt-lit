# 类别五：RISC-V RVV 后端——反事实微基准驱动的代价模型修补闭环

> 审阅结论：原方向基本成立，但必须把“发现性能问题”推进到“形成可验证的编译器代价模型补丁”，并严格限定 QEMU 的作用。
> 文献范围：本类 6 篇逐篇阅读笔记；重点参考 RVV 自动向量化分析、TSVC 覆盖研究、Closer in the Gap、RVV MetaSchedule、LLVM 后端社区讨论和 RVV Intrinsic Specification。
> 证据强度：中高；其中两篇原文受限，不能引用其具体数值。
> 日期：2026-07-15

## 1. 先说结论

已有研究已经发现 RVV 自动向量化在 predication、stride load、LMUL/VL 选择等方面存在代价模型盲区。单纯再做一次 benchmark、再报告“这里慢了”不够形成方法创新。

推荐创新点名称：**从后端负优化到 LLVM TTI/调度参数补丁的反事实微基准自校准闭环**。

## 2. 已有工作与真正缺口

| 已有工作 | 已经做到 | 尚未完成 |
|---|---|---|
| RVV autovectorization / TSVC 分析 | 统计覆盖率和性能差距 | 未自动定位到具体代价决策并修补 |
| Closer in the Gap | 用微基准与应用揭示 predication、stride、LMUL 等盲区 | 诊断后仍主要依赖人工修改模型 |
| RVV MetaSchedule | 在 RVV 上用真实测量搜索 tensor 调度 | 生成的是程序调度，不是通用 LLVM 后端补丁 |
| LLVM RISC-V backend 社区 | 有 target feature、scheduler/tune 和测试机制 | 缺少从硬件反例自动产生可审查参数更新的闭环 |

LLVM 已具备 RISC-V 调优特性、调度模型和向量化成本模型接口，因此研究重点应是**如何可靠地产生更新证据**，而不是另建一个与编译器脱节的黑盒预测器。

## 3. 推荐创新点

### 3.1 一句话解释

当编译器生成的 RVV 代码比标量或另一种 RVV 方案更慢时，系统自动构造“只改一个决策”的成对程序，在真实硬件上反复测量，确认是哪项成本估错了，然后生成一条带适用条件、置信区间和回归测试的代价模型修补建议。

### 3.2 为什么必须用反事实对照

一个完整程序变慢可能同时涉及：

- 向量化与否；
- mask 还是 scalar epilogue；
- LMUL；
- `vl` 设置位置；
- contiguous/stride/gather load；
- unroll 因子；
- 寄存器 spill；
- 代码尺寸和缓存。

直接比较 `-O3` 与 `-O2` 无法确定原因。系统应构造只改变一项选择的 A/B 变体，并确保语义、数据布局和其余编译选项一致。

### 3.3 闭环流程

1. 从 TSVC、应用和编译 remarks 中收集 missed optimization 与负优化样本；
2. 将样本归因到一个候选决策：mask、stride、LMUL、VL、unroll 等；
3. 自动生成最小微基准和单因素 A/B 变体；
4. 交错执行、固定环境、重复测量，采集运行时间和可用 PMU 事件；
5. 判断现有 TTI/调度模型的预测排序是否与真实排序相反；
6. 学习或拟合带上下文的成本修正，例如 `cost(strided_load, stride, LMUL, CPU)`；
7. 生成候选 TableGen/TTI 参数补丁或外部可插拔 cost override；
8. 在未参与拟合的完整 benchmark 上验证；
9. 若出现新负优化，则把它作为反例重新收紧适用条件。

### 3.4 输出必须可审查

每个修补建议至少附带：

- 对应 CPU、ISA 扩展和编译器版本；
- 最小复现程序；
- 旧模型预测、新模型预测、实测值；
- 置信区间和重复次数；
- 适用特征与不适用边界；
- LLVM `lit`/benchmark 回归用例；
- 对其他 CPU 的影响检查。

这样输出才可能进入真实编译器，而不是停留在论文模型里。

## 4. QEMU 的严格边界

[QEMU 官方文档](https://www.qemu.org/docs/master/system/invocation.html)明确说明其仿真并非 cycle accurate，指令计数通常也与真实性能缺少可靠相关性。因此：

QEMU 可以用于：

- 编译和执行功能正确性；
- 多 VLEN/ISA 配置覆盖；
- 指令类型、代码尺寸等静态检查；
- 早期筛除明显错误候选。

QEMU 不可用于：

- 宣称 RVV 真实性能加速；
- 校准延迟、吞吐、缓存或 spill 成本；
- 代替真实 CPU 比较两个代价模型。

若没有真实 RVV 硬件，本方向只能完成工具原型，不能完成核心实验。

## 5. 最小可行实验

### 5.1 第一阶段只选三个盲区

- predication 与 scalar epilogue；
- contiguous 与 strided load；
- LMUL 选择与寄存器压力。

### 5.2 硬件要求

- 最低：1 台真实 RVV CPU，完成闭环可行性；
- 推荐：2 台微架构不同的 RVV CPU，检查补丁是否只适用于单机；
- x86/ARM 只作方法外部对照，不是必需。

### 5.3 基线

1. LLVM 默认 cost model；
2. 只做 benchmark 报告、不修改模型；
3. 黑盒 ML 预测器；
4. 无上下文的统一成本常数；
5. 本文的反事实、上下文条件化修补。

### 5.4 指标

- 模型排序准确率；
- 向量化负优化率；
- 完整 benchmark 的几何平均加速；
- 产生一个有效补丁所需测量数；
- 补丁跨程序、跨 CPU 的回归数量；
- 编译时间开销；
- 可上游化程度：是否有最小复现和稳定回归测试。

## 6. 可证伪假设

主假设：单因素反事实微基准能比整程序黑盒训练更少测量地定位代价排序错误，并形成在未见程序上减少负优化的上下文修补。

应停止或降级的情况：

- 微基准排序与完整程序排序长期不一致；
- PMU/时间测量噪声无法区分候选；
- 修补在训练程序上有效却在多数未见程序上回归；
- 不同 RVV CPU 的成本差异无法用 target tune 参数隔离。

## 7. 论文边界

可主张：自动化单因素反例生成、从证据到 TTI/调度补丁的闭环、带范围的 RVV 成本修补。

不可主张：首次发现 RVV cost model 有问题、首次在 RVV 上做真实测量、用 QEMU 证明真实性能、一次修补对所有 RVV 处理器通用。

## 8. 综合判断

| 维度 | 评分（5 分） | 说明 |
|---|---:|---|
| 新颖性 | 4.3 | 从诊断推进到可审查补丁闭环 |
| 可实现性 | 3.8 | 工具链可做，但真实硬件是硬条件 |
| 实验清晰度 | 4.8 | A/B 反事实与未见程序回归清楚 |
| RISC-V 相关性 | 5.0 | 直接改进 RVV 后端 |
| 风险 | 中高 | 硬件、PMU 和上游工程细节决定成败 |

最终建议：类别五最强、最工程化的主创新候选。只要能获得至少一台稳定的 RVV 实机，应优先推进。
