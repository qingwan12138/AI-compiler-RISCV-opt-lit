论文题目：**Interleaving Large Language Models for Compiler Testing**

作者：Yunbo Ni、Shaohua Li

发表时间：2025

发表平台：Proceedings of the ACM on Programming Languages，Volume 9，Issue OOPSLA2，Article 301，页 815–841

论文链接或编号：DOI `10.1145/3763079`；arXiv `2508.18955`

> 本文档依据论文正文阅读整理。论文事实、阅读后的分析和后续建议分开描述。

## 1. 研究背景

本文研究大语言模型（Large Language Model，LLM）辅助的编译器测试。编译器仍会出现崩溃和错误编译，而随机程序生成、变异测试和基于规则的生成器长期承担大规模测试任务。论文指出，现有 LLM 编译器测试方法有两个实际困难：生成程序常常过于简单或无效，且每个测试样例都调用 LLM 会带来较高的计算和经济成本（第 1 节）。

论文以 Fuzz4All 和 WhiteFox 作为相关 LLM 测试方法的背景。正文报告的对比观察是：Fuzz4All 生成的 C 程序对 GCC 的有效率为 37.26%，平均长度约 18 行；WhiteFox 生成的程序平均约 21 行。论文还指出，现有 LLM 工具在其已报告的 GCC/LLVM 问题中没有发现 C 编译器的错误编译问题。传统的 Csmith 可以生成大量且高有效率的程序，但其预定义规则可能使搜索空间趋于饱和（第 1、7 节）。

因此，论文希望把 LLM 擅长的代码理解和变换能力用于离线构建高质量代码积木，再把高吞吐量的程序组合交给非 LLM 的在线合成过程，以同时改善测试程序质量、复杂度和生成成本。

## 2. 论文要解决的问题

### 2.1 生成程序质量与复杂度不足

编译器错误编译往往需要复杂控制流、数据依赖、函数调用和优化特性之间的交互。单次自然语言提示生成的程序可能存在语法错误、运行时未定义行为或过短，导致它们只能用于有限的崩溃测试，难以可靠地暴露错误编译。

### 2.2 LLM 在线调用成本过高

大规模 fuzzing 需要短时间生成大量输入。论文报告 Fuzz4All 在 24 小时内约生成 16,000 个有效 C 程序，而传统工具可以达到更高数量级。若让 LLM 参与每一轮测试程序生成，计算和 API 成本会成为瓶颈。

### 2.3 组合代码时保持有效语义

仅把多个独立函数放进同一个文件，并不会形成足够的跨函数交互。论文要解决的是：如何利用已验证函数构造函数调用和全局变量依赖，同时尽量保持种子程序的运行语义不变。

> 本文主要研究：如何用 LLM 离线生成有效、富有特征的 C 函数积木，并在无需继续调用 LLM 的在线阶段迭代合成复杂测试程序，以高效发现 GCC/LLVM 的编译器缺陷。

## 3. 核心方法概述

LegoFuzz 将编译器测试拆成离线代码数据库构建和在线迭代程序合成两个阶段。离线阶段用真实开源代码作为模板，提示 LLM 将复杂代码转换为单个、数值输入输出的 C 函数；随后用编译器、sanitizer、CompCert 和运行时 profiling 过滤无效函数。在线阶段只复用这些已经 profile 的函数，通过函数调用插入和全局变量共享建立依赖，在保持已观测运行值的条件下逐轮扩大程序。

```text
AnghaBench 真实 C 函数
        ↓
LLM 代码对齐变换（单函数、数值 I/O）
        ↓
编译/ASan/UBSan/MSan/TypeSan/CompCert 与运行时检查
        ↓
有效函数 + 输入/输出/表达式 profile 数据库
        ↓
随机选择种子函数和全局变量
        ↓
按 profile 选择表达式
        ↓
插入函数调用或共享全局变量（多轮）
        ↓
生成复杂 C 测试程序与 driver
        ↓
GCC/LLVM 多优化级别编译、执行和差分比较
        ↓
崩溃、错误编译或超时报告；用 C-Reduce 约简
```

LLM 的最终角色是生成可复用的编译器测试能力和测试程序构建数据库，属于 GENERATOR。它不是 pass、phase、flag 或规则选择器，也不是直接替换用户程序的优化器。编译器、sanitizer、profile 工具和差分执行器承担验证与测试反馈角色。

## 4. 实验框架与训练流程

本文不涉及模型预训练、SFT、PPO、GRPO 或强化学习训练，主要采用提示驱动的离线代码变换和在线程序合成。

### 4.1 离线代码数据库构建

1. 从 AnghaBench 的 146 个开源项目中抽取真实函数；项目包括 Linux、Redis 和 Nginx 等。
2. 使用预定义 prompt 指导 LLM 将程序变成一个独立函数，要求数值型输入输出、保留语义、无标准 I/O、避免未定义行为。
3. 使用 ChatGPT-4o-mini-2024-07-18，最大输出 token 为 512，temperature 为 0.7；论文也用 GPT-3.5-turbo 和 Qwen2.5 Coder 32B Instruct 做模型对比。
4. 对候选函数执行编译和多 sanitizer 检查；对随机输入发现运行时错误的样例丢弃。
5. 对通过样例收集输入、输出和每行表达式的运行时值，形成函数及 profile 的数据库条目。

### 4.2 在线迭代程序合成

1. 随机生成数值型全局变量。
2. 从数据库选取一个函数作为种子，并生成调用它的 driver。
3. 从目标函数的 profile 中选择表达式。
4. 随机决定是否合成；若合成，则插入未使用过的函数调用，或读写全局变量。
5. 对稳定表达式用等值表达式维持观测运行值，对不稳定表达式加入运行值为 0 的补偿项；全局写入使用 `g = g + (expr - value)` 形式。
6. 重复预定轮数 `N`，控制最终程序规模。

### 4.3 编译器 fuzzing 执行

对生成的程序使用 GCC 和 LLVM 的 `-O0`、`-O1`、`-Os`、`-O2`、`-O3` 编译。程序打印由函数返回值和全局变量构成的 checksum，跨编译器及优化级别比较输出；编译器崩溃、输出不一致或超时进入人工分析和 C-Reduce 约简。

## 5. 奖励函数、损失函数或关键公式

本文没有使用强化学习奖励函数，也没有模型训练损失函数。在线阶段的核心目标是：在已 profile 的运行值约束下插入新的依赖，使程序结构更复杂，同时保持测试输入的运行语义。

关键构造可以用以下纯文本形式概括：

```text
稳定表达式 e，运行值为 v：
    函数调用替换：e' = f(args) +/− 常量，使 e' 的运行值仍为 v
    全局变量读取：e' = g +/− 常量，使 e' 的运行值仍为 v
    全局变量写入：g = g + (e − v)，因为 e − v = 0，所以不改变当前观测值
```

其中“稳定”指 profile 在该位置只观察到一个运行值。该机制不是形式化语义等价证明；它依赖已采集输入、运行时检查和 profile 约束。论文中未明确说明一个能够覆盖所有可能输入的语义保证。

## 6. 实验设置

### 6.1 数据集来源

论文使用 AnghaBench，包含来自 GitHub 146 个开源项目的超过 1,040,000 个函数。离线处理后得到 553,246 个函数，约占原始函数的 53%。作者报告最常见的丢弃原因是违反数值 I/O 要求，invalid I/O function rate 为 14.2%。数据库函数平均约 30 行、3 个分支，多数函数少于 60 行和 10 个分支。

数据库构建成本为调用 ChatGPT-4o-mini 约 394 美元。论文明确说明，单独使用这些函数测试时未发现编译器 bug，因此后续合成依赖是必要的。数据泄漏风险的系统评估，论文中未明确说明。

### 6.2 模型与工具

| 项目 | 设置 |
|---|---|
| LLM 主模型 | ChatGPT-4o-mini-2024-07-18 |
| 主模型参数 | 最大 token 512，temperature 0.7 |
| 其他模型 | GPT-3.5-turbo、Qwen2.5 Coder 32B Instruct |
| 编译器 | GCC、LLVM；每日更新至最新版本，正文给出 commit 区间 |
| 优化级别 | `-O0`、`-O1`、`-Os`、`-O2`、`-O3` |
| 验证/检查 | ASan、UBSan、MSan、TypeSan、CompCert |
| 约简 | C-Reduce |
| 环境 | Ubuntu 20.04、AMD EPYC 7742 64 核、256 GB RAM |
| 资源限制 | 每个 fuzzing 进程 1 GB 内存、200 秒编译超时 |

### 6.3 对比方法

主要对比包括：直接使用数据库单函数、缩小后的 LegoFuzz 数据库、使用 Creal 数据库的 LegoFuzz、使用 LegoFuzz 数据库的 Creal、Fuzz4All、WhiteFox 和 Creal。对于 WhiteFox，论文只测量 LLVM 覆盖率，因为其生成 C++ 后转换为 LLVM IR。

### 6.4 评价指标

| 指标 | 含义 | 趋势 |
|---|---|---|
| Bug 数量 | 由报告状态、重复关系和维护者确认区分的编译器问题数 | 越多越好，但需看确认状态 |
| Crash | 编译器内部错误、断言失败或运行时失败 | 发现能力指标 |
| Miscompilation | 编译成功但生成结果错误 | 发现能力指标，通常更难检测 |
| Function Coverage | 覆盖的编译器函数比例 | 越大越好 |
| Line Coverage | 覆盖的编译器代码行比例/数量 | 越大越好 |
| Branch Coverage | 覆盖的编译器分支比例 | 越大越好 |
| Generation Time | 生成 10,000 个测试程序的时间 | 越小越好 |

## 7. 实验结果与结论

### 7.1 主要结果

LegoFuzz 共报告 GCC 和 LLVM 的 66 个问题：GCC 23 个、LLVM 43 个；其中 58 个（88%）被论文称为此前未知的新问题，56 个（85%）已被修复。表 1 的状态为：已确认 2 个、已修复 56 个、重复 8 个。表 2 显示 36 个为崩溃，30 个为错误编译。

### 7.2 覆盖率和生成速度

从 1,000 个随机种子函数生成 10,000 个程序后，GCC 的 LegoFuzz line coverage 为 39.5%，相对种子函数 27.0% 增加 110,945 行；LLVM 为 36.6%，相对种子函数 31.7% 增加 80,295 行。论文还报告，LegoFuzz 生成 10,000 个程序用时 193 秒，平均约 0.02 秒/程序；这只指程序生成时间，不是完整编译和执行时间。

### 7.3 与传统方法和其他 LLM 方法的比较

与 Fuzz4All、WhiteFox 和 Creal 的 10,000 个测试程序比较时，LegoFuzz 在覆盖率上更高。Fuzz4All 生成 10,000 个程序需要 12,121 秒，WhiteFox 需要 28,284 秒，分别约为 LegoFuzz 的 62 倍和 146 倍；Creal 需要 13,997 秒。论文报告 Fuzz4All 和 WhiteFox 没有发现 GCC/LLVM 错误编译问题，但这些结果依赖论文对已有报告的人工收集与分析。

### 7.4 消融实验

数据库规模增大时，GCC 和 LLVM 的 line coverage 均提高；使用 Creal 的原始数据库会降低 LegoFuzz 覆盖率，而把 LegoFuzz 数据库交给 Creal 也能提升 Creal 的覆盖率，说明数据库质量和在线合成策略都重要。

Qwen2.5 Coder 32B Instruct 生成的 10,000 个函数覆盖率高于 GPT-4o-mini，GPT-3.5-turbo 低于 GPT-4o-mini，说明 LLM 选择会影响离线数据库质量，但论文认为框架与具体模型松耦合。

当在线合成轮数 `N` 从 10 增至 200，程序最大长度超过 15,000 行；覆盖率在 `N=100` 后增长有限，GCC 覆盖率甚至下降。因此作者将 `N=100` 作为生成时间和覆盖率的折中配置。

### 7.5 案例分析

论文给出四类约简案例：GCC `-O3` 向量化相关崩溃；LLVM InstCombine 在内联后错误简化指针偏移导致错误编译；LLVM LoopVectorize 的新旧 VPlan cost model 不一致导致断言失败；GCC 循环迭代分析错误导致程序超时。原始触发程序规模约为 3,989–6,697 行、24–107 个函数，显示跨函数依赖和全局状态交互能触发单函数方法难以覆盖的编译器行为。

## 8. 主要创新点

### 8.1 创新点一：LLM 离线/在线解耦

现有 LLM fuzzing 常在每个生成循环中调用模型。LegoFuzz 只在离线阶段调用 LLM 生成代码积木，在线阶段复用数据库。实验中的生成速度和覆盖率结果支持该设计的工程价值，但它不是新的 LLM 训练算法。

### 8.2 创新点二：真实代码对齐的提示变换

论文不要求 LLM 从抽象描述直接生成百万级测试程序，而是把真实开源函数作为模板，并要求把复杂类型和多函数逻辑变换成单个数值 I/O 函数。该设计保留真实代码结构，同时让后续 profile 和组合更容易。论文报告其有效提取率超过 50%，而 Creal 对相应复杂例子的有效提取率为 5%。

### 8.3 创新点三：基于 profile 的迭代依赖合成

函数调用插入和全局变量共享使多个积木形成跨函数依赖；稳定表达式和 profile 值用于构造保持当前输入输出的替换。相比只做一次调用插入，论文实现了多轮合成和更丰富的依赖结构。

### 8.4 创新点四：面向真实编译器优化的测试能力

论文用 GCC/LLVM 崩溃、错误编译和覆盖率验证系统价值，并报告大量已修复缺陷。真正的贡献是测试生成器架构和组合机制，而不是“使用 LLM”本身。

## 9. 局限性

### 9.1 论文明确承认的局限

1. 当前实现主要支持数值函数签名；支持更多输入输出类型需要额外工程工作。
2. 当前在线合成粒度是函数级；论文提出未来可研究函数体直接合并等其他粒度。
3. prompt 对擅长自然语言指令的模型更有效，对专门代码模型可能需要调整。
4. 当前实现主要测试 C 编译器，迁移到 Rust 等语言仍需适配。
5. LLM 生成函数依赖 sanitizer、profile 和过滤；论文没有声称这些检查对所有未定义行为提供完备证明。

### 9.2 阅读后发现的潜在局限

1. 语义保持是基于有限输入 profile 的观测约束，不等同于对所有输入的形式化等价证明。
2. 论文的主要实验平台是 GCC 和 LLVM，跨架构、真实硬件和 RISC-V 后端的效果没有在本文中验证。
3. 数据库构建成本、模型版本和 prompt 可能影响复现；数据泄漏和训练语料重叠风险没有系统量化。
4. 生成时间很低，但完整测试成本仍包括编译、执行、超时处理和人工确认，不能把 193 秒解释为端到端测试时间。
5. 只用数值 I/O 和函数级组合可能遗漏依赖复杂 I/O、宏、并发、异常控制流或跨模块链接的编译器行为。

## 10. 阅读后的研究方向反思

LegoFuzz 最值得借鉴的是“昂贵的 LLM 生成”和“廉价的大规模组合”解耦，以及把 compiler feedback 前移到数据库构建阶段。对于 RISC-V 研究，直接把 GCC/LLVM 目标从 x86/通用平台替换为 RISC-V 并不足以构成充分创新；更有价值的是围绕 RVV、后端指令选择、ABI、寄存器分配和多目标代码生成设计架构特定的 profile、oracle 和依赖构造。

论文的核心贡献不能简单改写为“把 C 换成 RISC-V”：RISC-V 是目标 ISA，不是测试输入语言；必须明确要测的是 RISC-V 后端、LLVM MIR/汇编生成、模拟器差分，还是 RVV intrinsic 的语义边界。该工作更适合作为 GENERATOR/G4 的方法基线和测试工具模块，而不是直接作为优化算法或 Translator。

## 11. 可进一步尝试的研究方向

### 11.1 面向 LLVM RISC-V 后端的 profile 引导 fuzzing

#### 研究问题

如何让离线函数积木和在线依赖合成更集中地覆盖 RISC-V 指令选择、寄存器分配、压缩指令和 RVV lowering 路径。

#### 与原论文的区别

不只更换目标编译器，而是新增后端状态、MIR/汇编特征和跨优化级别的差分 oracle。

#### 可能的创新点

将后端诊断、指令序列特征和模拟器结果纳入 profile；区分合法汇编、汇编器接受但运行错误、以及语义差分三类反馈。

#### 实验框架

```text
真实 C/RVV 函数 → LLM 离线变换 → LLVM/RISC-V profile
→ 依赖合成 → LLVM MIR/汇编生成 → QEMU/Spike/硬件差分
→ 后端 bug 约简
```

#### 可行性

需要 LLVM RISC-V、QEMU 或 Spike、可重复的 RISC-V 工具链和覆盖率采集。

#### 主要风险

模拟器与真实硬件行为可能不同；RVV 配置和未定义行为会造成 oracle 不稳定。

### 11.2 多架构等价 checksum 与后端错误编译检测

#### 研究问题

如何用同一高层测试程序对 x86、AArch64 和 RISC-V 生成结果做可比的语义差分，同时避免把合法的未定义行为误报为后端 bug。

#### 与原论文的区别

原论文主要在 GCC/LLVM 编译器之间及优化级别之间比较输出；新方向增加跨 ISA 归一化和 ABI 处理。

#### 可能的创新点

设计定义良好的 C 子集、跨 ISA checksum 规范和失败样例自动分类。

#### 实验框架

```text
有效函数数据库 → 依赖合成 → 多目标编译
→ 原生/模拟器执行 → 归一化输出比较 → C-Reduce/后端定位
```

#### 可行性

可利用现有 LegoFuzz 组合逻辑，新增多工具链和跨架构执行环境。

#### 主要风险

ABI、浮点、并发和实现定义行为会混淆差分结果；测试子集过窄又会降低覆盖范围。

### 11.3 结合历史后端缺陷的 LLM 代码积木检索

#### 研究问题

历史 RISC-V/LLVM 后端缺陷能否指导 LLM 离线变换产生更容易触发特定后端路径的代码积木。

#### 与原论文的区别

原论文以真实开源代码和通用 prompt 为主；新方向将历史 bug、修复 patch 和后端组件标签加入检索与提示。

#### 可能的创新点

建立“后端症状—代码特征—可验证测试”的检索闭环，并测量新 bug 与已知 bug 的区分能力。

#### 实验框架

```text
历史 bug/patch/组件 → 检索上下文 → LLM 生成函数积木
→ sanitizer/profile → 依赖合成 → 目标后端 fuzzing
→ 新旧缺陷去重与约简
```

#### 可行性

需要公开 bug tracker、LLVM 修复记录和稳定的 RISC-V 后端构建环境。

#### 主要风险

检索可能造成测试集泄漏；重复发现旧 bug 不能等同于新颖性。

## 12. 与其他已读文献的关系

本轮 staging 只完成这一篇论文的正文阅读，因此没有另一篇“当前批次已读并确认”的论文可作横向事实比较。论文自身将 Fuzz4All、WhiteFox 作为 LLM 测试对比，将 Creal 作为真实代码与传统 fuzzing 的对比；LegoFuzz 的区别是离线 LLM 代码数据库、在线多轮依赖合成以及 Csmith-free 的组合流程。

按 Taxonomy v2 角色划分，本文属于 GENERATOR/G4，因为最终交付的是可复用的编译器测试/fuzzing 工具。它不是 SELECTOR：没有让 LLM 选择 pass 或 phase；也不是 TRANSLATOR：测试程序生成是服务于测试工具构建，而非优化用户程序。
