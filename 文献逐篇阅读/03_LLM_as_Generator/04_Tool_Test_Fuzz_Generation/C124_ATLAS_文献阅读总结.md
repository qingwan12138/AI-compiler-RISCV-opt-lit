# ATLAS 文献阅读总结

论文题目：**Unveiling Compiler Faults via Attribute-Guided Compilation Space Exploration**

作者：Jiangchang Wu、Yibiao Yang、Maolin Sun、Yuming Zhou

发表时间：2025

发表平台：2025 USENIX Annual Technical Conference（USENIX ATC ’25），Boston，pp. 1109–1125

论文链接或编号：[USENIX 官方论文页面](https://www.usenix.org/conference/atc25/presentation/wu-jiangchang)；[官方 PDF](https://www.usenix.org/system/files/atc25-wu-jiangchang.pdf)；DOI：论文正文未给出 DOI

建议 Taxonomy v2 分类：`GENERATOR / G4_Tool_Test_Fuzz`。理由是 ATLAS 输出的是可复用的编译器测试/变异工具能力，而不是由模型输出 pass、IR 或目标程序。该论文不包含 LLM；本分类建议不代表正式 taxonomy 登记。

## 1. 研究背景

编译器是系统软件构建的基础设施，编译器缺陷可能影响程序正确性、安全性、可靠性、性能和维护成本。论文关注的是编译器测试，而不是生成面向用户的优化程序。已有测试方法通常先生成或变异 C 程序，再配合优化级别和编译选项进行压力测试。

论文介绍的代表性方法包括 Csmith、YARPGen/YARPGen v2 和 Equivalent Modulo Input（EMI，保持给定输入下行为等价的变异测试）。这些方法能够产生大量测试程序，但编译选项通常以全程序为粒度应用。现代 GCC/Clang 同时支持作用于函数、变量或语句的属性，例如 `always_inline`、`noinline`、`aligned`、`noreturn` 和 SIMD 相关属性；属性可以改变特定代码元素的优化、代码生成或运行时语义。

论文的动机是：如果只改变全局编译选项，会遗漏“同一程序中不同函数/变量/语句采用不同编译约束”的稀有路径。属性与编译选项的组合可能触发普通测试未覆盖的前端、IR、中端优化和后端代码路径，因此需要一种细粒度的编译空间探索方法。

## 2. 论文要解决的问题

### 2.1 全局编译选项粒度过粗

既有方法主要通过选择 `-O` 级别或其他编译选项探索空间，这些设置往往作用于整个程序，不能精确表达某个函数、变量或语句的特殊编译约束。论文要解决的是如何把局部属性也纳入系统化测试空间。

### 2.2 属性与选项的交互路径难以覆盖

不少属性只有在相关编译选项同时启用时才生效。例如，`no_sanitize_address` 只有在启用 AddressSanitizer 时才会影响编译。随机插入属性但不匹配相应选项，会产生大量无效变体；因此需要同时选择属性和能使属性生效的编译选项。

### 2.3 需要在可编译率、覆盖率和缺陷发现之间取得平衡

属性尤其是变量属性可能与原程序的类型或使用方式冲突，导致变体不可编译。论文评估 ATLAS 是否在相同时间内发现更多独特 GCC/LLVM 缺陷，是否保持较高可编译程序产量，以及是否提升行、分支和函数覆盖率。

> 本文主要研究：如何将程序元素级属性插入与编译选项组合起来，系统地扩展 GCC 和 LLVM 的编译空间，从而发现更多编译器缺陷。

## 3. 核心方法概述

ATLAS（Attribute-guided comprehensive compiler Testing technique）先解析测试程序，收集函数、变量和语句等可以插入属性的位置；随后按照属性适用条件随机生成程序变体；再选择与已插入属性匹配的编译选项和优化选项，送入被测编译器。编译崩溃或其他由论文流程识别的异常会进入缺陷报告与验证流程。

```text
种子程序 P
    ↓
LLVM LibTooling/解析器收集函数、变量、语句位置
    ↓
形成属性候选集合 S
    ↓
按属性适用性随机插入函数/变量/语句属性
    ↓
生成带属性的程序变体集合 Sp
    ↓
根据属性选择相关编译选项，并组合优化选项
    ↓
编译 GCC/LLVM trunk 或 nightly 版本
    ↓
收集崩溃、缺陷状态、可编译率和代码覆盖率
```

方法的关键区别有三点：

1. 属性插入的粒度可以细到单个函数、变量或语句，而不是只改变全局开关。
2. 属性与选项联合选择，尽量让属性真正影响编译过程。
3. ATLAS 是自动化测试工具，不是训练模型或在线学习系统；论文中没有 LLM、工具调用代理或候选生成模型。

在 Algorithm 1 中，函数属性、变量属性和语句属性分别使用候选集合；每个候选位置通过 `FlipCoin()` 决定是否插入，`formFuncAttr`、`selectVarAttr` 和 `formStmtAttr` 负责生成适用属性，直到达到指定变体数 `N`。语句属性可以从该语句涉及的变量列表构造，例如论文 Figure 6 用 `#pragma omp simd linear(...)` 触发 LLVM bug 108166。

## 4. 实验框架与训练流程

### 4.1 程序信息收集

ATLAS 使用 LLVM 的 LibTooling 收集测试程序中的函数、变量和语句位置及类型等信息。属性插入器据此过滤不适用属性，例如不能把 `noreturn` 随意施加到返回类型和控制流不匹配的函数上。

### 4.2 属性引导的变异

对每个原始程序，ATLAS 依据函数、变量和语句候选集合随机插入属性，生成多个变体。函数属性可能包含 `pure`、`returns_twice`、`sanitize`、`simd`、`optimize`、`vector_size` 等；变量和语句属性具有不同的适用条件。每条语句最多关联一个由 Algorithm 2 构造的语句属性。

### 4.3 编译选项选择与测试

ATLAS 根据插入属性选择相关选项。例如，`no_sanitize_address` 需要 `-fsanitize=address` 才会产生预期影响。随后将这些选项与优化选项组合，以增加编译配置的多样性和复杂度。

### 4.4 缺陷识别与结果统计

程序变体被送入 GCC 和 LLVM。论文主要把编译过程中的崩溃等异常作为缺陷线索，并通过 bug tracker 状态、修复提交和人工分析进行后续确认。实验持续比较同一时间窗口内 ATLAS 与基线的独特缺陷数、可编译程序数和覆盖率。

### 4.5 训练、推理和强化学习判定

本文不涉及模型训练，主要采用静态程序分析、随机属性变异、编译配置组合和自动化编译器测试。没有 SFT、预训练、提示词推理、PPO、GRPO、奖励反馈或多阶段模型训练。

## 5. 奖励函数、损失函数或关键公式

本文没有使用强化学习，因此不存在强化学习奖励函数，也没有神经网络损失函数。ATLAS 的核心是搜索/变异目标，而不是可学习目标：在给定时间或测试预算内增加编译空间覆盖和独特缺陷发现。

可用纯文本概括其测试目标：

```text
测试效能 ≈ 独特编译器缺陷数 + 编译器代码覆盖率
约束：变体应尽可能可编译，且属性与编译选项组合有效
```

这不是论文给出的数学公式，而是对论文 RQ1–RQ3 的阅读归纳。论文未提出一个统一的数值优化目标，也未给出可训练的 reward shaping 机制。论文使用 Correcting Commit 方法估计由错误触发的 bug 数；作者明确承认这是自动估计指标，不可能达到完美精度。

## 6. 实验设置

### 6.1 数据集来源

论文使用两类测试程序来源：

1. GCC 和 LLVM 自带的开源回归测试套件。作者选择它们是因为可获取、覆盖较广的 C 语义，且很多测试可以独立编译运行、无需外部库并具有固定输入。
2. Csmith 和 YARPGen/YARPGen v2 生成的随机 C 程序。Csmith 用预定义规则或语法生成多样 C 程序；YARPGen 更关注循环优化相关程序。论文未把这些来源称为传统机器学习训练集，也未报告一个统一的训练/验证/测试划分规模。

因此不存在 SFT 数据集或模型数据泄漏分析。论文未明确给出全部原始种子程序总数；当前 PDF 内容不足以确认一个统一的种子规模。

### 6.2 模型与工具

| 项目 | 论文明确内容 |
| --- | --- |
| 基础模型 | 不适用；本文无机器学习模型 |
| 被测编译器 | GCC 与 LLVM 的 trunk/nightly 开发版本 |
| 程序分析工具 | LLVM LibTooling |
| 测试生成器 | Csmith、YARPGen/YARPGen v2，以及 GCC/LLVM 回归测试套件 |
| 属性范围 | GCC/LLVM 的函数、变量、语句属性，具体组合见表 1 和表 3 |
| 运行硬件 | 论文正文未明确给出完整 CPU/GPU 型号配置 |
| 形式化验证器 | 不使用；论文没有把有限测试提升为形式化证明 |

### 6.3 对比方法

论文比较四种技术：

| 方法 | 含义 |
| --- | --- |
| RO（Random Option） | 随机生成/选择程序和优化编译选项，不插入属性 |
| AO（Attribute Only） | 使用属性，但不配套选择编译选项；依赖特定选项的属性被排除 |
| EMI | 等价模输入的程序变异方法，论文将其作为已有状态方法比较 |
| ATLAS | 属性插入、相关编译选项选择和优化选项组合的完整方法 |

### 6.4 评价指标

| 指标 | 含义 | 趋势 |
| --- | --- | --- |
| Unique bugs | 在给定测试窗口内识别出的独特 GCC/LLVM 缺陷数 | 越大越好 |
| Compilable programs | 成功通过编译的变体数量 | 需结合总程序数解释 |
| Line coverage | 编译器被测试代码的行覆盖率 | 越大越好 |
| Function coverage | 函数覆盖率 | 越大越好 |
| Branch coverage | 分支覆盖率 | 越大越好 |
| Correcting Commit 估计 | 通过后续修复提交等证据估计真实缺陷数 | 越多不一定代表质量更高，需人工核验 |

## 7. 实验结果与结论

### 7.1 主要结果

ATLAS 在 GCC 和 LLVM 上共发现 73 个独特缺陷，其中论文摘要称 58 个已经 confirmed 或 fixed；结论部分进一步写明 58 个已确认、17 个已由开发者解决。表 1 列出了具体 GCC/LLVM issue ID、优先级、状态、选项和属性组合。

论文报告 ATLAS 相比不插入属性的 baseline，平均多发现 109.1% 的缺陷。该百分比对应论文的实验比较，不是某个单独编译器或单个程序的绝对提升。

### 7.2 与传统编译器测试方法的比较

在 10 天测试中，表 4 给出以下缺陷数：

| 生成器 | 技术 | GCC | LLVM | 总数 |
| --- | --- | ---: | ---: | ---: |
| Csmith | RO | 13 | 5 | 18 |
| Csmith | AO | 19 | 11 | 30 |
| Csmith | EMI | 17 | 11 | 28 |
| Csmith | ATLAS | 32 | 17 | 49 |
| YARPGen | RO | 8 | 6 | 14 |
| YARPGen | AO | 12 | 10 | 22 |
| YARPGen | EMI | 10 | 9 | 19 |
| YARPGen | ATLAS | 25 | 13 | 38 |

这些数字是 10 天窗口中相应生成器与技术组合发现的独特 bug 数，不是运行速度或真实硬件加速比。ATLAS 在 Csmith 与 YARPGen 两个生成器、GCC 与 LLVM 两个目标上都高于三种比较方法。

同一表还报告可编译程序数。例如 Csmith+ATLAS 为 30,170 个可编译程序、46,416 个总程序；YARPGen+ATLAS 为 62,142 个可编译程序、99,439 个总程序。RO/EMI 的可编译比例通常更高，原因是 AO/ATLAS 需要修改程序并插入可能冲突的属性，特别是变量 `vector_size` 属性。

### 7.3 与其他 LLM 方法的比较

本文没有 LLM baseline，也没有比较代码模型、LLM 生成 mutation operator 或 agent。不能把 ATLAS 的随机属性变异描述为 LLM 生成器。

### 7.4 覆盖率结果

表 5 的覆盖率如下；括号中是相对 RO 的覆盖代码数量增量，而不是百分比增量：

| 编译器 | 技术 | Line | Function | Branch |
| --- | --- | ---: | ---: | ---: |
| GCC | RO | 33.5% | 35.2% | 21.1% |
| GCC | AO | 34.7% (+13,080) | 36.9% (+419) | 22.0% (+10,697) |
| GCC | EMI | 35.3% (+19,619) | 36.8% (+314) | 22.4% (+15,450) |
| GCC | ATLAS | 36.3% (+30,519) | 37.6% (+1,152) | 23.2% (+24,958) |
| LLVM | RO | 34.4% | 25.6% | 20.0% |
| LLVM | AO | 35.6% (+20,324) | 26.5% (+849) | 20.9% (+6,472) |
| LLVM | EMI | 35.1% (+12,435) | 26.9% (+1,307) | 21.3% (+9,592) |
| LLVM | ATLAS | 36.8% (+41,806) | 27.6% (+1,953) | 21.7% (+12,954) |

论文指出百分比差异看起来不大，但绝对覆盖的行和分支可达到数万条增量；ATLAS 在 GCC 和 LLVM 的三类覆盖指标上均高于比较方法。

### 7.5 时间趋势与属性案例

在 Csmith 程序上，RO 约 40 小时后趋于饱和，EMI 在超过 200 小时后接近饱和；AO 和 ATLAS 在 10 天内仍能持续发现缺陷。YARPGen 程序上四种方法都能持续发现缺陷，但 RO、AO 和 EMI 找到更多 bug 所需时间明显增长，ATLAS 的发现速率更稳定。

论文将一些 bug 归因于真实软件中常用的属性，例如 `optimize`/`optnone`、`simd`、`malloc`、`aligned` 和 `vector_size`。这些属性常见于系统库、图形引擎、深度学习框架、HPC 软件和性能敏感应用。属性与优化、IR 处理和代码生成的交互导致 73 个 bug 分布在前端 23 个、中端 21 个、优化组件 16 个、后端 13 个；这些是按组件统计的 bug 归属，不是互斥的执行阶段性能指标。

### 7.6 消融含义

RO、AO 和 ATLAS 的设置隔离了两项因素：属性本身，以及让属性生效的编译选项。AO 高于 RO 说明属性插入有额外价值；ATLAS 高于 AO 则说明属性与相关编译选项的联合选择仍然重要。论文没有把这称为机器学习意义上的 ablation loss，而是作为测试策略对比。

## 8. 主要创新点

### 8.1 创新点一：把编译器属性作为细粒度测试维度

以往编译空间探索主要改变全局优化级别或选项。ATLAS 将函数、变量和语句属性视为可组合的测试维度，使同一程序内的不同代码元素可以走不同的编译路径。论文的 bug 和覆盖率实验支持这一设计有效。

### 8.2 创新点二：属性与相关编译选项联动

仅插入属性可能不产生效果。ATLAS 根据属性选择对应选项，再和优化选项组合，避免把依赖 sanitizer、向量化等开关的属性放在失效环境中。这是相对于 AO 的关键差异。

### 8.3 创新点三：可嵌入既有测试生成流程的自动化工具

ATLAS 使用 LibTooling 收集结构信息，可以处理 GCC/LLVM 回归测试以及 Csmith、YARPGen 生成程序。论文还讨论了先做 EMI 或 Creal 变异，再对结果插入属性的分层组合方式，因此它更像可复用的测试变换层，而不是只能独立运行的单一生成器。

### 8.4 工程实现与真正创新的区分

使用 GCC、LLVM、LibTooling、Csmith 或 YARPGen 本身不是创新。真正的技术贡献是将属性的程序元素级作用域、属性适用性、相关编译选项和缺陷测试流程组合成一个系统化的编译空间探索策略。

## 9. 局限性

### 9.1 论文明确承认的局限

1. 编译器版本代表性可能不足。作者通过测试 GCC 与 LLVM 的多个版本缓解单版本风险，但实验仍集中于两个广泛使用的 C 编译器。
2. Correcting Commit 只是 bug 数自动估计方法，精度并不完美；论文称这是目前可用的自动估计方式之一，并通过 crash message 分析减少重复和误报。
3. 属性插入会降低可编译率，尤其是变量属性可能与原程序使用要求冲突。
4. 测试程序主要来自 Csmith、YARPGen 和 GCC/LLVM 测试套件，覆盖范围不能自动代表所有语言、前端和真实工作负载。

### 9.2 阅读后发现的潜在局限

1. ATLAS 主要依赖随机 `FlipCoin()` 和手工设计的属性集合；论文没有显示面向历史 bug 的自适应概率学习或基于反馈的属性优先级模型。
2. 发现编译崩溃和 tracker 状态不等于证明编译器生成代码存在语义错误。该流程包含有限测试、人工确认和开发者修复证据，不能被表述为形式化验证。
3. 论文未给出完整硬件型号、所有编译器版本号、属性覆盖全集和各阶段时间开销，因此复现实验的环境细节仍不充分。
4. 当前方法面向 C/C++ 风格属性和 GCC/LLVM；对 MLIR dialect、RISC-V 后端、GPU kernel 或跨语言 LLVM 前端的迁移需要重新定义属性作用域与合法性规则。
5. 属性组合空间可能快速爆炸。论文报告了较好的结果，但没有证明在更多属性、跨函数约束或更复杂控制流下仍然保持相同效率。

## 10. 阅读后的研究方向反思

### 10.1 值得借鉴的思想

最值得借鉴的是把“编译空间”从全局 flags 扩展到程序元素级约束，并把语法/类型适用性检查放在变异生成之前。对 LLVM/MLIR 研究而言，这提示测试不应只覆盖 pass 开关，还应覆盖 dialect attribute、operation attribute、函数属性、目标特性和后端指令选择约束之间的交互。

### 10.2 不能简单照搬的核心贡献

直接把 GCC/LLVM 属性插入器改成 RISC-V 属性插入器，或只把目标架构换成 RISC-V，不足以形成新贡献。ATLAS 的核心是属性作用域与相关选项联动；后续工作需要提出新的 RISC-V/异构硬件语义、验证反馈或后端覆盖机制，并证明它能触发原方法无法触发的缺陷类别。

### 10.3 与 LLM/编译器优化方向的关系

ATLAS 更适合作为编译器 fuzzing 工具模块或正确性测试 baseline，而不是完整的 LLM 优化框架。LLM 可以作为候选属性组合、约束模板或 bug 归因的提议器，但最终仍应由编译器、差分执行、崩溃去重和人工/形式化检查提供证据。不能因为它使用 LLVM 就把论文归类为 LLM 编译器优化论文。

### 10.4 与 RISC-V/异构优化方向的关系

相关性为中等偏低到中等：论文测试的是 GCC/LLVM 编译器基础设施，属性会影响优化、IR 和代码生成，但实验没有 RISC-V、RVV、GPU 或异构设备。它可提供测试空间设计和后端 bug 发现方法参考；不能直接证明对 RISC-V 性能或语义正确性有效。

## 11. 可进一步尝试的研究方向

### 11.1 RISC-V/LLVM 后端特性引导的编译空间 fuzzing

#### 研究问题

如何将 RISC-V ISA/扩展、RVV 向量长度、目标特性、指令选择约束和函数属性联合起来，发现 LLVM RISC-V 后端在优化和代码生成中的稀有缺陷？

#### 与原论文的区别

不是只替换测试目标，而是增加后端特性与生成代码/汇编约束的交互，并以目标指令合法性和差分执行作为额外反馈。

#### 可能的创新点

设计 ISA 特性与程序元素作用域的联合变异；对 RVV intrinsic、VLA 向量化和 ABI 约束建立合法性过滤；把编译器崩溃与汇编验证分开统计。

#### 实验框架

```text
C/C++/LLVM IR 种子
    ↓
属性、target feature、RVV 约束联合变异
    ↓
LLVM RISC-V 后端编译
    ↓
汇编合法性检查 + QEMU/硬件差分执行
    ↓
缺陷去重、覆盖率和修复提交分析
```

#### 可行性

需要 LLVM RISC-V 工具链、QEMU 或可用 RVV 设备、Csmith/YARPGen/LLVM test suites 和汇编/执行验证器。

#### 主要风险

硬件或模拟器行为可能掩盖后端缺陷；RVV 运行环境、ABI 和向量长度差异会降低可复现性。

### 11.2 面向 MLIR dialect attribute 的合法变异与 verifier fuzzing

#### 研究问题

如何针对 MLIR operation、region、type 和 dialect attribute 的局部组合，发现 verifier、canonicalization、lowering 和 codegen 之间的缺陷？

#### 与原论文的区别

MLIR 具有显式 dialect/type/region 结构，不能简单复用 C 属性插入；需要维护 IR 合法性并测试多级 lowering 的语义保持。

#### 可能的创新点

用 dialect schema 和 verifier 约束生成最小有效变体；对 lowering pipeline 的阶段组合做覆盖引导；将 verifier 接受但 lowering 失败的案例分类。

#### 实验框架

```text
合法 MLIR module
    ↓
dialect/type/attribute/region 约束变异
    ↓
逐级 verifier 与 canonicalizer
    ↓
LLVM IR/目标代码 lowering
    ↓
崩溃、拒绝、错误 IR 和差分语义结果
```

#### 可行性

需要 MLIR 源码、dialect 定义、MLIR test infrastructure、LLVM 后端以及解释器或运行时参考实现。

#### 主要风险

如果只统计 verifier 拒绝，会把预期错误当成缺陷；跨 dialect 的语义 oracle 和最小化仍然困难。

### 11.3 反馈驱动的属性选择模型

#### 研究问题

历史覆盖率、崩溃栈和修复提交能否用于学习不同属性/选项组合对新编译路径的边际收益？

#### 与原论文的区别

原论文使用随机插入；该方向引入基于覆盖增量和缺陷新颖性的自适应调度，但不把模型输出直接当作正确性证据。

#### 可能的创新点

定义属性组合的去重特征、阶段覆盖反馈和崩溃相似度奖励；比较 bandit、传统搜索和 LLM 提议器在相同编译预算下的发现效率。

#### 实验框架

```text
属性/选项候选池
    ↓
搜索器或 LLM 提议组合
    ↓
编译器执行与覆盖/崩溃反馈
    ↓
去重、奖励/优先级更新
    ↓
下一轮候选选择
```

#### 可行性

可以从 ATLAS 的开源 artifact、GCC/LLVM issue 历史和现有 fuzzing 框架开始，不需要先训练大模型。

#### 主要风险

覆盖率奖励可能导致重复探索热门路径；Correcting Commit 延迟高，容易造成稀疏反馈和错误归因。

这篇论文最值得学习的是把编译器测试从全局 flags 扩展到函数、变量和语句级属性，并用选项联动让这些属性真正进入编译路径；最主要的局限是实验集中于 GCC/LLVM 的 C 编译场景，且有限测试不等于语义证明。如果用于后续研究，最合理的使用方式是把 ATLAS 作为细粒度变异与 baseline 工具，再加入 MLIR/RISC-V 特有的合法性、后端和差分执行反馈，而不是简单替换目标架构或把随机属性插入称为 LLM 优化。
