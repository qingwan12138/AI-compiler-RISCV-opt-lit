# Code-Optimise 文献阅读总结

论文题目：**Code-Optimise: Self-Generated Preference Data for Correctness and Efficiency**

作者：Leonidas Gee、Milan Gritta、Gerasimos Lampouras、Ignacio Iacobacci

发表时间：2025

发表平台：Findings of NAACL 2025

关键词：代码语言模型、偏好数据、DPO、正确性、运行效率、动态样本选择

> 本文档基于 NAACL 2025 论文 PDF 全文整理。

## 1. 研究背景

代码模型通常优先追求功能正确，显式优化执行时间可能造成正确率下降。依赖 GPT-4 等更大模型蒸馏又带来法律、费用和隐私问题；RL 实现复杂且不稳定（第1节）。

## 2. 论文要解决的问题

如何只依赖基础代码模型自身生成的数据，同时把“通过/失败”和“快/慢”作为偏好信号，在提高功能正确率的同时继续降低代码运行时间，并减少训练过拟合。

## 3. 核心方法概述

Code-Optimise 对每道题从基础模型采样 100 个 Python 解答；用单元测试标注正确性，并稳定重复计时标注速度。过滤后构造 Quick-vs-Slow、Passed-vs-Failed 或二者合并的偏好对，分别用 SFT 或 DPO 训练。Dynamic Solution Selection 在每个 epoch 为同一 prompt 重新随机选择解答/偏好对，避免固定少量 completion 被记忆（第2节）。

## 4. 实验框架与训练流程

```text
题目+单测 → 基础模型每题采样100解
→ 运行单测与稳定计时 → 正确/错误、快/慢标签
→ 过滤至少2个通过+1个失败的题
→ SFT或DPO训练（每epoch动态选解）
→ MBPP/HumanEval评测
```

## 5. 奖励函数、损失函数或关键公式

SFT 使用标准负对数似然（式1）。DPO 使用参考策略 `π_ref` 和偏好解 `y_w/y_l` 的 logistic 分类损失（式2），`β` 控制相对参考模型的偏离。本文不用在线 RL，也没有手工加权的多目标标量奖励；正确性与速度通过偏好对类型编码。

## 6. 实验设置

### 6.1 模型与数据

StarCoder 1B/3B、CodeLlama 7B/13B。训练/验证各从 384/90 个问题出发，每题采样 100 个解；过滤后的比例随模型规模约为 40%–58%（表1）。训练 30 个 epoch。

### 6.2 计时方法

每个解先执行 50 次，系数变异 `CoV≤0.1` 才接受；否则最多重试 1000 次。整个计时算法独立执行 5 次并取平均（算法1）。

### 6.3 指标

MBPP 为域内、HumanEval 为域外；正确性用 `pass@1/10/100`，效率用正确解的中位运行时间，生成成本用正确解字符数中位数。

## 7. 实验结果与结论

DPO 配置在不同模型规模上整体提高 `pass@k`，尤其对小模型和较小 `k` 明显；SFT 的收益较弱且高 `k` 可能下降（第3.2节）。DPO Quick-vs-Slow/All 相对已很强的基础模型，在 MBPP 上进一步降时最高 6%，在 HumanEval 上最高 3%；代码长度最高减少 48% 和 23%（第3.3节）。动态样本选择对所有配置有益，DPO 更明显。若只重正确性选 PvF，只重速度选 QvS，兼顾两者选 All（第3.7节）。

## 8. 主要创新点

### 8.1 自生成多目标偏好数据

不依赖更大教师模型，用执行器自动得到正确性与速度信号。

### 8.2 轻量 DPO 代替复杂 RL

把快慢和成败直接组成偏好对，训练简单且可复现。

### 8.3 动态解答选择

每个 epoch 改变偏好组合，提高有限题目下的数据利用率。

## 9. 局限性

作者明确指出短程序计时仍有噪声；训练提示只有约 200 个开源问题，且全部实验为 Python，尚未验证 C/C++、编译器 IR 或跨 ISA。运行时间只在特定环境测量，偏好可能过拟合硬件/解释器；字符数缩短不等同于算法或机器码效率。过滤要求基础模型先产生足够正确解，对困难任务覆盖不足（第6节）。

## 10. 阅读后的研究方向反思

该方法适合借鉴“执行信号→偏好数据”的轻量路线，但它是源码生成优化，不是 compiler phase ordering。若用于编译研究，应把偏好单元改为可验证的 IR/Transform script/pass 方案，并同时记录跨硬件性能和语义正确性。

## 11. 可进一步尝试的研究方向

### 11.1 跨硬件编译方案偏好学习

#### 研究问题

同一程序的两个编译方案，如何根据正确性、x86/K3 延迟和测量置信度构造稳定偏好。

#### 与原论文的区别

从 Python 源码 completion 转为编译器动作，并由双硬件实测与验证器标注。

#### 可能的创新点

置信区间偏好、架构条件偏好、不可比较样本的 Pareto DPO。

#### 实验框架

```text
程序 → 生成多个 pass/Transform 方案
→ 编译测试 + 双机计时 → 构造偏好对 → 小模型 DPO
```

#### 可行性与风险

不需要在线 RL；风险是收集可靠的双机偏好成本较高。

## 12. 与其他已读文献的关系

与 Compiler-R1/AwareCompiler 的在线 RL 相比，Code-Optimise 用离线 DPO 更轻；与 ECCO 代码效率基准同样强调正确性与效率不可混为一谈；与 TRACE 相比，本文用于训练，TRACE 主要构建跨语言效率评测基准。

## 13. 一页式总结

| 项目 | 内容 |
|---|---|
| 论文研究任务 | 同时提高代码生成正确性和执行效率 |
| 核心问题 | 优化速度易损害正确性，教师数据昂贵 |
| 输入/输出 | 题目+测试 / 优化后的代码模型 |
| 核心方法 | 自采样、执行标注、DPO、动态选择 |
| 使用模型 | StarCoder 1B/3B、CodeLlama 7B/13B |
| 是否使用强化学习 | 否，使用 DPO |
| 是否使用形式化验证 | 否，单元测试 |
| 最重要结果 | 运行时间再降 6%/3%，代码长度降 48%/23% |
| 核心创新 | 自生成正确性+效率偏好数据 |
| 主要局限 | 小型 Python 任务、计时噪声、硬件依赖 |
| 与 RISC-V 相关性 | 间接，可迁移到跨硬件偏好学习 |
| 最适合作为 | 轻量离线训练范式参考 |

> 最实用的思想是：先用执行器自动造偏好，再训练模型学会选择，而不是直接上复杂在线 RL。
