# C44 C2HLSC 文献阅读总结

作者：Luca Collini、Siddharth Garg、Ramesh Karri

## 1. 研究背景

高层次综合（HLS）把 C/C++ 转为硬件 RTL，但通用软件常用动态内存、递归、复杂指针和库调用等 HLS 不支持或有限支持的构造。工程师需手工固定数组/循环边界、改写接口并反复运行 HLS，过程耗时且易错。

LLM 对 C 的理解通常强于直接生成 Verilog，但生成的 C 仍可能有语法、功能或综合错误。论文在 C 层执行重构，并用编译器、参考测试和 HLS 工具组成反馈闭环。

## 2. 论文要解决的问题

### 2.1 将一般 C 改写为可综合 C

系统处理动态结构、递归、指针、流式接口等 HLS 不适合的代码形式，并尽量保持参考程序功能。

### 2.2 扩展到多函数层次结构

整体改写容易破坏函数接口或重写子函数。论文研究如何逐函数处理、从叶到顶层构建，并自动为子函数生成测试。

### 2.3 区分软件功能与硬件综合检查

普通编译和参考测试通过，不代表 HLS 可综合；综合成功也不代表 pragma 提升面积/延迟。系统需分别检查两类目标。

> 本文主要研究：如何用 LLM 与层次化编译反馈，将真实 C 应用重构为 Catapult HLS 可综合代码，并按面积或延迟目标插入优化 pragma。

## 3. 核心方法概述

C2HLSC 包含层次预处理、函数重构和 pragma 识别。解析器找出顶层函数及调用层次；程序调试运行时，GDB 读取子函数调用参数，以顶层测试构造子函数测试。模型再从叶函数到根函数逐个改写：g++ 与测试捕获编译/功能错误，Catapult HLS 捕获综合错误。综合成功后模型按面积或延迟目标插入 pragma，并重复双重检查。

流程：原始 C 和顶层测试 → pycparser 分析调用层次、GDB 提取子函数参数 → 自底向上逐函数改写 → g++ 编译和参考测试 → Catapult 综合并反馈错误 → 加入优化 pragma → 再次检查。

模型直接输出变换后的 C，因此主要角色是源程序改写器。HLS 错误参与迭代；论文没有形式化等价证明。

## 4. 实验框架与训练流程

### 4.1 工程师参与的案例

作者先用 Gemini 手工提示 NIST 800-22 随机性测试、QuickSort、AES-128，观察流式接口、去指针/递归及 HLS 错误修复难点。

### 4.2 层次预处理与重构

以用户指定顶层函数和测试为起点。pycparser 解析 C；调试运行和 GDB 记录子函数调用参数并生成单元测试。模型从叶函数开始逐层重构，并在提示中固定子函数签名，减少接口不匹配。

### 4.3 双层反馈与 pragma

g++ 和参考测试是快速内循环；成功后才运行 Catapult HLS。编译/测试或综合错误进入提示，驱动再次改写。综合成功后，模型按面积/延迟目标尝试循环展开、流水线、数组分区、函数内联等 pragma，再经双重检查。

### 4.4 模型使用

论文不训练新模型。自动框架先用 GPT-4o-mini，连续三次失败后切换 GPT-4o；另比较 Claude Sonnet 3.5。案例研究使用 Gemini。未涉及 SFT 或强化学习。

## 5. 奖励函数、损失函数或关键公式

本文没有强化学习奖励函数或模型损失函数。参考测试通过、普通编译通过和 Catapult 成功综合是阶段门槛；面积与周期数用于比较结果，并非训练奖励。

## 7. 实验结果与结论

### 7.1 成功率

GPT-4o/4o-mini 在延迟目标下 AES 成功率 60%，Claude Sonnet 3.5 为 80%；两者在 DES 上均为 0。不同模型、目标和基准结果变化较大。表 3–6 的比例来自各基准的 10 次运行。

### 7.2 流式接口与复杂层次

流式接口成功率不等于综合成功率。Sonnet 在部分测试上能综合，却没有形成流式接口；有嵌套循环的 Overlapping 等任务较难。层次拆分不能消除复杂宏展开的错误。

### 7.3 面积与延迟

GPT 集成在延迟优化时结果变异较大；Claude 的 pragma 语法错误有时使工具忽略优化。作者指出单次 pragma 生成效果有限，较好结果来自 10 次运行中选出的最好一次。表 8 中 QuickSort 最好面积 11813.6、延迟 4 周期；AES 面积 2965.3、延迟 853 周期。此表比较的人工/手工实现来源不同，不能推断所有任务都更优。

### 7.4 消融与案例

没有独立移除层次预处理、子函数测试或双层反馈的消融。案例显示模型能改写流式接口并消除 QuickSort 递归/指针，但会出错于循环边界、栈管理和位宽，工具反馈可暴露这些问题。

## 8. 主要创新点

### 8.1 从顶层测试自动构造子函数测试

作者运行程序并提取子函数调用参数，为自底向上重构生成测试，减少逐层手工准备工作。

### 8.2 分离普通编译/功能检查与 HLS 综合

快速软件内循环与较重 HLS 外循环分别捕获语法/功能问题和综合约束问题；成功综合后再尝试 pragma 优化。实验展示系统可用，但未用消融量化模块贡献。

## 9. 局限性

### 论文明确呈现的边界

- DES 因宏展开后函数复杂且功能错误多，多种配置均失败。
- Overlapping、Monobit Block 等嵌套循环的流式改写成功率低。
- pragma 生成不稳定；Claude 会输出工具不识别的语法。
- 部分基准的综合报告出现零延迟异常，作者检查后将其剔除。
- 作者指出框架受宏密集风格限制；未来考虑复杂 C++ 对象及综合反馈驱动的 pragma 搜索。

### 阅读后发现的潜在局限

子函数测试来自一次运行参数，可能漏掉其他调用状态；普通测试不是全输入等价证明；评测依赖 Catapult 和单一目标工艺；仅 10 个基准且每配置 10 次运行，统计范围有限。

## 10. 阅读后的研究方向反思

值得借鉴的是层次化重构、用顶层轨迹生成子函数测试，以及把快速软件检查和硬件综合分层。只把 Catapult 换成另一综合器，新意有限。对 RISC-V 研究的直接联系较弱，但其反馈和层次测试可迁移到 LLVM 后端或 RVV intrinsic 改写；新工作应围绕具体后端、语义检查和硬件实测提出问题。

## 11. 可进一步尝试的研究方向

### 11.1 后端约束驱动的 C-to-HLS 重构

#### 研究问题

如何将不同 HLS 后端与 FPGA/ASIC 约束显式传入改写，减少可综合但资源成本过高的输出。

#### 与原论文的区别

把阶段门槛扩为约束优化，并以设计空间搜索验证资源收益，而非仅增加 pragma 生成。

#### 可能的创新点

结构化综合诊断、后端条件化改写、资源估计与搜索联合决策。

#### 实验框架

C 与功能测试 → 后端分析 → 结构化诊断 → 局部改写 → 综合和资源测量 → Pareto 候选。

#### 可行性

需两个以上 HLS 后端、稳定基准、日志解析与可复现实验脚本。

#### 主要风险

工具许可/版本、综合波动和跨后端语义差异影响复现。

### 11.2 从动态轨迹生成覆盖导向子函数测试

#### 研究问题

如何把单次 GDB 轨迹生成测试扩展为覆盖更多分支与调用状态的测试。

#### 与原论文的区别

重点研究测试生成与错误检出率，比较轨迹回放、符号执行和覆盖引导方法。

#### 可能的创新点

覆盖缺口驱动输入增量生成、调用上下文聚类、测试最小化与反例回传。

#### 实验框架

顶层测试 → 轨迹采集 → 覆盖缺口 → 输入生成 → 子函数测试 → 错误检出率比较。

#### 可行性

可沿用 GDB、编译器插桩或测试生成工具，以覆盖率和错误检出率评价。

#### 主要风险

状态空间大；生成的内部状态必须符合有效调用上下文。

## 12. 与其他已读文献的关系

本批次 SLEB 让 LLM 识别稀疏结构，再由综合器生成库/DSL 表达式；C2HLSC 让 LLM 直接输出重构的 C，并用 g++、参考测试和 Catapult 反馈修复。二者可作结构识别/搜索与源码重构/工具闭环的对照，但任务、正确性保障和性能目标不同，不能把 I/O 测试与综合成功率当作同一指标。

| 论文研究任务 | 一般 C 程序自动改写为 HLS 可综合 C |

| 输入 | C 程序、顶层测试、面积/延迟目标 |
| 输出 | 可综合 C、pragma 与 Catapult 综合结果 |

| 是否使用强化学习 | 否 |
