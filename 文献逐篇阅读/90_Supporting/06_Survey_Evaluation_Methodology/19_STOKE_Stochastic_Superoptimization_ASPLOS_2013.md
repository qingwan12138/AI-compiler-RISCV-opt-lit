## 1. 研究背景

传统编译器把指令选择、寄存器分配、指令调度等后端优化任务拆分为多个独立的Pass顺序执行，每个Pass在有限的视野内做出局部最优决策。这种分解虽然简化了编译器的设计，但也带来了根本性的限制：每个Pass只看到IR的部分信息，无法考虑不同优化阶段之间的交互效应。例如，一个非传统的指令序列可能同时利用了指令选择和寄存器分配的特殊交互来实现更高的性能，但这种联合优化在Pass分解的框架下很难被发现。此外，现代x86-64指令集包含数百条指令和复杂的寻址模式、标志寄存器隐式使用等特性，手工编写优化规则很难充分利用所有可能的指令组合。STOKE的核心理念是：放弃传统的Pass分解方法，将整个无循环（loop-free）x86-64二进制代码的优化问题表达为一个随机搜索问题，通过MCMC（马尔可夫链蒙特卡洛）在庞大的程序空间中搜索更优的等价实现。这种方法不依赖于编译器开发者的领域知识，而是通过随机探索自动发现非传统的、高效的指令序列。

## 2. 论文要解决的问题

### 2.1 问题一：如何在二进制级别搜索等价但更高效的指令序列

在没有显式Pass分解的情况下，直接搜索x86-64二进制级别的优化代码是一个极具挑战性的问题。搜索空间涉及所有合法的指令序列组合，其大小随指令数指数增长。对于一段10条指令的代码，替换指令、调整顺序、插入和删除操作产生的候选程序数量可达数十亿甚至更多。STOKE需要设计有效的搜索策略和提议分布（proposal distribution），使得搜索过程能够在合理时间内收敛到高质量的优化结果。

### 2.2 问题二：如何同时考虑正确性、性能和多个约束来评估候选程序

优化搜索面临的核心挑战是多目标权衡：候选程序需要正确（与原始程序语义等价）、高效（比原始程序更快）、满足各种约束（代码尺寸、寄存器使用限制等）。这些目标之间可能存在冲突——例如，一个更快的程序可能使用了更多的寄存器。STOKE需要设计一个多目标成本函数来同时编码这些因素，并通过加权组合实现自动权衡。成本函数的设计对搜索行为的引导起着决定性作用。

> 本文主要研究：如何在x86-64二进制级别，利用MCMC随机搜索技术发现等价但更高效的指令序列，同时通过多目标成本函数平衡正确性、性能和约束条件。

## 3. 核心方法概述

STOKE把无循环x86-64二进制超优化问题表述为随机搜索，使用MCMC（马尔可夫链蒙特卡洛）来探索程序空间。核心工作流是：从初始程序（如LLVM -O0生成的x86-64二进制）出发，STOKE通过随机变换（如替换指令、交换指令顺序、插入/删除指令）生成候选程序变体，然后使用成本函数评估每个变体。成本函数同时编码：(1) 正确性——候选程序在测试集上的行为是否与原始程序一致；(2) 性能——候选程序是否比原始程序更快（使用指令延迟或微架构模型估算）；(3) 其他约束——如代码尺寸、寄存器使用限制等。MCMC采样过程使用Metropolis-Hastings算法：接受更好的候选（成本更低），也有一定概率接受较差的候选（避免陷入局部最优），通过温度参数控制探索程度。搜索过程持续进行，直到达到预设的迭代次数或找到满足性能目标的解。

```
原始程序（LLVM -O0生成的x86-64二进制）
  ↓
随机提议（Random Proposal）
  - 指令替换
  - 操作数交换
  - 指令插入/删除
  - 指令交换
  ↓
候选程序
  ↓
成本评估（Cost Function）
  - 正确性成本（测试集验证）
  - 性能成本（指令延迟估算）
  - 其他约束（代码尺寸等）
  ↓
MCMC接受/拒绝（Metropolis-Hastings）
  - 更优候选: 接受
  - 较差候选: 以一定概率接受（退火策略）
  ↓
迭代搜索 → 直到收敛
  ↓
优化后程序
```

## 4. 实验框架与训练流程

STOKE不涉及训练流程，而是基于MCMC随机搜索的优化算法。以下描述其系统执行流程。

### 4.1 提议分布与搜索策略

STOKE的提议分布定义了如何从当前程序生成新的候选程序。提议操作包括五种基本变换：(1) 指令替换（Replace）——将一条指令替换为另一条语义可能不同的指令，这是最核心的变换操作，也是探索新指令组合的主要途径；(2) 操作数替换（Operand Shuffle）——交换或修改指令的操作数，例如交换加法指令的两个源操作数，或将寄存器操作数替换为内存操作数；(3) 指令插入（Insert）——在随机位置插入一条新指令，通常用于引入额外的计算步骤来创造优化机会；(4) 指令删除（Delete）——删除一条指令，直接减少指令数，通常能带来性能提升；(5) 指令交换（Swap）——交换两条指令的顺序，探索指令调度优化的可能性。提议分布的设计需要在探索深度（激进的变换）和搜索稳定性（小的局部调整）之间取得平衡——过于激进的变换会导致大量无效候选，过于保守的变换则难以跳出局部最优。

### 4.2 成本函数设计

STOKE的多目标成本函数是一个加权组合，包含三个主要分量：(1) 正确性成本——候选程序在随机生成的测试集上产生错误输出的惩罚，用错误输出的测试用例数量来衡量，测试用例通常使用32-256组随机生成的输入；(2) 性能成本——候选程序的指令延迟之和（使用x86-64指令延迟表估算），或者基于微架构模型的更精确预测结果；(3) 约束成本——代码尺寸、特定指令的使用限制等附加条件的惩罚项。成本函数的设计是STOKE性能的关键——太简单的成本函数可能导致搜索收敛到正确但性能差的候选，而太复杂的成本函数可能引入过多的噪声影响搜索方向。温度退火策略控制着搜索过程中的探索程度：初始高温鼓励广泛探索，后期低温促使收敛到局部最优解。

## 5. 奖励函数、损失函数或关键公式

STOKE的核心是MCMC搜索中的接受概率公式和成本函数。

| 符号 | 含义 |
|---|---|
| P | 当前程序（x86-64指令序列） |
| P' | 候选程序（通过随机变换生成） |
| C(P) | 程序P的成本函数值（越小越好） |
| T | 温度参数（控制接受较差候选的概率） |
| A(P→P') | 从P接受P'的概率 |
| C_correct(P) | 正确性成本（错误测试用例数） |
| C_perf(P) | 性能成本（指令延迟总和） |
| w_c | 正确性权重系数 |
| w_p | 性能权重系数 |

Metropolis-Hastings接受概率：A(P→P') = min(1, exp((C(P) - C(P')) / T))

成本函数：C(P) = w_c × C_correct(P) + w_p × C_perf(P)

当C(P') < C(P)时（候选更优），接受概率为1（总是接受）；当C(P') ≥ C(P)时（候选更差），接受概率为exp((C(P) - C(P'))/T)，温度T越高，接受较差候选的概率越大。

## 6. 实验设置

### 6.1 数据集来源

实验在x86-64平台上进行，从LLVM -O0生成的二进制代码出发，尝试优化到超越GCC -O3的质量。测试案例包括：
- Hacker's Delight中的位操作函数（bit manipulation）——包括前导零计数、位反转、位置换等经典位操作算法
- SAXPY（标量向量乘加）——高性能计算中的常见操作模式
- 手写汇编案例——矢量运算和特定算法的高效实现

### 6.2 模型与工具

- LLVM -O0（生成初始二进制代码）
- GCC -O3（作为优化质量对比基线）
- STOKE工具（MCMC随机搜索优化器）
- x86-64指令延迟表（用于性能成本估算）
- 随机测试生成器（用于正确性验证）

### 6.3 对比方法

- LLVM -O0生成的二进制（起始点）
- GCC -O3生成的二进制（业界标准优化质量）
- 专家手写汇编（最优质量参考）

### 6.4 评价指标

| 指标 | 说明 |
|---|---|
| 最终程序性能（指令延迟总和） | 优化后程序的理论延迟 |
| 最终程序性能（实际运行时间） | 优化后程序的实际执行时间 |
| 搜索收敛时间 | 从初始程序达到稳定解所需的搜索时间 |
| 与全局最优的差距 | 在已知最优解的场景下评估搜索质量 |
| 多链搜索成功率 | 多链并行搜索找到最优解的概率 |

## 7. 实验结果与结论

### 7.1 主要结果

从LLVM -O0的x86-64二进制出发，STOKE在若干Hacker's Delight位操作案例、SAXPY和手写汇编案例上达到或超过GCC -O3的优化质量。一个引人注目的发现是：部分优化后的代码甚至比专家手写汇编更好——STOKE发现了非传统的指令序列组合，充分利用了x86-64指令集的特殊特性（如复杂寻址模式、标志寄存器的隐式使用等），这些组合是手工编程时通常不会考虑的。这一结果证明了"随机探索可以找到超越专家知识的优化"这一重要理念。搜索收敛时间通常在数分钟到数小时之间，取决于代码长度和搜索空间大小——简单函数（5-10条指令）可在数分钟内收敛，复杂函数（20+条指令）可能需要数小时。

### 7.2 消融实验

多链并行搜索相比单链搜索显著提高了找到最优解的概率（约2-3倍），且可以更早跳出局部最优。MCMC的温度退火策略对搜索效果影响很大：退火过快导致陷入局部最优，退火过慢导致收敛缓慢。成本函数中正确性权重的设置对搜索行为有决定性影响：权重过高导致搜索过度保守（不敢探索风险变换），权重过低导致大量搜索时间浪费在错误程序上。测试集大小的影响方面，32个测试用例与256个测试用例在搜索质量的差异不大，但使用32个测试用例时搜索速度快4-8倍。

### 7.3 案例分析

在Hacker's Delight的位反转（bit reversal）案例中，STOKE发现了一个使用x86-64的复杂寻址模式来实现位反转的非传统指令序列，该序列仅用6条指令就完成了通常需要10-12条指令才能完成的操作。在SAXPY案例中，STOKE发现了一个通过巧妙利用x86-64的乘加指令（如VFMADD）来减少寄存器压力的优化方案。这些案例说明STOKE搜索到的优化不仅"更短"，而且往往是"不同"的——它通过重新思考指令的使用方式来实现性能提升，而非简单的指令删除。

## 8. 主要创新点

### 8.1 创新点一：将MCMC随机搜索应用于x86-64二进制级别的超优化

首次将MCMC随机搜索应用于x86-64二进制级别的超优化，证明了在不使用传统编译器Pass分解的情况下，随机探索可以找到具有竞争性甚至是超越专家手写的代码。这一创新改变了编译器优化的研究范式——从"设计更好的Pass"转向"设计更好的搜索策略"。STOKE的成功为后续的基于学习和基于搜索的编译优化工作提供了方法论基础。

### 8.2 创新点二：多目标成本函数与测试驱动的等价性验证

设计了多目标成本函数，同时编码正确性、性能和约束条件，使得搜索过程可以在多个目标之间自动权衡。使用测试用例（而非形式证明）来验证等价性的方法在实际中足够有效——在搜索过程中生成的候选程序中，虽然大部分是错误的，但那些通过测试集验证的候选程序在实际运行中很少出现错误。这种"测试驱动"的验证方法使得STOKE能够在缺乏完整的x86-64形式语义模型的情况下工作。

## 9. 局限性

**论文明确承认的局限：**
- 方法不完备——依赖测试而非形式证明。通过测试集验证的候选程序可能在未测试的输入上行为不一致，STOKE不能保证所有输入上的绝对正确性。
- 面向x86 loop-free binary，难以直接迁移到LLVM IR/RVV等更高级的表示或包含循环的程序。STOKE的搜索空间定义和提议分布都是x86-64特定的。
- 随机搜索开销和局部最优问题明显——对于超过20条指令的程序，搜索时间可能达到数小时甚至更长，且无法保证接近全局最优。
- 成本函数依赖x86指令延迟表的静态估算，无法准确反映现代超标量处理器的动态行为（乱序执行、缓存效应、分支预测等）。
- 无循环限制是根本性的——大多数有意义的程序包含循环和分支，但STOKE的搜索空间在这些构造下会变得不可控。

**阅读后发现的潜在局限：**
- 实验中使用的测试案例规模有限（主要是位操作和简单向量运算），在更复杂程序上的泛化性未经验证。
- 测试验证的完备性在实际部署中存在风险——对于安全关键系统，通过测试而非证明的验证方式可能不满足认证要求。
- 搜索效果高度依赖提议分布和超参数（温度、权重）的调优，可能存在"报告了调优后的最佳结果"而低估了实际使用中的调优成本。
- 对于现代x86-64处理器，单纯的指令延迟总和已经不能准确反映性能，乱序执行、微融合、缓存层次等因素使得静态性能估算的可信度降低。

## 10. 阅读后的研究方向反思

【分析内容】STOKE是目标后端智能体的历史基线：真实性能可以直接监督低级搜索，但CrossTune-RL要解决跨层IR动作如何影响后端空间。STOKE提醒我们，IR层"更少"并不等于机器码更快——STOKE发现的优化往往是利用了x86-64指令集的特殊特性（如地址计算指令的协同效应），这在IR指令数上是"增加"而非"减少"的。STOKE的MCMC搜索框架可以作为CrossTune-RL中Backend Agent的局部搜索策略的参考，但与STOKE的纯随机变换不同，Backend Agent的搜索应该由IR Agent的决策指导，而非纯随机提议。STOKE的局限性（无循环、局部最优、测试不完备）直接对应CrossTune-RL需要改进的方向：通过IR Agent提供高层指导、通过多架构扩展搜索范围、通过形式验证（Alive2）替代测试验证。STOKE的成本函数设计理念（多目标权衡）可以扩展到跨架构场景——在x86上优化延迟，在RISC-V上优化指令数，在ARM上优化功耗，通过参数化的成本函数适应不同架构的目标。

## 11. 可进一步尝试的研究方向

### 11.1 基于强化学习的搜索策略学习

#### 研究问题
STOKE的纯随机提议分布效率较低——大部分生成的候选程序是错误的或性能更差的。能否利用强化学习来学习一个"智能提议分布"，根据当前程序的特征有目的地生成高潜力的候选变换？

#### 与原论文的区别
STOKE使用固定的、与程序无关的提议分布（均匀随机的指令替换/插入/删除）。本方向通过学习一个策略网络来动态生成提议，使搜索更有方向性。

#### 可能的创新点
- 设计一个策略网络，以当前程序的表示（如指令嵌入）为输入，输出最优提议操作的概率分布
- 使用REINFORCE或PPO来训练策略网络，以搜索效率和最终性能作为奖励信号
- 将策略网络作为MCMC搜索的提议分布生成器，实现"学习引导的随机搜索"

#### 实验框架
在STOKE的测试基准上（Hacker's Delight、SAXPY等）训练策略网络，比较学到的提议分布和固定提议分布的搜索效率和最终优化质量。

#### 可行性
中。需要大量搜索数据来训练策略网络，但STOKE本身可以在离线状态下生成大量训练数据。

#### 主要风险
策略网络可能过拟合到训练集中的程序类型，在未见过的程序上泛化能力有限。

## 12. 与其他已读文献的关系

STOKE（第19篇）与Souper（第17篇）在处理粒度和方法论上形成鲜明对比：STOKE在x86-64二进制级别使用MCMC随机搜索，Souper在LLVM IR级别使用SMT引导的合成搜索。这两篇论文代表了超优化的两条主要技术路线——"随机搜索路线"和"形式合成路线"。Souper GitHub Repository（第18篇）是Souper的工程实现，与STOKE在方法论上无直接关联。Minotaur（第20篇）与STOKE在方法论上差异较大——Minotaur使用形式合成（类似Souper）而非随机搜索。STOKE的"通过测试验证等价性"方法与Minotaur的"通过Alive2形式验证等价性"方法形成对比，代表了两种不同的正确性保证思路。对于CrossTune-RL项目，STOKE的方法更适合作为Backend Agent中局部搜索策略的参考，而Souper/Minotaur的方法更适合作为验证基础设施。

| 核心问题 | 传统编译器Pass分解错失跨阶段联合优化机会，且手工规则难以覆盖所有可能的指令组合 |
| 核心方法 | MCMC随机搜索 + Metropolis-Hastings采样 + 多目标成本函数 + 测试驱动验证 |
| 使用模型 | 无（基于MCMC随机搜索） |
| 是否使用RL | 本文没有使用强化学习 |
| 是否使用形式验证 | 否——使用测试用例验证而非形式证明（方法不完备） |
| 主要指标 | 指令延迟总和、搜索收敛时间、与GCC O3的对比 |
| 最重要结果 | 在部分测试案例上达到或超越GCC -O3优化质量，甚至超越专家手写汇编 |
| 核心创新 | 首次将MCMC随机搜索应用于二进制级别超优化；多目标成本函数设计 |
| 主要局限 | 依赖测试验证（不完备）；局限于无循环代码；x86特定；搜索开销高 |
| 与RISC-V相关性 | 低——方法直接面向x86-64二进制，但搜索理念可迁移至RISC-V指令组合探索 |
| 最适合作为 | 后端搜索策略参考（随机关联搜索方法论基线） |

> STOKE通过MCMC随机搜索在x86-64 loop-free二进制上实现了达到甚至超越GCC -O3的超优化效果，验证了"IR层的指令数减少不等于后端性能提升"这一重要发现，但局限于无循环代码和测试验证的不完备性。STOKE的核心贡献在于提出了一种不依赖手工规则和Pass分解的随机优化范式，为后续基于学习的编译器优化工作奠定了方法论基础。
