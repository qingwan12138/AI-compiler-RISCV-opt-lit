## 1. 研究背景

本文研究生产级 WebAssembly（Wasm）到本地代码编译器中的指令选择验证。Wasm 为浏览器、操作系统和云服务中的不可信代码提供沙箱，但沙箱的实际安全性还依赖编译器把 Wasm 正确地编译为本地机器码。指令选择阶段把编译器中间表示映射为目标 ISA 指令；一条错误的 lowering（降级/指令映射）可能破坏功能正确性，甚至破坏沙箱保证（第 1 节）。

传统的全编译器形式化验证（例如 CompCert、CakeML）能提供很强保证，但工程代价高，且通常牺牲生产编译器需要的性能或可扩展性。针对工业指令选择器的局部验证更现实，但此前方法遇到三个瓶颈：Cranelift 的 ISLE 规则图很深、规则链路径很多；内存、陷阱、标志位等副作用难以用简单函数语义表示；手写的机器指令规格难以覆盖真实 ISA 的复杂细节。

Cranelift 使用 ISLE（Instruction Selection Lowering Expressions）领域特定语言，以项重写规则描述从 CLIF（Cranelift IR）到机器指令的映射。生产后端的规则链经常包含十条以上规则，直接逐条验证会遗漏组合行为，而枚举全部路径又会导致状态空间爆炸。因此，论文引入 Arrival，目标是在不把整套 Cranelift 重写为证明助手编译器的前提下，对真实后端进行端到端、高保证的指令选择验证。

## 2. 论文要解决的问题

### 2.1 如何覆盖深而复杂的指令选择规则链

每个 ISLE 规则单独正确，并不自动推出多条规则组合后的整条 lowering 路径正确。论文要解决的是：如何在规则数量多、存在中间项、优先级和潜在循环的情况下，对从 CLIF 到最终机器指令的组合路径进行验证，同时避免为每个中间项手写规格（第 2、3 节）。

### 2.2 如何高效表示状态性副作用

指令选择不只计算输出值，还可能读写内存、设置或依赖 AArch64 标志位、触发陷阱。若把完整机器状态和完整内存都交给 SMT 求解器，验证会变得昂贵；但忽略这些副作用又会漏掉真实错误。论文研究一种只建模与指令选择相关效果的轻量状态表示（第 4 节）。

### 2.3 如何获得可信且可扩展的机器指令语义

验证结果依赖机器指令规格。如果规格手写错误，验证器可能证明错误的规格而不是硬件语义。论文要解决如何从 Arm 提供的、以 ASL（Architecture Specification Language）描述的机器可读 ISA 规格中自动生成适合编译器验证的、简洁的 AArch64 指令族语义（第 5 节）。

### 2.4 如何把验证放入生产开发流程

验证工具不仅要“理论上能证明”，还要覆盖 Wasm 关键 lowering、减少开发者标注负担，并在普通工作站上达到 CI 或局部开发可接受的时间。论文把覆盖率、规格编写负担和运行时间作为三项评估问题（第 6 节）。

> 本文主要研究：如何利用规则链组合、轻量效果状态和权威 ISA 语义生成，把生产级 Cranelift Wasm-to-native 后端的指令选择验证扩展到更高覆盖率。

## 3. 核心方法概述

Arrival 是构建在 Cranelift/Wasmtime 之上的指令选择验证器。它读取 ISLE 指令选择规则，自动沿规则图构造若干可验证的规则链，把 CLIF 起点规格与由 ISA 语义得到的机器指令规格连接起来，再为每条展开路径形成语义等价验证条件。SMT 求解器（论文使用 cvc5 和 Z3）检查这些条件是否成立；若不成立，则给出反例或报告超时。

整体数据流如下：

```text
CLIF 指令规格 + ISLE 规则 + 外部谓词规格
                    ↓
       Arrival 规则链展开与类型/可适用性分析
                    ↓
       生成从 IR 到机器指令的端到端 expansion
                    ↓
   轻量状态效果建模：load/store/trap/flags 等
                    ↓
  Arm ASL → 部分求值 → 编码模板 → ISLE 机器语义
                    ↓
           为每条路径形成 SMT 验证条件
                    ↓
              cvc5 / Z3 求解与反例
                    ↓
      通过、失败、超时及可定位的错误报告
```

### 3.1 Rule chaining（规则链）

Arrival 在 ISLE 元编译器生成的 trie（规则匹配树）表示上进行规则链组合。它从一个带有规格的边界项开始，沿可链式调用的规则展开，直到遇到已有规格的项或配置的边界。类型推断、模式约束和不可满足路径剪枝用于减少展开数量；对标注了优先级的规则，工具可加入高优先级规则条件的否定，以保持规则优先级语义。开发者可以通过规格或 `veri_chain` 等属性控制链式展开，从而避开递归和路径爆炸。

论文指出，若不限制展开，AArch64 后端的规则组合可能超过 4.87 亿条；但 94% 的项并不属于这种“爆炸项”。可配置的边界使大多数普通中间项自动内联，同时保留对复杂项的人工控制（第 3 节）。

### 3.2 轻量状态效果模型

Arrival 不表示完整内存或完整处理器状态，而是让开发者声明少数全局效果变量。例如，`clif_load` 与 `isa_load` 表示两端是否发生加载，`clif_trap` 表示 CLIF 语义要求陷阱，AArch64 标志位则通过生产者输出与消费者输入的变量连接。每个项可以声明哪些效果变量被修改，并给出条件；验证条件检查 lowering 前后对应效果是否一致。

该模型可以表达除结果值外的 load、store、trap、flags 等关键副作用，同时避免对大地址化内存进行完整符号建模。论文用有符号除法的除零/溢出陷阱作为案例，说明效果模型如何让 Arrival 发现旧方法漏掉的错误。

### 3.3 从权威 ISA 语义自动生成规格

论文使用 Arm 的机器可读 ASL 规格。开发者用 Arrival 的 Rust 库配置指令族的编码字段、操作数和参数化方式；工具把符号指令族划分为编码模板，对每个模板进行部分求值，翻译寄存器、立即数、处理器状态以及内存访问，最后合并为简洁的 ISLE 规格。生成后还会枚举可能的具体编码，并与 Cranelift 的汇编器结果核对，以发现编码模板配置错误。

### 3.4 发现的具体错误

Arrival 在 AArch64 8 位和 16 位有符号除法 lowering 中发现一个失败的溢出检查：本应触发陷阱的输入被错误地编译成静默返回错误结果的机器码。该路径涉及 12 条 ISLE 规则、9 条相互依赖的机器指令和 5 个指令族；错误与条件比较的操作数位宽、NZCV 标志以及 `TrapIf` 伪指令之间的组合有关。Arrival 在尝试验证 `sdiv` 时不到 9 秒发现该错误（第 2.4 节）。

## 4. 实验框架与训练流程

### 4.1 系统执行流程

本文不涉及模型训练，主要采用静态规则分析、语义规格生成和 SMT 验证。执行过程是：

1. 选取 Wasm 编译器会生成的 CLIF 指令和 AArch64 ISLE 后端规则。
2. 使用 Arrival 读取规则 trie、进行类型推断和适用性检查。
3. 以配置的规格边界为起点，对规则进行链式展开，得到可验证的规则路径。
4. 将 CLIF 语义、内部 ISLE 语义、外部 Rust 谓词和自动生成的机器指令语义组合起来。
5. 对每个具体类型实例建立 SMT 验证条件，交给 cvc5 或 Z3。
6. 汇总验证通过、失败和超时，并用反例定位不一致行为。

### 4.2 语义规格准备

机器指令部分使用 ASL 语义自动生成；CLIF IR 和外部 Rust 项仍需规格。论文说明，CLIF 没有现成的完整形式语义，因此作者在能做到的地方根据 Wasm 规格逐行转写，其他情况结合实现检查和与开发者讨论完成。外部项和某些可信辅助组合子也需要手写规格。

### 4.3 运行配置

实验在 Intel i7-13700K 工作站上运行，处理器有 8 个性能核和 8 个能效核，共 24 个带超线程的线程。Arrival 支持多线程并行处理 expansions。SMT 后端使用 cvc5 和 Z3，并可按标签配置默认求解器或覆盖某些项。论文没有使用 SFT、PPO、GRPO、强化学习、LLM 工具调用或多阶段模型训练。

## 5. 奖励函数、损失函数或关键公式

本文没有使用强化学习，因此不存在强化学习奖励函数，也没有神经网络损失函数。论文的核心目标不是训练模型，而是检查每条 lowering 路径的语义保持。

可将论文的验证目标概括为以下逻辑关系（这是对论文验证条件的文字化表达，不是论文新增公式）：

```text
对于每条可适用的规则链 expansion：
    机器指令语义 ∘ 规则链语义  ≡  CLIF 起点语义
```

其中：

| 符号/概念 | 含义 |
| --- | --- |
| `CLIF` | Cranelift 中间表示层的输入操作及其规格 |
| `ISLE rule chain` | 从输入项到机器指令项的一组重写规则 |
| `machine semantics` | 由 Arm ASL 规格生成的 AArch64 指令语义 |
| `state effects` | load、store、trap、NZCV flags 等被抽象跟踪的副作用 |
| `VC` | 为某一 expansion 形成的 SMT 验证条件 |

若语义等价条件可证，则该路径在所建模的规格范围内通过；若不可证，求解器可以给出反例；若在给定超时内无法决定，则记为 timeout。论文没有定义奖励稀疏、奖励冲突或奖励投机问题。

## 6. 实验设置

### 6.1 数据集来源

本文不是数据集或训练集论文。输入是 Wasmtime 的 Wasm-to-CLIF 编译路径和 Cranelift AArch64 指令选择后端中的 ISLE 规则。验证范围针对 Wasm 核心指令集，重点是 Wasm 1.0 core 相关 lowering，覆盖整数运算、非原子内存 load/store、浮点运算以及转换，并包含部分 Cranelift 对 8 位和 16 位整数的扩展。

论文报告验证范围有 6,212 个不同规则链 expansion。经过类型推断和可适用性检查后，有 10,834 个可适用的类型实例进入验证；其中 10,807 个完成验证，27 个在 4 小时求解器超时限制下超时。论文没有把这些输入称为传统意义上的训练/验证/测试数据集，也没有报告随机数据集划分或数据泄漏分析。

### 6.2 模型与工具

| 项目 | 论文中使用的内容 |
| --- | --- |
| 编译器 | Wasmtime/Cranelift 生产级 Wasm-to-native 编译器 |
| 指令选择 DSL | ISLE（Instruction Selection Lowering Expressions） |
| 目标 ISA | AArch64；论文讨论 RISC-V Sail，但没有在本文实验中验证 RISC-V 后端 |
| ISA 规格 | Arm 机器可读 ASL；通过 ASLp/SymASLp 风格的部分求值获得简洁语义 |
| SMT 求解器 | cvc5、Z3 |
| 实现语言/库 | Arrival 的 Rust 库与 Cranelift 集成 |
| 处理器 | Intel i7-13700K，8 个性能核、8 个能效核、24 个超线程线程 |
| 机器学习模型 | 无；论文中未使用 LLM 或神经模型 |

论文配置了 559 个 AArch64 指令，分布在 39 个指令族中；生成的规格包含 12,608 行 ISLE 规格，开发者用于参数化这些指令族的配置约 1.9K 行。

### 6.3 对比方法

主要对比是先前的 Crocus ISLE 验证工作。Crocus 需要手写机器指令规格，不能表达状态性副作用，要求逐条规则验证，因此没有达到 Arrival 的端到端深度。论文还在相关工作中比较了 CompCert、CakeML、Alive2、TurboTV、RGFuzz、Hydra、Islaris 等方向，但实验中的定量覆盖率和规格负担对比重点是 Crocus。

### 6.4 评价指标

| 指标 | 含义 | 方向 |
| --- | --- | --- |
| Verification coverage | 可验证的规则链/类型实例及 Wasm 关键 lowering 覆盖范围 | 越大越好 |
| Verified paths | 在给定条件下完成证明的不同 expansion 数量 | 越大越好 |
| Timeout count | SMT 在规定时间内未完成的实例数量 | 越小越好 |
| Specification burden | 需要开发者手写的 term specification 数量和代码量 | 越小越好 |
| Automation rate | 使用 Arrival 自动化辅助的规格比例 | 越大越好 |
| Verification time | 全量或局部验证运行耗时 | 越小越好 |
| Bug finding | 发现真实或人为注入错误的能力 | 定性/案例验证 |

## 7. 实验结果与结论

### 7.1 主要结果

Arrival 对 6,212 个规则链 expansion 产生 10,834 个可适用类型实例；其中 10,807 个完成验证，27 个超时，占 0.2%。验证对象覆盖 Wasm 相关的全部整数数值操作、非原子内存 load/store、浮点数值操作和转换，但论文列出了常量池、部分递归规则及 Wasm 中尚未覆盖的栈/控制流等例外。

Arrival 发现了一个旧工作遗漏的 AArch64 有符号除法溢出检查错误。该错误不是单条规则的简单错误，而是 12 条规则、状态性陷阱、条件标志和多条机器指令组合后才暴露的行为，说明端到端规则链与状态建模确实改变了可发现的错误类别。

### 7.2 与传统/先前验证方法比较

相较 Crocus，Arrival 的覆盖更深更广：覆盖了内存和浮点 lowering，能够处理陷阱等状态行为，并将验证推进到机器代码 IR。论文给出的规模比较是：Arrival 覆盖的规则数量约为先前工作的 3.3 倍，类型实例数量约为 29.2 倍；这些是验证范围的规模比较，不是运行速度提升。

### 7.3 规格负担结果

在验证子集所需的 410 个 term 规格中，60% 得到 Arrival 某种自动化帮助。在其中 266 个可以自动化的项里，93% 实现了自动化。机器指令项中，3 个规格需要手写，39 个项通过自动化覆盖 93% 的规格情况；中间项中，116 个因规则链自动内联而不必单独手写，95 个 ISLE 类型项由工具综合规格。CLIF IR 的 60 个项和外部项的 84 个项仍全部需要手写，因为缺少可直接使用的正式规格。

与 Crocus 需要为 410 个项全部手写规格的估算相比，Arrival 需要的手写规格约少 2.6 倍；Arrival 以多写 24 个手写规格为代价，取得了更广的覆盖。

### 7.4 运行时间结果

在全量运行中，论文设置的求解器超时为 4 小时；27 个实例超时，但绝大多数查询在几秒内完成。使用 cvc5、60 秒超时和并行工作站时，全量运行耗时 10.06 分钟，超时实例增加到 55 个，但总体覆盖接近全量高超时配置。图 5 显示，大多数单个类型实例在 5 秒以内完成。论文据此认为定时 CI、夜间/每周全量验证和受影响规则的 pull request 检查是可行的；这不是对所有硬件或所有后端的性能保证。

### 7.5 案例分析

有符号除法案例中，Arrival 发现 8 位和 16 位输入的溢出检查错误；旧 Crocus 之所以漏掉它，一是手写规格不能表达完整状态性陷阱，二是没有链式组合所有规则，三是错误的 `trap_if_div_overflow` 手写规格本身没有反映实际错误，而 Arrival 的机器语义来自权威 ISA 规格。

## 8. 主要创新点

### 8.1 创新点一：面向生产指令选择器的规则链验证

现有逐规则验证要求开发者为大量中间项写规格，且不能保证跨规则组合正确。Arrival 自动构造规则链 expansion，在开发者指定的边界和中间规格之间推导完整路径，从而验证 CLIF 到机器指令的端到端组合行为。规则链是减少手写负担并发现组合型错误的关键机制；6,212 个 expansion 和发现 `sdiv` 错误的结果支持其价值。

### 8.2 创新点二：面向指令选择的轻量状态效果模型

论文没有对完整内存和完整处理器状态做重型符号执行，而是声明少量与指令选择相关的效果变量，并描述它们何时被修改。这种设计让 load/store、trap、flags 等关键副作用进入验证范围，同时控制 SMT 成本。它不是一般意义上对所有编译器状态的完整建模，适用性依赖于目标后端可被少量效果变量充分表达。

### 8.3 创新点三：从厂商 ISA 规格自动生成编译器可用的指令语义

Arrival 将 Arm ASL 的高保证来源与编译器所需的符号寄存器、符号立即数和指令族语义连接起来，并通过编码模板和汇编器一致性检查避免部分配置错误。论文声称这是首次把自动生成的、来自厂商权威硬件规格的语义用于这一类编译器验证；实验中 93% 的机器指令规格由 ISA 语义自动生成，减少了信任手写规格的风险。

### 8.4 工程实现与真正创新的区分

使用 Rust、Cranelift、SMT 或 ASL 本身不是创新。论文真正的贡献在于把这些部件组织成可扩展的规则链验证管线，并为状态副作用与符号指令族提供特定机制。论文的 AArch64 实验是对该机制的验证，不应解读为已经支持所有 ISA 或已经证明整个 Cranelift 编译器正确。

## 9. 局限性

### 9.1 论文明确承认的局限

* 论文只实测 Cranelift AArch64 后端。作者说明 RISC-V 已有 Sail 正式规格，但 RISC-V 在 Cranelift 中使用较少且属于 Tier 3 目标，因此未纳入本文实验。
* Cranelift 常量池没有建模，导致 `off64const` 的一个 lowering 无法验证。
* 少数场景为避免递归，作者与 Cranelift 工程师合作重构了 ISLE 规则；这会改变被验证的规则结构。
* 验证范围依据 Wasm 到 CLIF 转换器可达的 IR 项；Cranelift 中端优化后可能出现更大的可达项集合，因此这些新增项不一定被覆盖。
* 仍有 Wasm core 的栈、控制流以及 Wasm 1.0 之外的 SIMD 等功能没有被完整覆盖。
* 27 个实例在 4 小时求解器超时下未完成；除法、余数和 population count 是较难的求解类别。
* CLIF IR 缺少完整正式语义，部分规格依赖实现检查和开发者讨论；外部 Rust 项和一些辅助组合子仍是可信手写部分。
* AArch64 两类复杂逻辑立即数编码和伪指令不能通过当前 ISA 生成管线自动化，仍需手写规格。

### 9.2 阅读后发现的潜在局限

* “通过”只针对论文定义的 CLIF、ISLE、状态效果和 ISA 规格关系，不等同于整个 Wasmtime、操作系统环境或所有微架构上的端到端安全证明。
* 轻量状态抽象减少 SMT 成本，但如果某个后端错误依赖未声明的内存别名、异常、缓存或微架构状态，抽象可能无法表达该错误；论文没有声称覆盖这些行为。
* 93% 的机器指令规格自动化并不意味着 93% 的全编译器语义自动化，因为 CLIF 与外部项仍需要手工规格。
* 论文主要报告验证覆盖、规格负担和求解时间，没有把 Arrival 与真实硬件执行速度或编译生成代码质量作性能比较。
* 将方法迁移到 RISC-V 需要处理 Sail 语义、向量/特权/内存模型和 Cranelift 后端结构的具体差异，不能只替换 ISA 名称就视为完成迁移。

## 10. 阅读后的研究方向反思

Arrival 对“大语言模型与编译器优化、LLVM IR、RISC-V、多架构优化”的直接启发主要在可靠性基础设施，而不是 LLM 训练。规则链的端到端验证边界、自动生成的 ISA 语义和轻量副作用模型，可以作为 LLM 生成或选择编译变换后的验证层。

值得借鉴的是：让生成/优化系统输出可被编译器和 SMT 验证的中间结果；把正确性反馈定位到完整变换链而不是单个局部规则；从可信硬件规格自动派生后端语义。不能直接照搬的是 AArch64 的 ASL 配置、Cranelift 的 ISLE trie 和 Wasm 的状态变量设计。

如果只把 AArch64 换成 RISC-V，创新性有限。更有研究价值的问题是：如何把 RISC-V Sail、RVV 向量状态、可变向量长度和 LLVM/MLIR lowering 的多级 IR 连接起来，并保持规则链验证可扩展；或者让 LLM 提议变换，再由 Alive2/等价检查与 ISA 级 Arrival 风格验证共同筛选。本文更适合作为验证工具模块和可靠性 baseline，而不是完整的 LLM 编译优化框架。

## 11. 可进一步尝试的研究方向

### 11.1 RISC-V Sail 驱动的 LLVM 后端指令选择验证

#### 研究问题

能否从 RISC-V Sail 自动生成适合 LLVM GlobalISel 或 SelectionDAG 指令族的简洁机器语义，并验证 LLVM IR 到 RV64/RVV 指令选择的端到端路径？

#### 与原论文的区别

目标从 Cranelift ISLE/AArch64 改为 LLVM 多级后端，并需处理 RVV 的 VL、VTYPE 和可变向量长度状态，而不是简单替换目标 ISA。

#### 可能的创新点

为 SelectionDAG/GlobalISel 规则建立可控的规则链切分；将 RVV 向量状态加入轻量效果模型；评估 Sail 语义与 LLVM 后端机器描述的一致性。

#### 实验框架

```text
LLVM IR/SelectionDAG
        ↓
GlobalISel 或 SelectionDAG 规则链展开
        ↓
RV64/RVV 状态效果抽象
        ↓
Sail 语义生成机器指令规格
        ↓
SMT 翻译验证与错误反例
```

#### 可行性

需要 RISC-V Sail 模型、LLVM 后端规则、SMT 连接层和一组可达 lowering；论文已指出 Sail 是可用的正式规格来源。

#### 主要风险

RVV 状态和内存模型可能无法由少量变量充分表达；LLVM 规则图的优先级、隐式约束和多级合法化可能导致路径爆炸。

### 11.2 LLM 变换与双层验证闭环

#### 研究问题

LLM 生成 LLVM IR 优化候选后，能否同时用 IR 级等价验证和目标 ISA 指令选择验证过滤错误候选？

#### 与原论文的区别

Arrival 本身没有 LLM，也不生成优化候选；新方向把 Arrival 风格后端证明作为生成式优化系统的安全约束。

#### 可能的创新点

构造分层反馈：Alive2 负责 IR 语义，后端验证器负责 lowering/ISA 语义；用反例精确修复候选，而不是只根据运行测试奖励。

#### 实验框架

```text
LLVM IR
  ↓
LLM 生成候选优化
  ↓
Alive2/等价检查
  ↓ 通过
LLVM 后端指令选择验证
  ↓
真实硬件或仿真性能评估
```

#### 可行性

可复用已有 LLM 优化候选生成器、Alive2、LLVM 后端和 SMT 工具；Arrival 的状态建模提供后端验证设计参考。

#### 主要风险

验证成本可能使候选吞吐量过低；IR 等价不一定保证目标微架构性能提升；反例格式需要适配 LLM，且不能把有限验证误称为全局证明。

### 11.3 基于验证反例的编译器 fuzzing 交叉检查

#### 研究问题

能否将规则链验证器产生的语义反例与 rule-guided fuzzing、差分测试结合，以覆盖 SMT 难以证明或超时的 lowering？

#### 与原论文的区别

原论文侧重对给定路径建立证明；新方向在超时和模型边界处加入动态执行、随机输入和多后端差分。

#### 可能的创新点

利用验证器知道的规则链结构定向生成触发状态副作用的输入；对通过验证器抽象但真实执行不一致的候选进行模型审计。

#### 实验框架

```text
规则链与 SMT 反例/超时信息
          ↓
状态敏感输入生成
          ↓
多个编译器后端/模拟器/真实硬件
          ↓
差分结果与崩溃归因
          ↓
回灌规则规格或验证边界
```

#### 可行性

论文已展示 Arrival 能快速给出人为错误的反例，并引用 RGFuzz 作为互补工作；因此组合具有明确工具基础。

#### 主要风险

动态差分测试只能发现有限输入上的错误，不能替代形式验证；不同后端的未定义行为、浮点和环境差异会产生误报。

## 12. 与其他已读文献的关系

本 slot-3 本轮只完成这一篇 OOPSLA 2025 论文，尚无可在本节进行事实性横向比较的同批已读论文。因此不能虚构其他论文之间的组合关系。

从论文自身引用关系看，Arrival 与 Crocus 的任务最接近：二者都验证 Cranelift 的 ISLE 指令选择，但 Arrival 增加了规则链、状态效果和自动 ISA 规格，覆盖更深。与 Alive2 相比，Arrival 面向后端指令选择和机器 ISA；Alive2 主要面向 LLVM IR 中端变换的翻译验证。与 RGFuzz 相比，Arrival 提供形式化验证条件，而 fuzzing 提供动态测试，两者可以互补。与 Hydride 相比，Arrival 验证既有生产后端，Hydride 更侧重从 ISA 语义综合可重定向编译器组件；本文没有把 Arrival 当作代码生成器。

## 13. 一页式总结

| 项目 | 内容 |
| --- | --- |
| 论文研究任务 | 验证生产级 Cranelift Wasm-to-native 后端的指令选择正确性 |
| 核心问题 | 规则链深、状态副作用复杂、机器指令规格手写负担高 |
| 输入 | CLIF 规格、ISLE 规则、外部项规格、Arm ASL ISA 规格 |
| 输出 | 端到端规则链 expansion 的 SMT 验证结果与反例 |
| 核心方法 | Rule chaining、轻量状态效果模型、ASL 驱动机器语义生成 |
| 使用的模型 | 无机器学习模型、无 LLM |
| 使用的编译器工具 | Cranelift/Wasmtime、ISLE、Arrival |
| 是否使用强化学习 | 否 |
| 是否使用形式化验证 | 是，SMT 语义验证 |
| 数据集规模 | 6,212 个 expansion；10,834 个可适用类型实例 |
| 主要指标 | 覆盖率、验证通过数、超时数、规格自动化率、求解时间 |
| 最重要实验结果 | 10,807 个实例完成验证，27 个超时；发现旧工作漏掉的 AArch64 有符号除法错误 |
| 核心创新 | 跨多条 ISLE 规则的端到端验证；轻量副作用建模；从权威 ASL 自动生成规格 |

| 最适合作为 | 编译器后端验证工具模块、RISC-V/LLVM 后端验证的 baseline 和方法参考 |

这篇论文最值得学习的是：把规则链组合、状态副作用和权威 ISA 语义放进一个可运行的生产验证闭环；最主要的局限是验证范围仍受后端、状态抽象和手写 CLIF 规格约束。如果用于后续研究，合理方式是将其作为 LLVM/RISC-V 后端正确性基础设施，再与 LLM 优化候选生成、IR 级翻译验证或定向 fuzzing 组合，而不是简单地把 AArch64 名称替换为 RISC-V 就宣称形成新方法。
