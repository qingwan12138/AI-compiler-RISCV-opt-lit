# Cpp2Rust 文献阅读总结

论文题目：**Cpp2Rust: Automatic Translation of C++ to Safe Rust**

作者：Lucian Popescu、Francisco Gouveia、Henrique Preto、João Silveira、Dmytro Hrybenko、José Fragoso Santos、Nuno P. Lopes

发表时间：2026

发表平台：Proceedings of the ACM on Programming Languages, Volume 10, Issue PLDI, Article 188

论文链接或编号：DOI 10.1145/3808266；[作者论文页](https://web.ist.utl.pt/nuno.lopes/pubs.php?id=cpp2rust-pldi26)

关键词：C++ 到 Rust 翻译、内存安全、源到源优化、所有权、指针算术、LLVM

> 本文档用于文献阅读、组会汇报和后续研究分析。论文事实与阅读后的研究思考严格分开。

## 1. 研究背景

论文研究 C++ 遗留程序向内存安全 Rust 的自动迁移。C/C++ 的指针、释放和数据竞争会造成空间/时间内存安全问题；手工重写规模大、易引入语义错误，且 Rust 的静态所有权与可变性规则不能直接表达任意 C++ 别名关系（第 1 节）。已有 C2Rust 主要生成含 `unsafe` 原始指针的 Rust，因此不能消除原程序的大部分风险。论文的基本取舍是先保证生成代码属于 safe Rust，再通过源到源优化逐步回收性能。

## 2. 论文要解决的问题

### 2.1 自动生成 safe Rust

如何将一个包含指针、数组、类、虚调用、模板和部分 STL 的 C++ 子集机械翻译为功能等价且不输出 `unsafe` 的 Rust。

### 2.2 降低安全翻译的运行时开销

直接把每个变量包装为 `Rc<RefCell<T>>` 会把所有权和可变性检查推迟到运行时。论文设计 `Rc`、`RefCell`、`Option` 三类消除分析，在不改变语义的条件下移除不必要包装。

> 本文主要研究：如何在保持 C++ 可观察行为和内存安全的约束下，自动生成 safe Rust，并用可证明保守的源到源优化减少动态检查。

## 3. 核心方法概述

Cpp2Rust 直接从 Clang AST 机械生成 Rust，再运行独立的 Rust 源到源优化器。变量通常映射为 `Value<T> = Rc<RefCell<T>>`；普通指针映射为带偏移量和弱引用的 `Ptr<T>`，虚类指针映射为 `PtrDyn`。弱引用避免指针延长对象寿命，从而保持 C++ 析构时机。翻译器保证生成程序不含 `unsafe`（运行时库中的 `Ptr::delete` 有受控的内部 `unsafe`）。

```text
C++ 源程序
    ↓ Clang AST
机械翻译：safe Rust + Value/Ptr/PtrDyn 运行时库
    ↓
Rust 源到源优化：Rc 消除 → RefCell 消除 → Option 消除，迭代到不动点
    ↓（可选人工修改后再次优化）
rustc/LLVM 编译
    ↓
可执行程序与差分测试结果
```

## 4. 实验框架与训练流程

本文不涉及模型训练、SFT 或强化学习；主要采用基于 AST 的翻译算法、静态源到源分析和运行时测试。

### 4.1 翻译流程

类型、表达式和语句分别由规则函数映射。局部变量先装箱；函数参数以原始类型传入、在函数入口装箱，以便后续过程内优化。C++ 标准库调用通过一个内部 DSL 描述映射。

### 4.2 优化流程

优化器对每个函数做保守的 over-approximation 分析：先建立可消除集合，再遇到别名、方法调用或函数边界时移除不安全候选；完成一类重写后继续下一类，直到固定点。论文明确指出把 `Ptr<T>` 全局改成原生 Rust 引用仍留作未来工作。

### 4.3 正确性检查

论文用 Rust 编译器的类型系统承载内存安全论证，并在 WOFF2、Brunsli 上进行单元测试、差分测试和字节级输出比较；这不是对所有任意 C++ 程序的自动形式化证明。

## 5. 奖励函数、损失函数或关键公式

本文没有使用强化学习奖励函数。核心是三类过程内判定条件：

| 分析 | 可消除条件的要点 |
|---|---|
| `Rc` 消除 | 不调用 `Rc` 专有方法、不创建新引用、不把变量传入函数 |
| `RefCell` 消除 | 只使用 `borrow/borrow_mut`，且不跨函数传递；生成代码不会产生重叠借用 |
| `Option` 消除 | 不赋值为 `None`，且除 `unwrap` 外不调用其他 Option 方法 |

论文的正确性目标是行为 refinement：对无 UB 的 C++ 轨迹，Rust 轨迹结构上保持对应行为；对 C++ UB 轨迹，Rust 的 panic 等行为属于允许的 refinement。论文没有给出一个覆盖全部 C++ 特性的机械定理证明。

## 6. 实验设置

### 6.1 数据集来源

论文使用两个真实 C++ 程序：WOFF2 字体压缩库（库约 4.6k 行，另有三个命令行程序）和 Brunsli 无损 JPEG 压缩工具。WOFF2 的实验压缩 128 个常见 TTF 字体并解压；Brunsli 压缩 100 张图像。论文还比较了 WOFF2 的 Google 手工 Rust 移植。

### 6.2 模型与工具

Cpp2Rust 是基于 Clang AST 的 C++ 工具，约 8.1k 行 C++；运行时库约 1.5k 行 Rust；源到源优化器约 3.6k 行 Rust，使用 `syn` 和 `prettyplease`。实验服务器为 Intel Xeon E5-2630 v2、64 GB RAM、Debian 12；使用 clang 20、rustc 1.89、LLVM 20 后端、Brotli 0.6.0 和对应 Rust crate。

### 6.3 对比方法

主要比较原始 C++、Cpp2Rust safe Rust、Cpp2Rust safe Rust 加优化器、再加 Clippy，以及 Cpp2Rust 的 unsafe Rust 上界；WOFF2 还与 Google 手工 Rust 版本比较。

### 6.4 评价指标

运行时间、峰值内存、二进制大小、生成代码行数，以及压缩/解压输出是否字节一致。运行时间重复 15 次，去掉两个极值后取平均。

## 7. 实验结果与结论

### 7.1 WOFF2

表 1 中，C++ 压缩/解压为 94.1/2.4 秒；safe Rust 为 103.4/5.9 秒；加入优化器后为 98.5/2.9 秒；再加 Clippy 后为 95.8/3.2 秒。优化器移除了 642 个 `Rc`/`RefCell` 使用（占总数 71%）。safe Rust 的峰值内存为 47.2 MB，优化后 46.0 MB；二进制从 C++ 的 1.2 MB 变为 safe Rust 的 1.7 MB，优化后 1.5 MB。

### 7.2 Brunsli

表 2 中，C++ 压缩 100 张图像耗时 5.3 秒，safe Rust 为 272.4 秒；优化后为 33.0 秒，仍明显慢于 C++。优化器移除了 87% 的 `Value<T>` 包装，但优化后仍有 39% 的执行时间花在 `Ptr<T>::deref`。这说明指针算术是该方法的主要剩余瓶颈。

### 7.3 正确性与人工移植比较

WOFF2 的压缩输出与 Rust 输出逐字节匹配，解压结果与原始 TTF 一致；测试曾发现运行时 `memcpy` 对多字节类型的端序 bug。机械翻译只需几秒，而论文报告 Google 手工移植的机械工作约 12 天、进一步惯用化约 8 天；性能和工程差异不能简单归因于翻译器本身。

## 8. 主要创新点

### 8.1 以 safe-first 方式处理不可判定的所有权迁移

论文不先生成 unsafe 指针再修补，而是用运行时引用计数、可变性检查和弱指针直接生成 safe Rust；价值在于把安全作为默认不变量，代价是运行时开销。

### 8.2 面向生成代码的三阶段源到源优化

`Rc`、`RefCell`、`Option` 的固定点消除把保守翻译与性能恢复分离。实验显示它显著改善两个案例，但目前主要是过程内分析，不能消除所有 `Ptr` 开销。

### 8.3 对复杂 C++ 特性的统一运行时表达

`Ptr<T>` 的偏移量、弱引用和数组共享引用计数同时覆盖指针算术、数组衰减和析构时机；`PtrDyn` 则承载纯虚类的动态派发。这是工程化翻译设计，而不是 LLM 或新型优化搜索方法。

## 9. 局限性

### 论文明确承认的局限

不支持 union、volatile、goto、异常、位域、placement new、用户自定义拷贝/移动构造、多继承、含字段的基类和多线程代码；模板采用完全实例化，可能产生代码重复；`Ptr` 到原生 Rust 引用的全局优化留作未来工作。

### 阅读后发现的潜在局限

实验只有两个程序，不能据此推断所有 C++ 项目都能保持类似性能。Rust 类型安全不等同于完整功能等价，论文的 refinement 论证依赖受支持子集和运行时库假设。Brunsli 的 6 倍级别慢速表明跨函数指针和复杂别名仍可能使结果难以实用；也没有 RISC-V 或真实多架构实验。

## 10. 阅读后的研究方向反思

值得借鉴的是“先保证语义/安全，再做保守优化”的分层结构，以及用共享运行时表示复杂跨语言内存语义。若迁移到 LLVM IR 或 RISC-V，仅替换后端并不足以构成创新；需要研究 RISC-V 特定 ABI、向量指针语义、后端寄存器压力或可验证的跨 ISA 细化关系。Cpp2Rust 更适合作为传统 source-to-source translator 的 baseline 和安全迁移工具模块，而不是 LLM 编译优化主线的完整框架。

## 11. 可进一步尝试的研究方向

### 11.1 面向 RVV 的 safe-first 指针/向量迁移

#### 研究问题

如何把含数组切片和指针算术的 C/C++ kernel 翻译为安全 Rust，再映射到 RISC-V Vector Extension（RVV）而不破坏别名和边界语义。

#### 与原论文的区别

研究对象加入向量长度无关执行、尾部处理和 RVV ABI，不只是换目标架构。

#### 可能的创新点

把安全指针证明条件与向量化合法性、寄存器压力代价模型联合起来。

#### 实验框架

```text
C/C++ kernel → 安全中间表示 → safe Rust/RVV lowering → Spike或真实RVV板卡 → 差分与性能验证
```

#### 可行性与主要风险

需要 LLVM/Rust 后端、RVV 模拟器或硬件和基准程序集；风险是动态指针检查会抵消向量化收益，且 C++ 未定义行为边界复杂。

### 11.2 跨函数 Ptr 消除的全程序分析

#### 研究问题

能否用上下文敏感别名、生命周期和逃逸分析，将剩余 `Ptr<T>` 安全降级为 Rust 原生引用。

#### 与原论文的区别

从过程内固定点优化扩展到跨函数、递归和容器边界，同时输出可审计的失败原因。

#### 可能的创新点

将安全性保持条件与优化收益估计结合，形成可解释的选择性重写。

#### 实验框架

```text
生成 safe Rust → 全程序调用图/别名分析 → 候选引用化 → 编译与差分测试 → 回滚不安全候选
```

#### 可行性与主要风险

需要 Rust MIR/LLVM 分析和大型 C++ 案例；风险是不可判定区域过多，保守分析可能几乎不产生收益。

## 12. 与其他已读文献的关系

Cpp2Rust 与本批 SAIL 都把生成过程与验证/约束分离，但 Cpp2Rust 是确定性的传统翻译器，SAIL 是 LLM 生成抽象变换器。Cpp2Rust 可作为跨语言迁移与安全运行时 baseline；SAIL 更适合作为形式验证驱动的 GENERATOR 方向参考。两者不能直接组合成“LLM 自动翻译 C++”的结论，因为 Cpp2Rust 的安全保证来自明确的翻译规则和 Rust 类型系统，而非语言模型输出。

## 13. 一页式总结

| 项目 | 内容 |
|---|---|
| 论文研究任务 | 自动将 C++ 子集翻译为 safe Rust |
| 核心问题 | 所有权/别名不可判定与安全代码性能开销 |
| 输入 | C++ AST |
| 输出 | safe Rust、运行时库和可执行程序 |
| 核心方法 | `Value/Ptr/PtrDyn` 运行时 + 三类源到源消除 |
| 使用的模型 | 无 LLM；Clang AST、Rust 工具链 |
| 使用的编译器工具 | Clang 20、rustc 1.89、LLVM 20、Clippy |
| 是否使用强化学习 | 否 |
| 是否使用形式化验证 | 有 refinement 论证，但案例正确性主要用测试/差分验证 |
| 数据集规模 | WOFF2、Brunsli；128 个字体、100 张图像 |
| 主要指标 | 时间、内存、二进制大小、代码行数、输出一致性 |
| 最重要实验结果 | WOFF2 优化后压缩约比 C++ 慢 2%，Brunsli 优化后仍约慢 6 倍 |
| 核心创新 | safe-first 翻译与可复用运行时/源到源优化 |
| 主要局限 | 支持子集有限，复杂指针仍昂贵，案例数少 |
| 与 RISC-V 研究的相关性 | 中：可借鉴安全 lowering，但论文未评估 RISC-V |
| 最适合作为 | 传统安全翻译 baseline、运行时与优化器模块 |

这篇论文最值得学习的是把安全不变量放在翻译起点，再用保守分析回收性能；最主要的局限是复杂指针算术和跨函数别名仍造成高开销。如果用于后续研究，合理方式是把它作为安全跨语言/跨 ISA baseline，而不是简单替换后端就宣称完成新的 RISC-V 优化。
