# Judging Code Efficiency 文献阅读总结

论文题目：**Rethinking Code Refinement: Learning to Judge Code Efficiency**

作者：Minju Seo、Jinheon Baek、Sung Ju Hwang

发表时间：2024

发表平台：Findings of EMNLP 2024

论文链接或编号：ACL Anthology 2024.findings-emnlp.645

关键词：代码效率判别、运行时间预测、代码精炼、分类、回归

> 本文档基于 PDF 全文整理。

## 1. 研究背景

人或 LLM 修改代码后不一定更快，而每次都执行新旧版本成本高。作者将问题从“直接生成优化代码”改写为“给定修改前后代码，先判断哪一个更高效以及提升多少”。

## 2. 论文要解决的问题

对 human-human、human-machine、machine-machine 三种修改来源，训练 Code LLM 在不执行代码时分类更快版本或回归相对提升，并考察跨语言泛化。

> 本文主要研究：如何学习一个廉价的代码效率判别器，为代码精炼过程预筛选候选。

## 3. 核心方法概述

```text
原代码 c + 修改代码 c'
        ↓
拼接输入 Code LLM
        ↓
分类：A/B 哪个更快
或回归：预测 c' 相对提升
```

训练标签来自真实执行时间，而推理阶段无需执行。

## 4. 实验框架与训练流程

作者使用既有人类代码编辑数据，并用 DeepSeek-Coder-Instruct-7B 继续生成 human-machine 和 machine-machine 修改。主判别器基于 DeepSeek-Coder-Instruct-1.3B 微调；同时测试 7B。本文是监督学习，不涉及强化学习或工具反馈迭代。

## 5. 奖励函数、损失函数或关键公式

```text
分类损失：L = -log p(正确的 A/B 标签 | 原代码, 修改代码)
效率目标：Exec(c) > Exec(c') 表示修改后更快
```

回归任务预测相对运行时间改善，并用 Spearman 等级相关系数评估。本文没有强化学习奖励函数。

## 6. 实验设置

### 6.1 数据集来源

包含 Python、C++，并额外测试 Ruby、Perl、Rust；覆盖 H-H、H-M、M-M。PDF 未在正文主表附近明确给出完整样本总数。

### 6.2 模型与工具

DeepSeek-Coder-Instruct-1.3B/7B；另以 GPT-3.5、GPT-4o、CodeQwen、Granite 作比较或数据生成。

### 6.3 对比方法

Zero-shot、few-shot、带/不带 CoT 的提示，以及未微调的 GPT-3.5/GPT-4o。

### 6.4 评价指标

分类准确率、Spearman 相关系数；“Easy”子集要求两代码效率差超过 10%。

## 7. 实验结果与结论

1.3B 判别器在 Python+C++ 全集准确率 64.42%，Easy 为 72.86%，高于 GPT-4o 的 57.75%/62.49%。回归在合集上的相关系数 0.56、转成类别后的准确率 68.87%；Easy 为 0.66/81.17%。模型在效率差异更大时更准，并能一定程度迁移到 Ruby、Perl、Rust。三种修改来源中，人类修改的代码更容易判断；机器修改的效率改善与退化比例相近。

## 8. 主要创新点

### 8.1 把效率判别定义成独立学习任务

不要求模型直接优化，而是学习比较代码对，适合用作搜索或生成系统的候选预筛器。

### 8.2 同时覆盖分类与相对提升回归

既回答“哪个更快”，也尝试估计提升幅度。

### 8.3 跨修改来源和跨语言验证

揭示修改主体和语言对判别难度的影响。

## 9. 局限性

论文明确主要训练/验证集中于 Python、C++，效率只以运行时间衡量，未纳入内存、I/O、OS 和硬件。阅读后还应注意：静态判别不具备可靠安全门控能力；准确率约 64% 仍不足以单独决定部署；运行时间标签可能依赖测量环境。

## 10. 阅读后的研究方向反思

该模型可作为昂贵编译和真机测量前的排序器，但不能替代实测。若用于编译器优化，新问题应是学习不确定性和跨硬件校准，而不是简单把输入换成 LLVM IR。

## 11. 可进一步尝试的研究方向

### 11.1 带拒判机制的硬件条件效率判别器

#### 研究问题

模型何时应承认无法可靠判断并交给真实执行。

#### 与原论文的区别

增加目标硬件特征、置信度校准和 abstention（拒判）。

#### 可能的创新点

不确定性驱动测量预算、跨架构校准。

#### 实验框架

```text
代码对+硬件描述 → 预测及置信度 → 低置信度真机执行 → 在线校准
```

#### 可行性与风险

可从小模型分类器开始；风险是不同硬件标签成本高。

## 12. 最小可行 Demo

### 12.1 Demo 目标

评估静态判别能否减少真机测量次数。

### 12.2 输入数据

100 对 PolyBench 编译候选及实际时间标签。

### 12.3 执行流程

```text
训练代码对分类器 → 按置信度排序 → 只执行低置信度/高潜力候选 → 比较预算
```

### 12.4 需要的工具

Clang、Python、轻量 Code LLM、x86 或 K3。

### 12.5 输出结果

| 阈值 | 判别准确率 | 实测比例 | 找到最优候选比例 |
|---:|---:|---:|---:|

### 12.6 成功标准

在保持大部分最优候选召回率的同时显著减少实测次数。
