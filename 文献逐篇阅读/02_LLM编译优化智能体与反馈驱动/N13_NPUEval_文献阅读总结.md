# NPUEval 文献阅读总结

论文题目：**NPUEval: Optimizing NPU Kernels with LLMs and Open Source Compilers**

作者：Sarunas Kalade、Graham Schelle

发表时间：2025

发表平台：arXiv 预印本

关键词：NPU、AMD AIE、kernel 生成、LLVM-AIE、RAG、编译反馈

> 本文档基于 PDF 全文整理。

## 1. 研究背景

NPU 编程生态年轻、厂商碎片化，训练语料远少于 CUDA。模型容易写出能编译但完全标量化的代码，或幻觉出不存在的向量 API，因此“功能通过”和“真正利用 VPU”是两件事。

## 2. 论文要解决的问题

建立一个可在真实 AMD NPU 上同时评估编译、功能正确性与向量利用率的开放基准，并测量编译反馈和向量示例 RAG 对 LLM kernel 生成的影响。

## 3. 核心方法概述

NPUEval 为每个算子提供 C++ 函数签名、文档、数据移动信息、Python 行为模型和测试向量。生成代码由 LLVM-AIE 编译、MLIR-AIE/IRON 部署到 NPU，再与 Python 输出比较并统计 VPU 周期利用率。

## 4. 实验框架与训练流程

```text
算子提示 + 可选向量 RAG → LLM C++ kernel
 → LLVM-AIE（失败则回传诊断，最多 10 次）
 → MLIR-AIE/IRON 部署 → NPU 实测 → 正确性/向量化评分
```

没有模型训练或强化学习。

## 5. 奖励函数、损失函数或关键公式

无训练损失。功能正确性按输出误差判定：默认绝对误差阈值 1e-2，低精度浮点为 2e-2。性能代理为 VPU 执行周期占处理输入总周期的比例；错误 kernel 记 0。

## 6. 实验设置

### 6.1 数据集来源

102 个常见机器学习算子，包含提示、行为模型、数据移动信息和可选参考 C++。

### 6.2 模型与工具

GPT-4.1/GPT-4o、Claude 3.5/3.7、DeepSeek V3/R1、Llama、Qwen2.5-Coder 等；LLVM-AIE、MLIR-AIE、IRON。真实硬件为 Ryzen 9 7940HS 笔记本内置 AMD NPU。

### 6.3 对比方法

纯系统提示、加入向量 kernel RAG、加入 1/2/5 次编译反馈；temperature=0（推理模型采用默认设置）。

### 6.4 评价指标

编译成功、功能测试通过率、最大绝对/相对误差、执行时间和向量化得分。

## 7. 实验结果与结论

编译反馈通常显著提高正确率，例如 DeepSeek V3 首轮常错误包含 `adf.h`，一次反馈后通过率升至约 42%。表中无 RAG、5 次重编译时，Claude Haiku 3.5、Qwen2.5-Coder 的功能通过率分别为 61.8% 和 68.6%；但加入 RAG 后对应结果可能下降到 53.9% 和 13.7%。RAG 普遍改善向量利用率，GPT-4.1 提升最明显，但编译器特定 pragma 会伤害部分模型。即使强模型、反馈和示例并用，真正向量化且正确的比例仍很低，论文摘要称约 10%。

## 8. 主要创新点

### 8.1 首个开放 NPU kernel LLM 基准

在真实消费级硬件上提供从提示到编译、部署和测量的完整链。

### 8.2 正确性与硬件利用率分开计分

揭示“小模型标量代码正确率高”不等于优化成功。

### 8.3 可复用编译反馈与 RAG 基线

给出适用于新硬件领域的最小 Agent 管线，同时展示 RAG 负迁移风险。

## 9. 局限性

仅 AMD AIE、单一 LLVM-AIE 后端和一台机器；缺少成熟人工最优基线；结果主要是 greedy 单样本，未评估 pass@k。向量 RAG 含编译器特定语法，可能不适配当前后端。

## 10. 阅读后的研究方向反思

NPUEval 最重要的结论是：专用硬件生成必须把“通过测试”和“使用了硬件特性”同时设为门槛。对 RISC-V/RVV 也应防止模型用标量循环伪装成成功向量化。

## 11. 可进一步尝试的研究方向

### 11.1 NPU—RVV 双后端向量语义检索

#### 研究问题

能否检索与后端 API 严格匹配的向量模式，避免跨编译器 pragma 污染。

#### 与原论文的区别

从通用向量例子 RAG 改为编译器版本/ISA 条件检索，并比较 NPU 与 RVV。

#### 可能的创新点

API 类型检查驱动的检索过滤和后端特征覆盖奖励。

#### 实验框架

```text
算子 → 后端标签检索 → 生成 → 编译反馈 → 特征覆盖检查 → 真机性能
```

#### 可行性与风险

K3 可提供 RVV 实测；风险是缺乏等规模 RVV kernel 库。

## 12. 与其他已读文献的关系

与 N17 AutoVecCoder 都区分显式向量化和功能正确；与 N10 GraphGlue 同样使用专用编译器反馈。NPUEval 更像开放评测基准，而非新的训练算法。
