# P0 候选管线与正确性记录实施计划

> 阶段编号：01  
> 状态：待执行  
> 执行者：DeepSeek  
> 审查者：Codex  
> 对应研究阶段：P0（无真实设备管线）  
> 依据：[P0 数据与实验设计规格](../03_设计与实施计划/MAPO-Pass_P0数据与实验设计规格.md)、[预实验实施方案](../MAPO-Pass_预实验实施方案.md)

## 1. 本阶段目标

在 `多平台自适应编译优化框架` 内建立可重跑的 P0 驱动，使同一批版本化候选能够面向 `x86_64`、`aarch64-linux-gnu`、`riscv64-linux-gnu` 编译，并通过本机或 QEMU 完成功能正确性验证；每一次尝试都输出结构化记录。

本阶段完成后允许的结论仅为：**候选生成、三目标交叉编译、功能验证和结果记录管线可运行。**不得报告 ARM/RISC-V 性能收益、候选速度排名或 MAPO-Pass 模型效果。

## 2. 已知前置事实

- WSL2 Ubuntu 24.04 已有 Clang/LLVM 18、QEMU 用户态、RISC-V 和 AArch64 交叉工具链；实际执行前必须重新核验版本。
- `benchmarks/sources/llvm-test-suite` 固定到提交 `3396731658fc485536a2aa690b5eff7b3087df0b`，初始子集含 PolyBench 与 TSVC。
- PolyBench `correlation` 需遵循其官方构建约束，包括 `-DPOLYBENCH_USE_C99_PROTO`，以及需要时的 `-ffp-contract=off -DFMA_DISABLED=1`；此前三目标输出一致仅是冒烟证据。
- 现有 `benchmarks/smoke_polybench.sh` 可参考，但不得把其输出格式直接当作完整 P0 结果格式。

## 3. 本阶段范围

### 必做

1. 新建可版本化的 `program_manifest`、`candidate_manifest`、`input_seed_manifest`；
2. 选择 6–8 个确定性程序，注明程序族、源路径、许可证、输入与浮点比较规则；
3. 注册每程序 16–32 条候选，包含 `-O3` 回退项；候选定义和随机种子在运行前冻结；
4. 实现或补全 P0 驱动：编译、链接、运行、超时、参考输出比较、哈希、IR/汇编特征索引、JSONL 记录；
5. 在三目标上运行所有注册的程序—输入—候选组合；
6. 生成一个唯一 `run_id` 的完整结果目录；
7. 将本计划要求的反馈写入 [01_P0候选管线与正确性记录_DeepSeek反馈.md](01_P0候选管线与正确性记录_DeepSeek反馈.md)。

### 明确不做

- 不记录或比较 QEMU 耗时；
- 不训练收益模型、风险模型或响应指纹；
- 不修改 LLVM 后端；
- 不下载无版本/无许可证说明的大型 benchmark；
- 不依据失败或结果临时更换候选、程序或随机种子。

## 4. 实施步骤

### Step A：环境与来源复核

记录 `clang --version`、`opt --version`、交叉链接器、`qemu-aarch64`、`qemu-riscv64`、Python 与 WSL 信息。核对 LLVM test-suite 提交哈希和稀疏检出路径。若缺少工具，仅报告缺项和安装建议；涉及系统安装时先在反馈中说明。

### Step B：冻结三份 manifest

在 `benchmarks/` 或适当的 P0 配置目录创建：

```text
program_manifest.json
candidate_manifest.json
input_seed_manifest.json
```

`program_manifest` 至少包括 `program_id`、`family`、`source`、`dataset/input`、`reference_mode`、`float_rule`。`candidate_manifest` 至少包括 `candidate_id`、`base`、`pass_sequence`、`generation_rule`、`seed`。随机输入不可由候选运行结果决定。

### Step C：实现 P0 驱动与 run 契约

驱动必须创建：

```text
runs/<run_id>/manifest.json
runs/<run_id>/candidates.jsonl
runs/<run_id>/summary.csv
runs/<run_id>/artifacts/
```

每一条 `candidates.jsonl` 记录必须有程序、输入、目标、候选、完整编译命令、二进制哈希、正确性状态、退出码、输出哈希、stderr 路径、IR/汇编特征路径和时间戳。目标运行时间字段若存在，必须显式标记 `simulated_or_qemu_only`，且不可用于汇总排名。

### Step D：参考与正确性执行

每个程序先构建独立参考输出。整数程序使用逐字节或哈希比较；浮点程序使用 manifest 固定的绝对/相对误差规则或官方严格 FP 配置。对每一候选执行 5 个边界输入与 20 个固定随机种子；编译失败、崩溃、超时和输出不一致均写入 JSONL。

### Step E：自检与提交反馈

检查 manifest 哈希、记录数量、每一状态数量、三目标覆盖、失败日志是否存在。新建反馈 Markdown，逐条填写第 6 节验收对照，状态标为“待审查”。

## 5. 约束与实现选择

- 可以使用 Clang 前端开关或 `opt` Pass pipeline 实现候选，但必须在 `candidate_manifest` 中完整表达；
- 任何候选若只在一个目标能编译，仍要记录其他目标的失败，不得从候选池删除；
- PolyBench 输出编码和浮点 FMA 差异必须按官方 CMake/源代码约束处理；
- 可为缩短 P0 首轮运行使用 SMALL_DATASET，但每个程序的输入策略必须如实记录；
- 新增脚本、配置和文档仅写入 `多平台自适应编译优化框架`，不得改动 EPAS；
- 运行目录可新增，但不得覆盖既有 run；每次运行用新 `run_id`。

## 6. 阶段验收条件

| 编号 | 验收项 | DeepSeek 需提供的证据 |
|---:|---|---|
| A1 | 工具链与基准来源可复核 | 版本命令原始输出、提交哈希、路径 |
| A2 | 6–8 程序与输入规则已冻结 | 三份 manifest 的路径与哈希 |
| A3 | 每程序 16–32 候选已注册 | 候选数统计、候选 manifest、种子 |
| A4 | 三目标均尝试全部注册组合 | `candidates.jsonl` 记录数和目标覆盖统计 |
| A5 | 接受候选经既定输入集验证 | 参考输出规则、输出哈希/容差结果 |
| A6 | 失败候选未丢失 | 各状态计数、至少一个失败日志样例或“无失败”证据 |
| A7 | 结果可复现 | `run_id`、manifest、完整命令、二次局部重跑结果 |
| A8 | 未产生伪性能结论 | 汇总字段说明；确认 QEMU 时间未参与排序 |

任何 A1–A8 未满足时，本阶段状态为“未通过”或“待补证”，不得进入 P2。

## 7. DeepSeek 反馈要求

反馈文件必须使用 [协同执行与反馈规范](00_协同执行与反馈规范.md) 的模板，并额外提供：

1. 三份 manifest 的完整相对路径、文件哈希与前 3 条示例；
2. `run_id`、`candidates.jsonl` 总记录数，以及按目标、程序、状态的交叉统计；
3. 每个程序的参考构建规则、输入数量和浮点比较规则；
4. 至少一次 AArch64/QEMU 与 RISC-V/QEMU 的输出一致性证据；
5. 所有新增/修改文件清单；
6. 若只完成子集，明确列出未完成的程序、候选、目标和原因；
7. 最终只写“待 Codex 审查”，不得自行宣布 P0 已完成。

## 8. Codex 审查后的可能决策

- 全部 A1–A8 通过：创建 P2 真实平台差异实验计划；
- 管线可运行但覆盖不足：创建 P0 补齐计划；
- 交叉目标存在系统性错误：先创建工具链/正确性修复计划；
- 候选不可控或不稳定：收缩 Pass 白名单并重新冻结候选 manifest；
- 缺少真实设备：P0 通过后停在 P1/P2 准备，不虚构性能结果。
