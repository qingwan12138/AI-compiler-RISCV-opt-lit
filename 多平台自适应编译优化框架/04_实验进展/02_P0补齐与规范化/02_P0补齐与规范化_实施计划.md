## 1. 本轮范围

第一轮只证明了 `gemm`、`atax` 的 5 个候选在三目标下可完成一次冒烟验证；`p0_val2` 不具备正式 P0 的记录、输入覆盖和可恢复执行能力。

本轮必须完成：

1. 指定唯一的正式 P0 驱动；
2. 修订输入协议，禁止把相同 PolyBench 配置的重复运行称为不同输入；
3. 建立不可覆盖的 run 工件和完整 JSONL 字段；
4. 以可恢复批次完成规定的三目标候选验证，并输出覆盖统计；
5. 验证失败记录、浮点规则和 QEMU 边界。

`p0_validate.py`、`p0_val2.py` 及已有 run 均不得删除或覆盖；统一标记为“历史冒烟 / 非正式 P0 证据”。

## 2. 固定决策

### 2.1 正式入口与运行目录

只允许一个正式入口，例如 `benchmarks/p0/driver/p0_driver.py`。`run_id` 使用：

```text
p0-YYYYMMDDTHHMMSSZ-<short-config-hash>
```

若目录已存在，驱动必须拒绝覆盖。续跑只能通过显式 `--resume`，并在 manifest 记录父 run 与已完成分片。

### 2.2 分类输入协议

| 程序类别 | 正确性输入要求 | 禁止行为 |
|---|---|---|
| 编译期固定数据的 PolyBench | 至少 5 个预注册、语义不同的编译期 dataset/dimension 配置 | 用重复运行伪装成 25 个输入 |
| 接受参数或种子的程序（TSVC） | 5 个边界输入 + 20 个预注册固定参数/seed | 让所有参数共用默认 `.reference_output` |

每一个 `input_id` 必须能对应到真实编译宏或 `argv`。若某程序无法提供五个不同配置，反馈中必须标为 `not_applicable` 并请求 Codex 决策；不得自行降低标准。TSVC 不改源码、不随意改 `RUN_OPTIONS`；对每个冻结输入以同输入的 `-O0` 参考二进制建立参考输出。

### 2.3 QEMU 边界

QEMU 仅用于功能验证。可记录 `diagnostic_elapsed_s` 管理超时，但必须同时标记 `simulated_or_qemu_only=true`，不得生成跨目标排名、加速比或性能结论。默认 QEMU 正确性超时可设为 120 秒，超时必须保存命令、阈值与 stderr。

## 3. 必做实施项

### A. 冻结修订 manifest

新建版本化 manifest，不覆盖第一版：

- `program_manifest`：程序类别、每个输入的语义、浮点规则与参考策略；
- `candidate_manifest`：维持已有 20 候选，不依据第一轮结果增删；
- `input_seed_manifest`：列出五个真实 PolyBench 编译期配置，以及 TSVC 的 5 + 20 个输入；
- `p0_config_manifest`：目标、超时、QEMU 前缀、驱动版本、执行范围和 resume 规则。

运行前计算并写入全部 SHA-256。

### B. 规范正式驱动和 run 契约

每个 `program × input × target × candidate` 都要写一条 JSONL：

```text
run_id, program_id, program_family, input_id, input_config,
target_triple, compiler_version, candidate_id, pass_sequence,
compile_command, binary_hash, correctness_status, exit_code,
timeout_status, output_stream, output_hash, stdout_path, stderr_path,
ir_features_path, assembly_features_path, simulated_or_qemu_only,
diagnostic_elapsed_s, timestamp
```

状态只能是 `compile_failed | link_failed | run_timeout | crashed | incorrect | accepted`。每个非接受状态保存 stderr 和可重放命令。正式 run 必须有：

```text
runs/<run_id>/manifest.json
runs/<run_id>/candidates.jsonl
runs/<run_id>/summary.csv
runs/<run_id>/coverage.csv
runs/<run_id>/artifacts/
runs/<run_id>/logs/
```

`manifest.json` 保存环境原始版本输出、Git 提交、WSL、全部 manifest 哈希、种子、开始/结束时间和父 run。每个成功二进制须保存或索引 LLVM IR 与汇编工件。

### C. 正确性和浮点规则

- PolyBench 按每个 `input_id` 独立构建 `-O0` 参考；
- `correlation`、`covariance` 的所有候选、全部目标实际传入 `-DPOLYBENCH_USE_C99_PROTO -ffp-contract=off -DFMA_DISABLED=1`，并在 `compile_command` 中可见；
- 不得将“`float_rule=abstol=1e-5`”与未经解析的输出哈希混用。要么使用官方严格 FP 后的精确哈希，要么实现并保存真实绝对/相对容差比较；
- TSVC 每个参数输入使用同输入的参考二进制输出。

### D. 批次执行和覆盖审计

每个批次后更新 `coverage.csv`：预期、已尝试、accepted、compile_failed、timeout、crashed、incorrect 和剩余数。不得因 QEMU 慢而删减候选池。

本轮最低覆盖：

- 6–8 个冻结程序，每程序全部 20 候选，三目标均完成**编译尝试**；
- `gemm`、`atax`、`correlation`、`covariance` 各完成 5 个不同 PolyBench 配置的三目标正确性验证；
- 至少一个 TSVC 程序完成 5 个边界输入的三目标正确性验证；
- 未完成组合必须在 `coverage.csv` 中精确列出，附失败或暂停原因。

完整 P0 仍要求所有冻结组合按适用输入协议完成。本轮覆盖不足只能写“P0 补齐进行中”，不能写“P0 通过”。

### E. 失败路径夹具

在独立测试夹具中传入无效源路径或无效编译参数，验证驱动记录 `compile_failed`、命令和 stderr。该夹具不能加入正式候选统计，也不能污染候选 manifest。

## 4. 禁止项

- 不进入 P2、不计时、不训练模型；
- 不覆盖/删除第一轮脚本、run 和反馈；
- 不修改 LLVM test-suite 源码以缩短 QEMU；
- 不因执行耗时缩小范围却宣称完整覆盖；
- 不安装大型依赖，除非在反馈中说明必要性与影响。

## 5. 验收条件

| 编号 | 验收项 | 必须证据 |
|---:|---|---|
| B1 | 输入协议修订正确 | 修订 manifest 哈希、五个真实 PolyBench 配置、TSVC 参数清单 |
| B2 | 唯一正式驱动且不覆盖 run | 入口路径/哈希、重复 run ID 拒绝或 resume 日志 |
| B3 | run 工件契约完整 | manifest、JSONL、汇总、覆盖表、日志、工件目录 |
| B4 | JSONL 字段与失败记录完整 | 3 条 accepted 和失败夹具原始记录及日志 |
| B5 | 浮点规则实际生效 | correlation/covariance 全候选三目标编译命令和验证证据 |
| B6 | 最低覆盖完成 | 第 3.D 节的精确覆盖统计 |
| B7 | 可恢复与可复现 | 新 run ID、resume、一次局部重放 |
| B8 | QEMU 边界保持 | 无排名/加速比，所有 QEMU 记录带模拟标记 |

任一 B 项未通过时，只能补证或返工；B1–B8 全部通过后才由 Codex 决定 P0 是否完成或是否创建 P2 准备计划。
