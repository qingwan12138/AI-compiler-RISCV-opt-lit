# FAME-Opt 预实验实施方案

## 1. 预实验目标

预实验按顺序回答五个问题：

### P0：基础管线能否稳定运行

完成：

```text
编译 → 正确性 → 重复计时 → 保存原始记录
```

### P1：LLM 能否生成合法有效的受限候选

检查 JSON 合法率、编译成功率、正确率和重复候选率。

### P2：是否存在超过 `-O3` 的稳定候选

若完全没有，先调整 benchmark、输入和动作空间，不直接上 RL 或多平台。

### P3：是否存在偶然成功和机制无收益

如果不存在可观察的错误归因，FOEU 的核心动机需重新评估。

### P4：选择性反事实和双证书是否改善经验质量

必须证明它们不是只增加日志和时间。

# 2. 环境与工具

## 2.1 操作系统

优先原生 Linux。Windows + WSL2 可先跑管线，但正式性能计时要评估虚拟化噪声。

## 2.2 最低工具

```text
clang
opt
llvm-dis
llvm-as
llvm-size
llvm-objdump 或 objdump
Python 3.10+
CMake/Make
```

建议：

```text
hyperfine
perf
pytest
ASan
UBSan
```

可选：

```text
Alive2
llvm-mca
```

`llvm-mca` 只作代理证据，不能代替真实运行时间。

# 3. Benchmark 选择

## 3.1 Demo 数量

5–8 个。

## 3.2 推荐类型

| 程序 | 类型 | 可能动作 |
|---|---|---|
| dot product | reduction | 向量化、展开 |
| saxpy | 连续访存 | 向量化、interleave |
| stencil 1D | 邻域访存 | 展开、向量化 |
| small GEMM | 计算密集 | 展开、内联 |
| branch filter | 分支密集 | 禁止错误向量化、布局 |
| stride sum | 非连续访存 | 展开、输入边界 |
| function chain | 调用密集 | 内联阈值 |
| conditional reduction | 混合 | 分布、向量化 |

## 3.3 每个程序必须具备

- 参考实现；
- 确定性输入；
- 小、边界、大输入；
- 固定随机种子；
- 独立计时区域；
- 输出校验；
- 运行时间足够长。

超短 kernel 应在程序内部重复，不把进程启动开销当 kernel 时间。

---

# 4. 首版动作空间

控制在 8–12 个宏动作。

| 动作 ID | 动作 | 参数 |
|---|---|---|
| A1 | 循环向量化 | on/off |
| A2 | SLP 向量化 | on/off |
| A3 | 循环展开 | 1/2/4/8 |
| A4 | interleave | 1/2/4 |
| A5 | 内联阈值 | low/default/high |
| A6 | 循环分布 | on/off |
| A7 | `-march=native` | on/off |
| A8 | 受限 Pass 宏动作 | 预定义模板 |
| A9 | 禁用一个已允许优化 | 受限列表 |
| A10 | 速度/尺寸偏好 | 受限枚举 |

约束：

- LLM 不直接输出任意命令；
- 每个候选最多 3 个非默认动作；
- 所有方法共享相同执行器；
- 不允许改变测试、输出和计时区域。

---

# 5. 输入集合

每个程序至少：

1. 小输入；
2. 典型输入；
3. 大输入；
4. 两个边界输入；
5. 三个固定随机输入。

向量循环示例：

```text
n = 31
n = 32
n = 33
n = 1024
n = 1048576
```

输入必须在候选生成前冻结。

---

# 6. 计时协议

## 6.1 预热

3 次，不计入结果。

## 6.2 正式重复

- Demo：7–15 次；
- 正式实验：15–30 次。

## 6.3 统计

保存全部原始值，报告：

- 中位数；
- MAD 或四分位距；
- 加速比；
- bootstrap 置信区间。

```text
Speedup = Median(T_O3) / Median(T_candidate)
```

初始接受阈值：

```text
LowerCI(Speedup) > 1.01
```

若机器噪声较大，提高至 1.02。

# 7. 分阶段实施

## P0：基础管线

### 程序

2 个。

### 候选

- `-O0`；
- `-O2`；
- `-O3`；
- `-O3 -march=native`。

### 工作

- 编译；
- 固定输入；
- 输出哈希；
- 重复计时；
- JSONL；
- 错误、超时记录。

### 验收

- 同一配置可复现；
- 失败不静默删除；
- 基线前后无明显漂移；
- 所有原始时间可追踪。

---

## P1：受限 LLM 候选

### 程序

3 个。

### 每程序

生成 3 个候选。

### 指标

- JSON 合法率；
- 动作合法率；
- 编译成功率；
- 正确率；
- 候选重复率。

### 建议最低条件

- JSON 合法率 ≥ 90%；
- 编译成功率 ≥ 80%；
- 正确率 ≥ 80%。

未达到时先改 Schema、动作空间和提示词，不训练模型。

---

## P2：性能闭环 Demo

### 程序

5–8 个。

### 候选预算

每程序 6–8 个，最多 3 轮。

### 流程

1. `-O3` Profile；
2. Round 1 生成 2–3 个候选；
3. 反馈正确性、Remark、运行时间；
4. Round 2 生成 2–3 个修正候选；
5. Round 3 精炼或停止；
6. 选择最优候选。

### 对比

- `-O3`；
- 随机动作；
- 无反馈 LLM；
- 只给运行时间的 LLM；
- 普通编译反馈 LLM；
- FAME-Opt 初版。

### 规模示例

```text
8 程序 × 8 候选 × 10 正式运行 = 640 次候选运行
```

另加基线和预热。该规模适合自动脚本，不需要多平台。

### 继续条件

以下至少两项成立：

- 至少 2 个程序稳定超过 `-O3` 2%；
- 几何平均不低于 `-O3`；
- LLM 比随机用更少候选达到同等最佳性能；
- 负优化率低于随机或无反馈 LLM。

---

## P3：FOEU 机制审计

对每个程序选择：

- 最优候选；
- 一个明显负优化；
- 一个机制冲突候选。

构建 10–20 个挑战案例：

- 声称向量化但无向量汇编；
- 展开发生但代码膨胀导致变慢；
- 内联发生但无收益；
- 多动作无法归因；
- 加速来自未声明动作；
- 单一输入加速但边界输入退化。

输出四态：

```text
confirmed_success
accidental_success
mechanism_without_profit
failed
```

验收：

- 至少识别一类普通性能日志无法区分的案例；
- 分类基于明确证据；
- 不依赖人工随意解释。

---

## P4：最小反事实

比较：

1. 不做反事实；
2. 所有候选固定探针；
3. 只审计每程序最佳候选；
4. 信息价值规则调度。

指标：

- 总编译；
- 总运行；
- 归因准确率；
- 偶然成功识别率；
- 单位预算确认经验数。

成功标准：

- 选择性方法保持接近的分类质量但更省测量；
- 或相同预算识别更多高价值经验。

---

## P5：双证书与未见程序

按程序族划分，禁止同模板泄漏。

比较：

- 无记忆；
- 所有成功样本；
- 确认成功 FOEU；
- FOEU + 负经验；
- 完整双证书。

指标：

- 未见程序加速；
- 达标候选数；
- 负优化率；
- 错误经验复用率；
- 回退 `-O3` 比例。

# 9. Demo 最小展示

建议展示：

1. 各程序不同方法的最优加速；
2. 达到 1% 或 2% 提升的候选数；
3. 四态 FOEU 实例；
4. 选择性与全量反事实成本；
5. 双证书拒绝的正确但变慢案例。

---

# 10. 无提升时的调整顺序

1. `-O3` 是否已完全优化；
2. 动作是否实际改变 IR/汇编；
3. 输入规模是否过小；
4. 计时噪声；
5. 机制是否发生；
6. benchmark 是否适合动作空间；
7. 是否加入安全 Hint 或更多受限动作。

不要第一时间增加多平台、RL 或更多 Agent。
