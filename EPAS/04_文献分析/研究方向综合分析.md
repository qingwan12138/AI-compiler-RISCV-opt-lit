## 0. 先给结论

这批文献共同呈现出一条清晰演化路线：

```text
传统 Pass / 张量程序搜索
        ↓
编译器环境与性能代价模型
        ↓
LLM 生成、工具调用与验证
        ↓
真实后端、向量 ISA 与 RISC-V 实机
        ↓
跨平台知识迁移与可解释的优化意图
```

从现有工作看，以下内容本身已经不能作为强创新：

- 单纯使用 LLVM Pass 强化学习；
- 单纯引入 LLM 或多智能体；
- 把 x86 实验换成 RISC-V；
- 把 IR 指令数换成运行时间；
- 给模型增加一个平台 ID 或 Adapter；
- 只做多个平台上的独立实验。

更值得继续凝练的研究问题是：

> **如何让 IR 层智能体学习可迁移的优化意图，并利用不同目标后端的真实反馈，判断该意图在不同架构上是否真正实现，从而以少量新平台评测完成适应？**

这比“IR Agent + Backend Agent”更像一个科学问题。双智能体应当作为承载框架，核心贡献应落在“跨架构优化知识的表示、分解、验证和迁移”上。

## 2. 文献地图

### 2.1 LLVM Pass 顺序与强化学习

代表工作包括 AutoPhase、HLS phase ordering、CompilerGym 和 Compiler-R1。它们回答了“如何在巨大 Pass 空间中搜索”以及“如何把编译器封装成可交互环境”。主要贡献是状态表示、搜索策略、环境接口和工具反馈。

主要结论：

- Pass 顺序非交换，固定 `-O2/-O3` 不一定是每个程序的最优点；
- IR 特征、已执行 Pass 历史和代理代价可以显著缩小搜索难度；
- RL 或 LLM Agent 可以在有限预算内找到优于固定优化级别的序列；
- 但大多数工作仍停留在单一编译器代理指标或单一目标平台。

### 2.2 LLM 编译器 Agent、验证与代码变换

Compiler-R1、LLM-VeriOpt、LLM-Vectorizer、REASONINGCOMPILER、ACCLAIM、CompilerGPT、VecTrans、IntOpt 和 LPG 代表不同路线：Pass 搜索、语义验证、向量化、MCTS、跨抽象层协作、代码重写、意图/知识库和 peephole 规则泛化。

主要结论：

- LLM 的价值不只是生成代码，也包括工具调用、失败诊断和搜索策略；
- Alive2、差分测试和编译器报告能显著提高正确性或反馈质量；
- “Optimization Intent”已经开始出现，因而仅把 intent 作为自然语言提示不能算充分创新；
- LLM 工作普遍面临评测成本、正确性边界、结果波动和平台泛化问题。

### 2.3 超级优化、形式验证与局部规则生成

Alive/Alive2、Souper、STOKE、Minotaur、LPG 和 missed code-size optimizations 展示了从 SMT 证明、随机搜索到 LLM 规则泛化的完整谱系。

主要结论：

- 局部等价变换可以获得比传统 InstCombine 更细的机会；
- 形式验证适合做“能不能改”的安全边界，但通常是有界的或成本较高；
- 这类工作更适合作为后端智能体的验证/规则生成工具，而不是直接替代全程序调优。

### 2.4 RISC-V、RVV 与真实后端性能

RVV 性能分析、RVV tensor program optimization、IntrinTrans、VecIntrinBench、neon2rvv、RVCC 和 RISC-V intrinsic specification 形成了 RISC-V 侧的实验基础。

主要结论：

- 同样的向量化或循环变换，在不同 RVV 实现和不同工具链上收益不稳定；
- predication、stride、LMUL、寄存器压力和指令映射会造成 IR 代理指标与真实性能不一致；
- RVV 迁移和 intrinsic 生成已有 LLM/多智能体工作，因此“LLM 生成 RVV 代码”本身不够新；
- RISC-V 更适合作为验证跨架构性能差异、后端反馈和新平台适应的主要实验平台。

### 2.5 张量编译器、代价模型与程序表示

TVM、Ansor、MetaSchedule 相关工作、Learning to Optimize Tensor Programs、Ithemal、ProGraML 和 MLIR 提供了三个重要启发：学习型代价模型、跨硬件迁移、结构化程序表示和多级 IR 基础设施。

主要结论：

- 多平台调优已有共享模型、代价模型和主动搜索方法；
- 因此“共享主干 + Adapter”需要和编译语义、后端行为或主动校准结合，不能单独作为核心创新；
- 这些工作可以作为 CrossTune-RL 的模型、表示和搜索基线。

## 4. 现有工作已经覆盖什么

### 已经比较成熟的方向

1. **Pass 搜索与代理指标优化**：RL、进化搜索、LLM 工具调用均已有代表性工作。
2. **编译器环境与代价模型**：CompilerGym、TVM、Ansor、MetaSchedule 等已经提供成熟范式。
3. **LLM 代码/IR 变换与验证**：Alive2、差分测试和编译反馈已经形成工具链。
4. **多抽象层 Agent 协作**：ACCLAIM 等工作说明“多个层次/多个 Agent”本身不够新。
5. **特定 ISA 的迁移与向量化**：NEON→RVV、RVV intrinsic、RVV tensor tuning 已有工作。
6. **共享模型与跨硬件调优**：张量编译领域已有多硬件 cost model、迁移学习和主动采样。

### 不能直接写成创新的内容

| 想法 | 为什么不够 | 需要升级为 |
|---|---|---|
| IR Agent + Backend Agent | 结构已有相邻工作 | 明确跨层协作变量、训练目标和可检验收益 |
| 多平台输入一个平台 ID | 只是条件输入 | 行为感知平台表示或跨架构效应分解 |
| x86/ARM/RISC-V 分别测试 | 属于实验覆盖 | 未见平台少样本适应和迁移效率 |
| 反事实奖励公式 | 多智能体已有通用方法 | 编译成本约束下的低成本分层反事实估计 |
| 优化意图自然语言 | IntOpt 等已相邻 | intent→后端实现的可验证、跨架构对齐 |
| RISC-V 真实运行 | 是平台选择 | 用平台差异检验可迁移知识和代理指标失效 |

## 5. 推荐的核心研究问题

### RQ1：哪些 IR 优化知识可以跨架构迁移？

将优化效果拆成三类：

$$
\Delta R(P,a^{IR},a^{BE},h)
=
R_{shared}+R_{arch}+R_{syn}
$$

- `R_shared`：多个平台上稳定有效的优化效应；
- `R_arch`：由平台、微架构或工具链条件决定的效应；
- `R_syn`：IR 动作与后端动作协同才出现的效应。

这比简单共享参数更有研究内容，因为它直接研究“可迁移知识的边界”。

### RQ2：如何判断 IR 意图是否被后端真正实现？

IR Agent 不只输出 Pass，而输出结构化意图，例如“减少访存”“暴露向量化”“提高 ILP”“控制寄存器压力”。后端根据 MIR、汇编和真实性能返回实现结果：

$$
L_{align}=Align(C^{down},\Delta F^{BE},R_{hardware})
$$

关键不是消息格式，而是：意图实现误差能否指导下一次 IR 决策，以及这种反馈是否比最终单一 reward 更有效。

### RQ3：新平台需要多少真实评测才能适应？

新平台适应应包含明确的预算：

$$
K\in\{0,5,10,20,50\}
$$

主动选择 `(程序, IR 动作, 后端动作)` 作为校准样本，并比较随机校准、最近平台迁移、共享模型和你的方法在 `Speedup@K` 上的差异。

## 6. 建议的 CrossTune-RL 研究定位

### 6.1 框架定位

```text
IR Optimization Agent
    ├─ 选择 Pass / Pass 宏动作
    ├─ 输出优化意图
    └─ 根据后端诊断调整或停止
             ↓ 跨层状态/意图接口
Target Backend Agent
    ├─ 分析 MIR/ASM/机器指令
    ├─ 选择目标相关配置
    ├─ 预测或请求真实硬件评测
    └─ 返回实现程度和瓶颈诊断
             ↓
多平台编译、运行、验证与适应
```

### 6.2 三个更像“你自己的”核心贡献

#### 贡献 A：跨架构优化效应分解

建立共享效应、平台效应和跨层协同效应的联合性能模型，并用跨平台配对轨迹训练/验证。反事实奖励可以作为估计工具，但不把通用反事实公式本身包装成创新。

#### 贡献 B：可验证的 IR 意图—后端实现对齐

用可计算的意图向量和后端事件/机器码特征表示“希望发生什么”和“实际发生什么”，根据对齐误差更新 IR 策略。必须证明它能识别典型反例：IR 指令数下降但运行时间变差，或 IR 变大但后端更快。

#### 贡献 C：基于架构关系和主动校准的未见平台适应

根据平台对编译动作的响应相似度构建架构关系；从相似平台组合知识；主动选择最有信息价值的校准实验；冻结共享知识，只更新轻量平台参数。核心指标是少量真实运行下的适应曲线，而不是平台数量。

### 6.3 硬件行为指纹的定位

硬件行为指纹是一个可选但很有价值的实现机制：用小型探测程序测量访存、分支、向量、ILP、寄存器压力和 I-Cache 等行为，生成平台嵌入。它应服务于贡献 C，而不是脱离编译调优单独成为“硬件测量论文”。

## 7. 建议实验框架

### 实验阶段一：建立跨平台配对数据

- 程序：PolyBench、MiBench、SPEC 子集、TSVC、LLVM test-suite 中可稳定运行的程序；
- 平台：至少一个 x86 和一个 RISC-V，条件允许加入 ARM；
- IR 动作：先选 8–12 个 Pass 宏动作，再扩展到细粒度 Pass；
- 后端动作：选少量可稳定控制的目标参数/配置；
- 记录：IR 特征、MIR/汇编特征、代码尺寸、spill、向量/分支/访存计数、运行时间/周期、正确性。

### 实验阶段二：验证代理指标失效与效应分解

统计 `R_IR` 与 `R_runtime` 的相关性，并分类：

| IR 指标 | 真实后端 | 解释 |
|---|---|---|
| 改善 | 改善 | 一致样本 |
| 改善 | 下降 | 代理指标误导 |
| 下降 | 改善 | 代理指标漏掉收益 |
| 下降 | 下降 | 无效样本 |

再比较单一模型、共享+平台条件模型和显式效应分解模型的候选排序能力。

### 实验阶段三：验证双层协作

基线至少包括：

1. `-O2/-O3/-Oz`；
2. IR-only 搜索；
3. Backend-only 调参；
4. 单智能体联合搜索；
5. 简单串联双 Agent；
6. CrossTune-RL 去掉 intent 对齐；
7. CrossTune-RL 去掉效应分解；
8. 完整方法。

指标：真实性能、正确率、编译/运行次数、搜索时间、未见程序泛化、IR 与后端收益一致性。

### 实验阶段四：未见平台少样本适应

训练平台与测试平台严格分离。设定 `K=0,5,10,20,50` 个校准样本，比较：

- 从零训练；
- 随机校准；
- 最近平台迁移；
- 共享策略无平台条件；
- 共享策略+静态平台信息；
- 共享策略+行为指纹；
- 行为指纹+架构关系+主动校准。

核心结果图应是 `Speedup@K`、真实性能评测次数和适应后的未见程序泛化。

## 8. 最小可行 Demo

第一版不需要完整 LLM+双 Agent+多平台 RL。建议按以下顺序落地：

1. 选 10 个 Pass 宏动作和 20–50 个小程序；
2. 在 x86 本机和一个 RISC-V 环境上生成 100–500 条配对轨迹；
3. 记录 IR 指令数、RISC-V 机器码大小、spill/访存/分支特征和运行时间；
4. 用一个小模型预测 `R_shared/R_arch/R_syn`，先验证效应分解是否能提高候选排序；
5. 再加入结构化 intent，并让后端返回“意图是否实现”的诊断；
6. 最后加入一个未见平台或同 ISA 新微架构的少样本适应实验。

第一篇论文/硕士阶段的主线可以先收敛为：

> **面向跨架构真实性能的 IR 优化意图—后端实现对齐与少样本适应。**

## 9. 风险与收敛建议

### 风险一：双 Agent 范围过大

解决：先让 IR Agent 负责候选生成，Backend Agent 先做性能预测/诊断策略网络；不要一开始训练两个 LLM。

### 风险二：真实硬件噪声

解决：固定频率/隔离环境/多次运行取中位数，记录方差；把运行次数作为预算；先使用静态后端特征筛选。

### 风险三：跨平台数据不对齐

解决：同一源码、同一输入、同一正确性测试和尽量一致的编译链；明确 `target triple`、`-march`、`-mabi` 和运行环境。

### 风险四：创新被已有 intent/迁移工作覆盖

解决：不要声称“首次提出 optimization intent”或“首次多平台迁移”；把新意压在“跨架构效应分解 + 后端可验证实现对齐 + 主动少样本适应”的组合机制和专门实验上。

## 10. 最终建议

当前最稳妥的论文主张不是：

> 我们设计了两个智能体，并在 RISC-V、x86 和 ARM 上测试。

而是：

> **我们研究 IR 优化知识在不同目标架构上的可迁移边界。系统通过平台条件化的 IR—后端协作，显式区分跨平台共享效应、平台特定效应和跨层协同效应，并利用后端真实性能验证 IR 优化意图；对于未见平台，系统通过架构关系和主动校准，在有限真实评测预算下快速适应。**

这条主线能够自然容纳 CrossTune-RL，但不会把“双智能体”误当成全部创新。
